# The program

`eu4.exe` as a program: what it is built of, what it does from its start to the main menu, how one frame runs, the threads beside the main one, the files and folders it reads and writes, how it saves and loads a game, and how it leaves a session. The systems a frame runs, the day among them, have pages of their own: [day.md](day.md), [interface.md](interface.md), [scripts.md](scripts.md).

## What it is built of

- **Three layers**: third-party libraries, the Clausewitz engine and the game itself; the game calls the engine, and both call the libraries ([research/architecture.md](../research/architecture.md), "Layers").
  - The libraries linked in: SDL 2 (the window, input, threads, sound), PhysFS (the file system over folders and zip archives), Lua 5.1 (the defines), boost, FreeImage, zlib and libcurl; imported: Direct3D 9 (and OpenGL), TBB, and the platform services, Steam, Epic, Nakama for multiplayer matchmaking and Paradox's own accounts ([research/architecture.md](../research/architecture.md), "Layers").
  - The engine's libraries hold the application and its states, the session and its commands, the random generator, the script reader, the file system, the graphics back end, sound, localisation and the platform services ([research/architecture.md](../research/architecture.md), "Layers").
  - The game's own code is the game state and its objects, the commands, the AI, the script engine (triggers, effects, modifiers, events: the bulk of the code), the map, multiplayer and the interface's views ([research/architecture.md](../research/architecture.md), "Layers").
- **Where its code lies tells where it comes from**: the game's source files lie in the order of their names, and each engine library's together, so an address in the game part says roughly which source file a function is of ([research/architecture.md](../research/architecture.md), "Where the code lies").
- **No class names ship with it**: there is no PDB and almost no RTTI; names come from the source paths in asserts and log lines, and from the token table of every script word the game knows ([research/architecture.md](../research/architecture.md), "The build").

## From the start to the main menu

- **`main`** (`0x8757e0`) checks for a second instance, reads the command line and the game's own options (`-userdir`, `-continue`, `-seed`, `-debug` and others), starts Steam and Epic, starts two pools of worker threads, reads `settings.txt` and makes the window, makes the platform services, sets up the file system, the DLCs and mods and the crash reporter, loads the localisation, and makes the application, whose Init brings up graphics and sound ([research/architecture.md](../research/architecture.md), "Startup").
- **The instance check finds nothing.** It looks for a window of a class no window of the game's has, since the game's window is SDL's, so a second game starts and runs beside the first ([research/several-games.md](../research/several-games.md), "The game's instance check never finds anything").
- **The startup load** runs on a thread of its own, the LoadingThread, while the main thread only keeps the window's messages and the online services going ([research/architecture.md](../research/architecture.md), "Startup"). It has two steps:
  1. the interface's sprite and font definitions (`.gfx`), the map, `shortcuts.txt` and the interface's windows (`.gui`), ending in the meshes and particles;
  2. the game's content: about a hundred databases from `common\` in an order fixed in the code (modifiers, country tags and countries, scripted triggers and effects, cultures and religions, trade goods, buildings, governments, ideas, the map's logic, trade nodes, casus belli, missions, decisions, then the history of provinces, countries and wars), then the events, on_actions and disasters, flags and loading screens, the trade nodes' setup, the bookmarks, and a check of every effect ([research/architecture.md](../research/architecture.md), "The databases"; [research/loading.md](../research/loading.md), "The databases").

  It then makes the main menu, which the main thread switches to at its next frame. When the player has not chosen a language yet, the load waits for the language screen and runs on the main thread instead ([research/architecture.md](../research/architecture.md), "Startup").
- **The defines** are Lua: `common\defines.lua` and its folder are run in a Lua state, and some 2,400 values are read out of it by name, each into a variable of its own in the program; the save's reader reads them again ([research/architecture.md](../research/architecture.md), "Defines").
- **The game checksum** is made from the files `checksum_manifest.txt` names, on a thread of the pool beside the databases, and compared with vanilla's ([research/architecture.md](../research/architecture.md), "The virtual file system"; [research/loading.md](../research/loading.md), "The startup after L1 to L3"). Whether achievements are allowed follows from it ([countries.md](countries.md)).
- **What the startup waits on.** With every DLC and the player's mods, the main menu came 46 to 55 s after the start before the framework shortened it, and about 26 s after ([research/loading.md](../research/loading.md), "Startup", "The startup after L5, broken down"). The time went to reading every music file whole and inflating it from the DLCs' zips, to opening and looking up files under two locks while threads beside the load checked that pictures exist, and to the script reader. What is left is mostly the reader's databases and events, one after the other: the events need the databases they name loaded first ([research/loading.md](../research/loading.md), "The startup after L5, broken down", "The events beside the databases: cannot"). Which other stretches could run side by side, and on what conditions, is in [research/loading.md](../research/loading.md), "Which stretches can run side by side".

## The file system

- **Every file the game reads goes through PhysFS**, mounted in this order, each in front of the last: the game folder, `eu4.pdx`, each enabled DLC and mod, then the user folder, which is also where the game writes. So the user folder's file wins over a mod's, a mod's over a DLC's (the last mounted first), and those over the game folder's (inferred) ([research/architecture.md](../research/architecture.md), "The virtual file system").
- **One function opens every game file** (`0x1718300`), under a lock; listings of folders go through a set registered at startup, and each mod's `replace_path` is kept for the lister ([research/architecture.md](../research/architecture.md), "The virtual file system"; [research/loading.md](../research/loading.md), "The startup after L1 to L3").
- **A lookup walks the whole search path**: the game folder, the user folder, the playset's mods and the DLCs' 123 zips, asking each in turn, and asking Windows for each folder ([research/loading.md](../research/loading.md), "Startup", "The databases with L4").
- **The user folder** is the one `userdir.txt` in the game folder names, or `-userdir`, and otherwise `Documents\Paradox Interactive\Europa Universalis IV`. The game uses the text of `userdir.txt` untrimmed, so a line break after the path makes another folder; a path beginning with `.` is relative to the game folder ([research/user-folder.md](../research/user-folder.md)).
- The framework adds files of its own, the framework files, mounted after every other place ([ADR framework-files-in-the-game-file-system](../adr/2026-11-03-framework-files-in-the-game-file-system.md)).

## A frame

- **The application** runs one frame after another until the player quits or the game restarts: the platform services' callbacks, SDL's input events handed to the current state, the state's own frame, in which everything else happens, and then a switch of state when one was asked for ([research/architecture.md](../research/architecture.md), "The application, its frame and the idlers").
- **The states, idlers in the engine's word**, are the language screen, the main menu, the game ("map manager") and the nudge editor; each has its own frame, input and graphics objects ([research/architecture.md](../research/architecture.md), "The application, its frame and the idlers"). The main menu and the game's frame are on [interface.md](interface.md).
- **In a game, a frame** executes the commands queued since the last one ([scripts.md](scripts.md)), lets time go on, which posts a day once the frames add up to one, updates the interface and draws ([research/architecture.md](../research/architecture.md), "Time", "Presentation"; [day.md](day.md)). A long day runs whole frames inside itself between its stages, so the game keeps drawing and answering input while a day is computed ([research/architecture.md](../research/architecture.md), "Frames inside a day").
- **There is no frame cap** in the frame itself (inferred: vsync paces it); after a present that was not shown, the next frame waits 100 ms ([research/architecture.md](../research/architecture.md), "The application, its frame and the idlers"; [research/headless.md](../research/headless.md), "What the game does when it is not seen").

## Threads

- **The main thread does nearly everything**: input, commands, the game state, the interface and drawing. The game raises its priority and pins it to one processor ([research/architecture.md](../research/architecture.md), "Threads").
- **Beside it**: the LoadingThread at startup; two pools of worker threads, one fewer than the processor's cores each, for the day's parallel stages and loading; sound's two threads; a thread that keeps the network polled while a save is written or read; and TBB's workers in a few places ([research/architecture.md](../research/architecture.md), "Threads"). What runs in parallel inside a day is on [day.md](day.md).
- **Shared, and what is safe from several threads**: the Direct3D device is made multithreaded, the file system's opens and lookups, the log and the heap are safe; making a new script word while the program runs, the timers and drawing the loading screen are not ([research/loading.md](../research/loading.md), "What every stretch shares").

## Saves

- **A save is a zip** of three entries, `meta`, `gamestate` and `ai`, or one plain file holding all three; either way text (`EU4txt`) or binary (`EU4bin`), a stream of script words by their ids. Ironman saves are binary ([research/saves.md](../research/saves.md), "The save file").
- **Writing** goes through one path whatever asked for it: a normal save, an ironman save, a cloud save, a multiplayer hot join, a debug dump ([research/saves.md](../research/saves.md), "Writing"). The world writes its header, its game state (the countries and the provinces the largest parts) and the AI into memory, each ending in its save checksum, then the zip is deflated and written to a `.tmp` file, which replaces the save after the old one is backed up. The result says the world was written, not that the save was replaced ([research/saves.md](../research/saves.md), "Writing", "Where a save's zip goes").
- **Writing stops the game** on the main thread; for a save of 1724 it took 1.0 to 1.4 s in the game's own code ([research/saves.md](../research/saves.md), "Where a save's zip goes"). Two objects the writers share keep the countries and the provinces from being written side by side as the code stands ([research/saves.md](../research/saves.md), "What writing the game state writes").
- **The save checksum** is an MD5 over a sum of the entry, its length and a salt. Once a save that did not match has been loaded, or the game checksum is not vanilla's, the saves of that process are salted so that they never match ([research/saves.md](../research/saves.md), "Writing", "Which salt"). A mismatch never refuses a save; it only takes achievements away ([research/saves.md](../research/saves.md), "Reading"). A plain text save loaded in a session never matched in vanilla, since that load sums the file another way ([research/saves.md](../research/saves.md), "Reading").
- **Reading** goes entry by entry into the world's handler of top-level keys; a key it does not know is an error in `error.log` and is skipped, and a save with errors still loads ([research/saves.md](../research/saves.md), "Reading"). After reading, the world is set up from what was read ([research/saves.md](../research/saves.md), "Reading").
- **The continue information** (`continue_game.json`) is written after every save and read once at startup ([research/main-menu.md](../research/main-menu.md), "The continue information").

## Leaving a session

- **Vanilla restarts**: returning to the main menu, by the game's question or the end-of-game summary, writes the ironman exit save and starts `eu4.exe` again with the same command line and `-skiplauncher`; the new process starts before the old one has ended, and loads the whole game again ([research/main-menu.md](../research/main-menu.md), "Returning to the main menu"; [research/safe-points.md](../research/safe-points.md), "Returning to the main menu"). The main menu is made once a process.
- **The in-game load** is the one way vanilla replaces a session in a process that goes on: a world reset without the game's history, then the save read over it, then the game's interface made again ([research/main-menu.md](../research/main-menu.md), "Loading a save in a game", "The world reset"). Only the interface refuses it in ironman ([ADR in-game-load-in-ironman](../adr/2026-11-03-in-game-load-in-ironman.md)).
- **What a world reset leaves**: some of the old session's state (the Empire's religious status, the achievements), interface windows the map manager never lets go, and memory the game never frees ([research/main-menu.md](../research/main-menu.md), "The world reset", "The memory a world reset and a session leave"). Sprites still counted by that interface are drawn from textures let go after a return, which crashed the game until a repair kept them loaded ([research/main-menu.md](../research/main-menu.md), "A return after time ran").
- **Commands queued in the last day** belong to the application's session, not to the game state, so a session left while time runs carries them into whatever comes next ([research/main-menu.md](../research/main-menu.md), "Leaving while time runs").

## Running unseen, and several at once

- **The window is made shown, and Init shows it again**; nothing else in the game shows it. A hidden window is not occluded, so a hidden game runs as fast as a shown one, once the framework opts it out of Windows' power throttling, which otherwise gives a game no one sees a tenth of a core; a minimized one runs at about ten frames a second and draws one in two ([research/headless.md](../research/headless.md), "What keeps the window on screen", "What the game does when it is not seen").
- **What could still reach the desktop**: the game reads the cursor against the active window, so a hidden game's map scrolls toward a cursor elsewhere; its error message boxes, which `-suppresserrormessages` leaves out; the crash reporter, a program of its own with a window; and sound, which SDL's `dummy` driver silences ([research/headless.md](../research/headless.md), "What could reach the player's desktop", "What the hidden start relies on").
- **The device must be a hardware one**: there is no reference or software device, so the game cannot run without a graphics card ([research/headless.md](../research/headless.md), "The graphics device", "What it would take").
- **Several games run at once** from the one game folder, each with a user folder of its own (`-userdir`); started from another folder, the game loses some DLCs. A game uses about 4 GB of memory and 1.4 GB of graphics memory, and slows a game beside it by 4 to 8% ([research/several-games.md](../research/several-games.md)).

## What the framework relies on

- The framework enters the process as `version.dll` beside `eu4.exe` ([ADR version-proxy-injection](../adr/2026-10-27-version-proxy-injection.md)), and attaches in every layer: the file system, the script tokenizer, localisation, input, Present, the restart, the in-game and main menu frames, the daily update, some commands, the save loader and writer ([research/architecture.md](../research/architecture.md), "Where the framework attaches"). Every such place is a dependency point ([ADR framework-succeeds-or-fails-as-a-whole](../adr/2026-10-27-framework-succeeds-or-fails-as-a-whole.md)).
- Extensions and remote control run at the in-game frame after the commands, and the framework UI is drawn at Present ([research/safe-points.md](../research/safe-points.md); [research/architecture.md](../research/architecture.md), "Presentation").
- The startup made shorter, its loads the same ([plans/loading.md](../plans/loading.md)); the save written with its countries and provinces on threads ([plans/game-speed.md](../plans/game-speed.md), S8).
- Extension save data in the save's game state, last before the checksum ([ADR extension-save-data-in-the-save](../adr/2026-11-02-extension-save-data-in-the-save.md); [research/saves.md](../research/saves.md), "What the framework does").
- The in-process return, which leaves a session as the in-game load does and makes a main menu again ([ADR return-to-the-main-menu-in-process](../adr/2026-11-03-return-to-the-main-menu-in-process.md); [plans/sessions.md](../plans/sessions.md)), with repairs for what the world reset leaves.
- The hidden start ([plans/hidden-start.md](../plans/hidden-start.md)) and test games, several at once ([plans/test-games.md](../plans/test-games.md)).
- A repair of a crash in a subject relation's end, a walk over a list the walk itself clears ([research/dependency-teardown.md](../research/dependency-teardown.md); [countries.md](countries.md)).

Vanilla's startup without the framework on the same machine was not timed ([research/loading.md](../research/loading.md), "Not looked into").
