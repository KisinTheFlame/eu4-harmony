# Adding a capability

How a capability reaches both extensions and remote clients, layer by layer, and what is done before it is merged. Terms are in [GLOSSARY.md](../GLOSSARY.md); the rules that shape a capability are in [ADR one-capability-catalogue](adr/one-capability-catalogue.md), [ADR one-command-layer-in-written-form](adr/one-command-layer-in-written-form.md) and, for the panels' actions, [player-actions.md](player-actions.md).

## Before writing code

- **Find it in the game first.** What the panel's button checks, the reasons its tooltip gives, the command it posts and that command's written form, the fields the panel reads. The command log of a developer build ([dev-tools.md](dev-tools.md)) shows a button's command in its written form when the player presses it in the game; `cargo xtask disasm` finds the code. Write what was found into `docs/research/`, addresses as RVAs into the 1.37.5 baseline, before or with the code.
- **Name it after what the player sees and does**, in the group of the panel it is on: `estate.grant_privilege`, not after the command (`grant_privilege`) or a field. What the player chooses among is named by its content key.

## The layers

1. **The catalogue** (`remote/src/<group>.rs`): the capability in its group's `group!` list, with its arguments, result and descriptions; a new group also goes into `groups!` in `remote/src/lib.rs`. `game`, `world` or `anywhere` for one extensions and remote control both have, `remote_game`, `remote_world` or `remote_anywhere` for one only remote control has; the `game` kinds run only while a game is going on with a country the player plays, the `world` kinds while a game is going on, also while the player only observes it (the time group), the `anywhere` kinds at the main menu too. A result is a struct deriving `Shaped`, with each field described; the shared `Choice`, `Amount` and `Acceptance` are in `remote/src/choices.rs`. An argument of a new kind adds a `Kind` there. Lua's calls, the editor's types, `wiki` and `describe` all come from this declaration, and the command line and the fake game of `eu4-harmony test` take it with nothing more.
2. **Refusals** (`checks/src/<group>.rs`, a new one with its `pub mod` line in `checks/src/lib.rs`): each refusal the framework makes itself, its status and words, with a unit test; the game's own reasons are passed through as they are, one a line.
3. **The capability layer** (`core/src/game/<group>.rs`): one function per capability, taking first the session it reads, `game::Session`, and returning the framework's own types. The catalogue opens the session for each request (`Session::open`), which decides in one place whether there is one to read (`not_in_game`, `not_ready` during the daily update, `WrongContext` off the main thread), and the capability reaches the game through it alone: `Session { m, ctx, .. }: Session` gives it the memory and the session at this instant. A `world` capability takes `game::WorldSession` instead, opened as the session is but with the world alone (`World`), also when the player has no country to play. A capability that runs without a session, such as the main menu's or the screenshot, or that checks something of its own before, takes the `Caller` instead, and opens the session itself with `Session::open(caller)` after its check. A read takes the caller's view (the session's `view`) and leaves out what the player's view does not show. Its arguments after the session are named as its request's fields, as the catalogue's binding names them: where it takes two of one type, a test reads its parameters' names from its source and fails when they are not the binding's (`catalogue::tests::arguments_of_the_same_type_reach_each_capability_by_their_names`), so that the two cannot be passed the other way round. An action checks as the panel does, with the game's reasons, writes its command with a small writer of its own (a pure function, unit-tested) and posts it with `commands::post`. Its addresses are dependency points in the file's `points()`, added to `crate::points()`; a field offset is checked against an instruction that uses it (`.uses`). Each game address is named in one file only, which a test checks: a field of the game's objects is read from `core/src/objects/`, and a function another part already calls from where it is named there (a power spending from `game::power::Spending`, a country's modifiers from `game::modifiers`, the game's heap from `game_heap`).
4. **The catalogue's group** (`core/src/catalogue/<group>.rs`), which remote control's engine and the Lua host both run: one `layer!` that binds each capability once, as one line. `GrantPrivilege => fn grant_privilege(estate: String, privilege: String) -> () = session crate::game::estates::grant_privilege;` declares the slice's method, calls the layer's function with the session `Live` opens for the request, and answers the request whose fields are its arguments; `= caller …` calls one that takes the `Caller`. A request that passes the layer something of its own is `Upgrade { province } => game.change_center_of_trade(province, true);`; one whose answer takes more than a call is `Get { country } => get(game, country);`, with the group's function beside it. IDs such as `ProvinceId` become the layer's numbers, and the layer's types become the answer's, through `Convert` (`core/src/catalogue/mod.rs`): a group whose answer reshapes a layer type adds its `Convert` impl. A new group is one line in the `groups!` list there. Remote control's engine and the Lua host reach the groups through one seam, `Catalogue` there; the engine's tests (`core/src/remote/tests.rs`) run every capability where its kind says, from its description, so a capability that only calls the layer needs no test of its own. A group that does more, such as waiting for an answer or reshaping what the layer gives, is tested in its file against `core/src/catalogue/fake.rs`, a fake layer whose capabilities fail unless the group scripts them there; every answer it gives is checked against its capability's shape (`catalogue::tests`). What the capability itself reads and checks is tested in the layer, through its interface, over a session built from the game's objects and image as a test lays them out (`core/src/game/buffers.rs`: `Object` for an object's fields, `Image` for the game's globals and functions at their RVAs, the functions the test's own), as `core/src/game/diplomacy/panel.rs`'s tests run `diplomacy.act`.
5. **Events** a part adds: its `Event`, its `Kind`, the kind's name in `Kind::name` and its line in `EVENTS` (`remote/src/events.rs`), with one of it in `every_event` (`remote/src/tests.rs`); its handler `on_<kind>` in `HANDLERS` (`remote/src/lua.rs`), its arguments named as the event's fields, or one `table` for the whole event; the `Event` made in `Frame::heard` (`core/src/game/mod.rs`), with whether the player's view shows it; and whether anyone listens (`game::events::listened(Kind::…)`), so that it is not worked out for nobody. Listening takes the kind, not its name, so a kind misspelled does not compile. Extensions' handlers are called with it, and remote control keeps it, with nothing more.

A new group is a line in `groups!` in `remote/src/lib.rs` and one in `groups!` in `core/src/catalogue/mod.rs`, and a new argument's kind lines in `Kind` and `arg_kind!` in `remote/src/lib.rs`; other sessions add to these lists as well, so when merging master, keep both sides' lines.

A part that brings a framework setting declares it once, as a row of `SETTINGS` in `core/src/settings.rs`: its key in the file, the settings window's page and widget it shows as with the keys of its words, and when it takes effect, with the `Listener` told of it, if any. Its field and default go into `Settings` there, and its words into each of `core/localisation/eu4harmony_l_*.yml`; the file, the settings window and what is applied at startup and on a save follow from the row, and the settings' tests run it with nothing more.

## Trying it in the game

- Claim the game, install and start it as [.claude/skills/game-test](../.claude/skills/game-test/SKILL.md) says, and drive it with `eu4-harmony game <group> <capability> …`; release it when done.
- Try each capability as the player would use it, and each of its refusals, comparing with what the game's panel shows; read back what changed. A capability only extensions have is tried from a test mod.
- Record the run in [prototype-log.md](prototype-log.md), one dated section, saying as plainly what was not tried.

## Before it is merged

- `cargo fmt --all`, the build, the tests and both clippies (AGENTS.md), and `cargo xtask offline-check` with the game installed.
- README.md and README.zh-CN.md, as AGENTS.md says of the front page: a line where players or mod authors notice the change, such as a feature or a setting; the full list of capabilities is `eu4-harmony wiki`'s.
- The plan's part says what it added.
