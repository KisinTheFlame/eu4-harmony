# Adding a capability

How a capability reaches both extensions and remote clients, layer by layer, and what is done before it is merged. Terms are in [GLOSSARY.md](../GLOSSARY.md); the rules that shape a capability are in [ADR one-capability-catalogue](adr/2026-11-03-one-capability-catalogue.md), [ADR one-command-layer-in-written-form](adr/2026-11-03-one-command-layer-in-written-form.md) and, for the panels' actions, [player-actions.md](player-actions.md).

## Before writing code

- **Find it in the game first.** What the panel's button checks, the reasons its tooltip gives, the command it posts and that command's written form, the fields the panel reads. The command log of a developer build ([dev-tools.md](dev-tools.md)) shows a button's command in its written form when the player presses it in the game; `cargo xtask disasm` finds the code. Write what was found into `docs/research/`, addresses as RVAs into the 1.37.5 baseline, before or with the code.
- **Name it after what the player sees and does**, in the group of the panel it is on: `estate.grant_privilege`, not after the command (`grant_privilege`) or a field. What the player chooses among is named by its content key.

## The layers

1. **The catalogue** (`remote/src/<group>.rs`): the capability in its group's `group!` list, with its arguments, result and descriptions; a new group also goes into `groups!` in `remote/src/lib.rs`. The same declaration makes the capability's arguments a struct of the group's `args` module (`eu4_harmony_remote::estates::args::GrantPrivilege`), which the capability layer takes, each argument by its name, and says where it runs as a type of `eu4_harmony_remote::place`. `game`, `world` or `anywhere` for one extensions and remote control both have, `remote_game`, `remote_world` or `remote_anywhere` for one only remote control has; the `game` kinds run only while a game is going on with a country the player plays, the `world` kinds while a game is going on, also while the player only observes it (the time group), the `anywhere` kinds at the main menu too. A result is a struct deriving `Shaped`, with each field described; the shared `Choice`, `Amount` and `Acceptance` are in `remote/src/choices.rs`. An argument of a new kind is one line of `kinds!` in `remote/src/lib.rs`: its name, an example, the types that are arguments of it, its shape and its text form; the editor's type and how Lua passes it (`arg_json`, `lua/src/sandbox.rs`) follow from the shape, the argument type's own where it has one. Lua's calls, the editor's types, `wiki` and `describe` all come from this declaration, and the command line and the fake game of `eu4-harmony test` take it with nothing more.
2. **Refusals**: each refusal the framework words itself, its status and words, lives with its capability in the core, in the group's file's `checks` module (`core/src/game/<group>.rs`; one several groups share, in the file they share, as the envoys' in `game::envoys`), returning a `game::Fail`; one that a fake standing in for the core outside it must make too, such as an army or a province that is not there, goes into the checks crate instead (`checks/src/<group>.rs`, with its `pub mod` line in `checks/src/lib.rs`), so that the fake refuses in the core's words (ADR refusals-live-with-their-capabilities). Where the panel's check says no, the refusal is `game::action`'s, with the game's own reasons passed through as they are, one a line. A refusal with logic of its own, such as a position off the map, gets a unit test.
3. **The capability layer** (`core/src/game/<group>.rs`): one function per capability, taking first the session it reads, `game::Session`, and returning the framework's own types. The catalogue opens the session for each request (`Session::open`), which decides in one place whether there is one to read (`not_in_game`, `not_ready` during the daily update, `WrongContext` off the main thread), and the capability reaches the game through it alone: `Session { m, ctx, .. }: Session` gives it the memory and the session at this instant. A `world` capability takes `game::WorldSession` instead, opened as the session is but with the world alone (`World`), also when the player has no country to play. What it takes first follows from where its group's declaration says it runs: a `game` capability takes the `Session`, a `world` one the `WorldSession`, an `anywhere` one, such as the main menu's or the screenshot, the `Caller`; a capability that checks something of its own before takes the `Caller` instead, its binding says so, and it opens the session itself with `Session::open(caller)` after its check. A read takes the caller's view (the session's `view`) and leaves out what the player's view does not show. After what it takes first, a capability with arguments takes its `args` struct, destructured by the arguments' names (`args::GrantPrivilege { estate, privilege }: args::GrantPrivilege`), so that two arguments of one type cannot reach it the other way round; a province or an army is its number inside its ID (`province: ProvinceId(province)`). One without arguments takes nothing more. An action checks as the panel does and is carried out through `game::action`: refused with the game's reasons when the panel's check says no (`action::carry_out` for a `Choice`, `action::allowed`, `action::not_allowed`), and otherwise its command, written by a small writer of its own (a pure function, unit-tested), posted through the session's commands (`Session { commands, .. }`, `action::post`), never the command layer directly. The action is named by what the player does, "raise stability", and every action refuses in the same words through it. A test of the action over a session built from the game's objects (`buffers::session`; `Object::list`, `Object::map` and `Object::vector` lay out the game's containers) sees what it posted (`commands::record`) and each refusal the framework words, as the tests of `core/src/game/loans.rs`, `estates.rs`, `policies.rs` and `ideas.rs` do. Its addresses are dependency points in the file's `points()`, which `game::points()` collects for `points::this_build`, every point of the build (a test fails when a module's points are collected nowhere); a field offset is checked against an instruction that uses it (`.uses`). A function of the game's it calls is a `points::GameFunction` of the number of arguments it takes, `const CAN_GRANT: GameFunction<4> = GameFunction::at(0x…);`, kept by a point (`Point::keep(CAN_GRANT, …)`) and called through it, `CAN_GRANT.call(m, [entry, tag, privilege, reasons])`, so that a call of another count does not compile; only a method or a pointer the game keeps is called at its address (`m.call`). The game's lists, `std::vector`s, `std::map`s, its own arrays and every country are read through `crate::containers`, which bounds them, refuses a loop and leaves out a node the game removed; a string the game keeps is read as a content key (`game_string::key`) or as the player sees it in the interface (`game_string::shown`), the form the capability's result says. Each game address is named in one file only, which a test checks: a field of the game's objects is read from `core/src/objects/`, and a function another part already calls from where it is named there (a power spending from `game::power::Spending`, a country's modifiers from `game::modifiers`, the game's heap from `game_heap`).
4. **The catalogue's group** (`core/src/catalogue/<group>.rs`), which remote control's engine and the Lua host both run: one `layer!` that binds each capability once, as one line, with the group's `args` imported. `GrantPrivilege => fn grant_privilege -> () = crate::game::estates::grant_privilege;` declares the slice's method, calls the layer's function with what `Live` opens for the request's place (`catalogue::Opens`) and the request's arguments, and answers the request; `= caller …` calls one that takes the `Caller`. A method of the slice the group's own functions call, not a request's, is a line of its own, `fn method(argument: Type) -> Result = session capability;`, which says what it takes first itself. A request that passes the layer something of its own is `Upgrade { province } => game.change_center_of_trade(province, true);`; one whose answer takes more than a call is `Get { country } => get(game, country);`, with the group's function beside it. IDs such as `ProvinceId` become the layer's numbers, and the layer's types become the answer's, through `Convert` (`core/src/catalogue/mod.rs`): a group whose answer reshapes a layer type adds its `Convert` impl. A new group is one line in the `groups!` list there, which declares its module too. Remote control's engine and the Lua host reach the groups through one seam, `Catalogue` there; the engine's tests (`core/src/remote/tests.rs`) run every capability where its kind says, from its description, so a capability that only calls the layer needs no test of its own. A group that does more, such as waiting for an answer or reshaping what the layer gives, is tested in its file against `core/src/catalogue/fake.rs`, a fake layer whose capabilities fail unless the group scripts them there; every answer it gives is checked against its capability's shape (`catalogue::tests`). What the capability itself reads and checks is tested in the layer, through its interface, over a session built from the game's objects and image as a test lays them out (`core/src/game/buffers.rs`: `Object` for an object's fields, `Image` for the game's globals and functions at their RVAs, the functions the test's own), as `core/src/game/diplomacy/panel.rs`'s tests run `diplomacy.act`.
5. **Events** a part adds: one entry in the `events!` list (`remote/src/events.rs`): its variant and its name, what it is and what each of its fields is in doc comments, and what its handler `on_<name>` is called with, `fields` (one argument each) or `table` (the whole event), with a note for extensions alone where they are told more. Its `Kind`, its JSON, the countries a read's `countries` finds in it (those its fields of countries hold), its handler, and what `eu4-harmony types` and `wiki` say of both follow from that entry; a field of a type no event had before says in `Names` there whether it names countries. One of it goes in `every_event` (`remote/src/tests.rs`), and its handler's call in `every_event_calls_its_handler`. Then the `Event` made in `Frame::heard` (`core/src/game/frame.rs`), with whether the player's view shows it; one that the frames decide from what they read, as the day, its month and the country in view are, is decided in `Recall::next` there and tested through it, fed what a frame read (`Observed`); and whether anyone listens (`game::events::listened(Kind::…)`), so that it is not worked out for nobody. Listening takes the kind, not its name, so a kind misspelled does not compile. Extensions' handlers are called with it, and remote control keeps it, with nothing more.

A new group is a line in `groups!` in `remote/src/lib.rs` and one in `groups!` in `core/src/catalogue/mod.rs`, each declaring its module; an empty `impl <group>::Layer for Fake {}` in `core/src/catalogue/fake.rs` while the fake scripts none of its capabilities; and its capability layer's `pub mod` and `points()` line in `core/src/game/mod.rs`. A new argument's kind is a line in `kinds!` in `remote/src/lib.rs`. Other sessions add to these lists as well, so when merging master, keep both sides' lines.

A part that brings a framework setting declares it once, as a row of `SETTINGS` in `core/src/settings.rs`: its key in the file, the settings window's page and widget it shows as with the keys of its words, and when it takes effect, with the `Listener` told of it, if any. Its field and default go into `Settings` there, and its words into each of `core/localisation/eu4harmony_l_*.yml`; the file, the settings window and what is applied at startup and on a save follow from the row, and the settings' tests run it with nothing more.

## Trying it in the game

- Claim a test game and start it with your build as [.claude/skills/game-test](../.claude/skills/game-test/SKILL.md) says, and drive it with `eu4-harmony game --test-game <owner> <group> <capability> …`; release it when done.
- Try each capability as the player would use it, and each of its refusals, comparing with what the game's panel shows; read back what changed. A capability only extensions have is tried from a test mod.
- Record the run in a file of its own in [prototype-log/](prototype-log/), named by its day, saying as plainly what was not tried.

## Before it is merged

- `cargo fmt --all`, the build, the tests and both clippies (AGENTS.md), and `cargo xtask offline-check` with the game installed.
- README.md and README.zh-CN.md, as AGENTS.md says of the front page: a line where players or mod authors notice the change, such as a feature or a setting; the full list of capabilities is `eu4-harmony wiki`'s.
- The plan's part says what it added.
