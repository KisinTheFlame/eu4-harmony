# 2026-11-02 Returning with the history, and what the game leaves (tested by me)

After the run above: the world reset at the return now reads the history, and the main menu is made after it (ADR return-to-the-main-menu-in-process); the framework puts back after every world reset what it leaves, and lets go at the map manager's destructor what that leaves; the single player setup's back button returns in process. Built with `trace`, installed between runs, ten processes in all; backups as AGENTS.md says, the framework files copied aside first. Driven by `eu4-harmony game` and `tools/game-input.ps1`; the GUI root's elements counted from outside the process.

- **Against a new process**: France started after a return from Austria's game of 1724 (`Austria-37_4-1`, ironman): its first save differed from two new starts' only where those differ between themselves; `hre_religion_status=0`, no `achievement` list, the gameplay options as in `gameplaysettings.txt`. Before the fix of the religions it was still 2: the Empire's religions were the 1724 game's (research/main-menu.md). `英格兰1444_11_11` loaded from the main menu after a return and in a new process gave the same first save, of the same size, but for `multiplayer_random_seed` and `campaign_id`.
- **Times**: a return 4.9 to 8.2 s, ironman ones with their exit save (with the census on, which slows the game); the world reset with the history 2.8 to 5.9 s of it; a new game from the returned main menu 4.2 to 8.5 s.
- **The single player setup's back button**: back to the main menu in the same process after 5.4 s (its reset with the history), the continue box offering the last save.
- **Odd moments**: with the court window and an event open, while observing (`observe`), and 0.55 s after the console's `autosave`: each returned, the main menu as after a start; the autosave was complete. From the end-of-game summary of a save dated 1821.1.1 run past the end date, by its "退出": returned in process.
- **The game's own way back crashed**: Esc, "返回主菜单", "确定" shows the end-of-game summary; its "退出" returned, and then the game crashed in the main menu (once of three; `0xc0000005` at `0x15ae44c`, the summary's quit button calling its delegate in the freed map manager). The previous run had only used `menu.return`, which skips the summary. Letting the session's interface go before the idler switch crashed at the switch; at the destructor's start, letting the summary go corrupted the heap (`0xc0000374`) after a return from it, since the world reset had let it go as a popup; letting the two plain structs go crashed later. As built: three returns by the summary in a row, the mouse moved over where its button was and over the main menu's buttons, no crash; then two `menu.return`, a return by the summary, in-game loads of an ironman and a plain save, an ironman return, the setup's back button and a new game, in one process, no crash.
- **A failing ironman exit save**: with `Castilla-5.eu4` held open by another process, `menu.return` answered `rejected` after 0.7 s ("the ironman exit save faulted": the game's save raised a C++ exception, `0xe06d7363`, out of `0x5cc160`), the session stayed, and the notice showed ("铁人存档没有保存成功……"). Once the file was free, the return wrote it and went on; the `.tmp` the failure left was deleted by the game's next save.
- **The setting off**: `menu.return` answered `ending` at once and a new process came up, as in vanilla.
- **What stays**: the GUI root had 3,095 elements in a new process's main menu, and about 1,030 more after each return (1,600 before the framework let the session's interface go). The census put 8 to 10 MB of the game's heap blocks left by each return, and 4.3 MB by each of the game's own in-game loads, the same forty sites every time (research/main-menu.md); the framework's heap stayed flat.
- **Poland**: a new game's max manpower for Poland came out 26,305 or 26,430 in new processes as after returns.
- **Not seen in the running game**: the 20 rounds with this build; an extension's `on_session_ended`; cloud saves.
