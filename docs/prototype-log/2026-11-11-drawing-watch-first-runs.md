# 2026-11-11 The drawing thread's write watch, first runs (tested by me)

The write watch's drawing mode ([dev-tools.md](../dev-tools.md), "Write watch"): what the drawing thread reads, then who writes it while the main thread runs days. To check that it finds a race, the race of [2026-11-11-passes-at-the-preparation.md](2026-11-11-passes-at-the-preparation.md) was let back in for these runs (the drawing thread's off-screen passes given the idler's own bytes), and closed again after. Hidden test games from this branch's core with `dev-test-games` and `dev-write-watch`, the 1780.7.1 save in observe mode, at speed 5 (`time.advance 8`); `dev.toml`: `drawing = true`, `after-days = 3`, `drawing-frames = 2`, `drawing-days = 2`, `let-run = ["nvd3dumx.dll"]` (the computer's graphics driver), `give-up-after = 90`. Another session's scenarios ran in a test game of their own beside the last run.

- **Every page stopped at every read**: the first frame had not ended after eleven minutes, the main thread held, the drawing thread busy in the exception handler; stopped. A page now goes on unwatched after 32 stops.
- **The pages limited; reads kept by their block**: both frames given up after 90 s, the drawing thread waiting for the presentation lock after Present (`Lock::take` from the Present observer): it gives the lock up for Present, and the main thread, held while waiting its turn, took it and kept it. Before Present, the first frame read 9,831 blocks of 111 sizes and 130 places of `eu4.exe`'s data. The days after, 120 MB of pages read-only for two days: 188,609 writes by the main thread without the lock to blocks the drawing read, in 29,600 groups, among them the day's provinces' phase writing the provinces' array (`0x9f5eb9`, a block of 58 MB, `+0x33b8`), which the let-in race reads; 1.9 million by other threads, in 247 groups. Too broad to read: a block the drawing reads may be the array of every province. The drawing thread now keeps the lock through a watched frame's Present, and the reads are kept by their eight bytes.
- **By their eight bytes**: both frames ended, 191,463 and 2,782 reads and writes, some 51,000 eight bytes read. The days after, 31 MB of pages read-only: the main thread and the drawing thread then both stopped inside the graphics driver (the main thread in `d3d9.dll` from the back end's texture bind `0x16d8651`, the drawing thread in Present), and the watch was given up after 90 s with 2.3 million writes recorded; the game did not go on and was stopped. _Inferred_: a write of the driver's or the kernel's into a page made read-only for the game's data beside it, which fails in the kernel instead of stopping. Until then: 182 writes by the main thread without the lock to what the drawing read, in 48 groups (the check for a frame inside a day, `0x769f24` and `0x76a1b0`, writing the world's `+0x1e10`, which the map's drawing reads; `0x75c5d7` writing an object of 0x1b70 bytes at `+0x1b00`–`+0x1b40`); 175,796 by other threads, in 310 groups, most the engine's job threads (`0x17a270`, `0x16bbe5f`) writing their queues; 107,227 by the main thread with the lock; 157 by the drawing thread.
- **So**: the watch's first part works and keeps a frame's reads; its second part finds writes to them, but making pages read-only while the driver runs can stop the game. The let-in race's list (`0x9f7a12`) was not among the writes found: the watched frames asked for no rebuild, so did not read the list.
- **Not verified**: which of the writes found are races that matter; the second part over more than a day without stopping.
- **Cleanup**: every test game stopped, their logs in their claims' folders; the race closed again in the code.
