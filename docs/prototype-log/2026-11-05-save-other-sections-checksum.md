# 2026-11-05 A save's other sections beside the pool, the save checksum's sum on threads, the update thread woken (tested by me)

This branch's developer builds (docs/game-speed.md, S8), installed with `cargo xtask install` within two claims (`cargo xtask game`, the game started hidden), the player's playset. Other sessions' builds held the machine's processor at 100% throughout, so the times are of a loaded machine.

- **`compare-saves`**, with the pool writing the loops while the main thread wrote the rest of the game state and the game's own loops as well: Austria-37_4-1 (1724, ironman, binary) at its load, the provinces the same, 22,876,653 bytes, and the countries the same, 24,396,272.
- **The bytes, end to end**: the same save loaded from the same file twice, its load's save written once by the game's code (`game-writes-saves`) and once by the framework's; Python's `zipfile` read both. `ai` was the same; `gamestate` (55,051,381 bytes each) differed in 4 bytes only, at 510, the value of the token `0x2dc6` that is different in every save the game writes (the save loaded, the game's and the framework's each held another); `meta` differed in a UUID that changes from save to save. The save checksums of the two game states were the same: the memory stream's sum, which each `b` past 0xffff makes 1, had forgotten the 4 bytes well before the end.
- **The parts traced** (`dev-call-trace`, the game's code): after `0x5ce5f0` the main thread waited 40 to 96 ms in the join of the game's "SaveSessionUpdateThread", whose update and `Sleep(50)` took 60 to 170 ms a call while a save was loaded; the local save's size check, `.tmp` check, backup and move took 3 ms together. What had been taken for the file's checks and move was that wait (research/saves.md, "The update thread").
- **The stop**, four ironman saves of Austria in a row each way: the framework's code 284, 300, 301 and 302 ms; the game's (`game-writes-saves`) 1149, 1195, 1219, 1312 and 1211 ms. With the framework's, the save checksum of the game state took 11 to 29 ms (60 to 65 with the game's), the wait for the update thread 0 to 2 ms, and the main thread waited 40 to 80 ms for the pool where the world has written its game state.
- **Saves the framework wrote were read**: the later loads read files the framework had written (each load's own save, and the leaving one), and the game played them.
- **A save of the player's** (the save window, "compress" ticked, a plain game of 1444 as England, `eu4harmony_s8_test`): written with the pool and the stored copy, the stop 149 ms, compressed in the background from 34 MB to 2.7 MB; `menu.load` played it.
- **A cloud save** (the save window's 云 tab, the game started with `SteamAppId` and `SteamGameId` 236850 in its environment through `cargo xtask game start`): over the test save of 2026-11-04, `eu4harmony_cloud_test`. The pool wrote its provinces and countries ("wrote 4942 provinces and 1380 countries ... beside the game's writing"); the game deflated and wrote the file itself, as cloud saves keep its path: three entries deflated, `zipfile` found it whole, `gamestate` beginning `EU4bin`. The game kept the file it overwrote as `eu4harmony_cloud_test_cloudbackup`. The load window's 云 tab loaded it (session 5, England, 1444.11.11).
- **The background thread's move refused**: twice the thread's move of its compressed file over the save was refused ("拒绝访问", os error 5), and the save stayed whole and uncompressed. Inferred, not verified: another program the player runs that reads each save it sees, EU4SaveMaster, held the file open. The thread now tries again, ten times 200 ms apart, unless the game is waiting for it; that was built after these runs and is not seen working against a held file.
- **Not verified**: a multiplayer game's save, a save in a random new world, a machine with one thread, and the stop on a machine not otherwise loaded.
- **Cleanup**: the game closed with `cargo xtask game stop`; releasing each claim put back every player file (the test save of the player's removed with them) and the game folder's framework files, and found each as the backup had it. The two cloud test files, `eu4harmony_cloud_test` and `eu4harmony_cloud_test_cloudbackup`, are still in the player's Steam cloud, for the player to delete. The repository's `dev.toml` is as it was.
