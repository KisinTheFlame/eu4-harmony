# 2026-11-02 Extension save data in the save (tested by me)

Extension save data now goes into the save itself (ADR extension-save-data-in-the-save). One run of `eu4.exe`, started directly and started again by `menu.return` between loads, Chinese playset with the unchanged regional-combat extension, at 3840x2160. This branch's build with the `trace` feature, tracing the game's checksum check `0x97500` and later the checksum `0x14e3390`, after the build, the tests, clippy and the offline checks against `eu4.exe` passed. Backups as AGENTS.md says, with the framework files installed in the game folder copied aside first. The game was driven by `eu4-harmony game`; test saves were made with a scratch script that writes the entry as the framework does and redoes the checksum with `I_am_such_a_cheater` (research/saves.md), after it matched the checksums of the player's saves salted so.

- **Startup**: 581 dependency points match; 103 hooks, 4 writes; the extension loaded. After the change below, 582 points.
- **No data, nothing written**: a new game as Castile (`menu.start CAS`) ran to the half-year autosave of 1445.1.1, a plain text save (`compress_autosave=no`), with no extension data: no line from `saves`, and no `eu4_harmony` in the file.
- **Two clicks went astray**: the start-of-game introduction was to be closed with two clicks from `tools/game-input.ps1`; it stayed open, and the foreground window was then the player's Chrome, so the clicks may have landed there. No further input was sent, and the regional-combat task was never turned on by its button; the data came from the test saves instead.
- **An entry after the checksum is never read**: a copy of that autosave with the entry appended after the checksum loaded with "data for 0 extension(s)". The text tokenizer logged "Quoted string doesn't close" once for each of the entry's five strings, and the game's check failed, the checksum's span having moved.
- **A defect, fixed in the run**: the entry put before the checksum, after the AI as the framework wrote it then (the world write's `after` observer), loaded with "data for 0 extension(s)" and no line in `error.log`. In a plain save the game reads top-level entries only up to the AI (research/saves.md). The entry is now written where the world has written its game state, before the AI (a jump at `0x751c87`).
- **Plain text**: the entry before the AI, with regional-combat's task for the army in Asturias (`850403524662`, center 207, radius 5) and 1,400 bytes for an extension that is not loaded (`rh-filler`), in five strings of up to 500 bytes. Loading it: "data for 2 extension(s)", "dropped the data of "rh-filler", which is not loaded", and the extension "restored 1 task(s)". The autosave of 1445.7.1 then wrote "the data of 1 extension(s), 1 string(s)": in the file, the entry between `idea_dates` and `ai`, in the layout ADR extension-save-data-in-the-save gives, and the file's checksum, with `I_am_such_a_cheater`, took it in. Loaded again: "data for 1 extension(s)", "restored 1 task(s)".
- **Zipped text** (`compress_autosave=yes` for the rest of the run): from that autosave to the one of 1446.1.1, `gamestate` held the entry last before the checksum, which took it in; `meta` and `ai` held none. The army had lost a battle on the way and the extension turned its task off ("task off: lost a battle"), and the save carried its new data, `enabled: false`. Loaded again: "data for 1 extension(s)" and "restored 0 task(s)", as that data says.
- **Ironman (binary)**: a copy of the ironman save `Castilla-5` (1470.3.13, salted with `I_am_such_a_cheater` as it was) with the entry in binary before the checksum, holding a task for the army in Constantinople (`28136330756150`, center 151, radius 8) and the same `rh-filler`. Loading it: "data for 2 extension(s)", `rh-filler` dropped, the save the game makes while loading an ironman game wrote the data, and "restored 1 task(s)". In the rewritten file the entry lay just before the checksum token, which took it in. Leaving for the main menu wrote it again; loaded again: "data for 1 extension(s)", the save while loading wrote it, "restored 1 task(s)".
- **The game's own check** returned 0 at every load. The trace of `0x14e3390` showed that the check salts with an 8-byte string, while every save loaded was salted with `I_am_such_a_cheater` (the test copies by the script, `Castilla-5` as it was) or, by its name, made by 1.37.4 (a copy of the player's untouched ironman save `Byzantium-37_4-1`); and once a check had failed, every save the game wrote was salted with `I_am_such_a_cheater` too, ironman ones included. That the playset's other four mods turned achievements off, as first supposed, is wrong: all four hold only graphics and localisation, and the run below found a new game's saves passing the check.
- **Not seen in the running game**: the regional-combat task turned on by its button; cloud saves; multiplayer, which is not supported; vanilla loading a save with the entry; data of 16 MiB.
- **Cleanup**: the game was closed by ending its process each time it had to start fresh, and at the end. `tools/player-state.ps1 -Restore` listed what the run changed (the autosaves, the three test saves and two `_Backup` files, the framework's logs, `continue_game.json`, `pdx_login_cache.txt`, `settings.txt`), put each back and found every file as the backup had it. No crash folder was made. The three framework files in the game folder were put back and compared equal to the copies; the regional-combat repository has no change. The backups, scripts, copies and screenshots of the run were deleted.
