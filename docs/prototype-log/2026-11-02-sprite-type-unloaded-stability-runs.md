# 2026-11-02 A sprite type unloaded while shown, and the stability runs (tested by me)

The build with the repair of a sprite type's unload (research/main-menu.md, "A return after time ran"), after the build, the tests, clippy and the offline checks against `eu4.exe` passed; from the fifth process on, with the fix to the load's check below. Six processes, `eu4.exe` started directly, the playset as installed (the Chinese one) and the regional-combat extension loaded, driven by `eu4-harmony game` and `tools/game-input.ps1`. Backups as AGENTS.md says, the framework files copied aside first. Saves: `法兰西1495_11_19`, `英格兰1444_11_11`, the test save of 1821.1.1 made from `法兰西1445_02_20`, and the ironman saves `Austria-37_4-1` and `Castilla-5`.

- **20 rounds**, each a load of `法兰西1495_11_19`, 30 days at speed 5, an in-game load of `英格兰1444_11_11`, 10 days, a return, a new game as France, 10 days and a return: every answer right, no crash, no lazy-load error in `error.log`. The build before this repair crashed at the fourth round's load. At each return the repair kept 32 sprite types loaded, each logged with how many shown sprites showed it: the 30 building icons (`GFX_barracks` and the like, which `macrobuildinterface.gui` shows), `GFX_government_boost_states` (`countryreformview.gui`) and `MessageSettingsButton`. Their counts only grew: the building icons by one at each in-game load, `GFX_government_boost_states` by one with each session, `MessageSettingsButton` by one or two with each in-game load. What shows them is left behind by every session, not at one moment of it.
- **Memory over the 20 rounds**, at the main menu after each return: handles 1,047 to 1,070, no growth. Private bytes 3,792 MB after startup, 4,086 MB after the first round, 4,779 MB after the twentieth: about 32 MB a round after the first, give or take 50 MB from one return to the next. Elements in the GUI root 3,095 after startup, then about 2,460 more each round: about 1,030 at the return after a new game, about 1,430 at the return after a load and an in-game load.
- **Odd moments**, in one process: a return with time running at speed 5; with three of the game's panels open (F1 to F3); with an event waiting for its answer; with the end-of-game summary open (the test save run past its end date); while observing; right after the console's `autosave`; a new game from a session, then its return; a return right after an in-game load; then five times a load and a return of each of two saves, with no time run. Every return answered `main_menu`, a save loaded after each was played, no crash, no lazy-load error. The ten returns with no time run added 10,231 GUI elements, about 1,020 each: what a return leaves does not depend on how long the session ran.
- **Ironman**, in two processes: a return from Austria's ironman game of 1724; Castile's ironman game run 10 days, `Castilla-5` loaded again in the game, an in-game load of a plain save and a return; a new game as France from Castile's ironman game and its return. No crash. In the first process, loading `Castilla-5` again was answered `rejected`, "it began a game of 1470.3.23 as CAS, where the save is of 1470.3.13 as CAS", though the game had loaded it: the ironman exit save of the session, written first, had rewritten that very save, and remote control compared the new session with the save's header as read when the load was asked. Fixed: the header is read again once the game comes. In the second process the same load answered 1470.4.12, CAS.
- **By the player's hand**, in one process, each from a fresh session: the in-game menu's 返回主菜单, its question's 确定, then the end-of-game summary's 退出, from France's game with an event waiting; the summary the game opened itself at its end date (the test save run two days), its 退出; the single player setup's 后退 from the main menu. Each came back to the main menu in the same process, with nothing of the session drawn on it, and a save loaded after was played.
- **The heap census**, a `trace` build with the census on, in one process: eight cycles of a load from the main menu (the two saves in turn), 30 days and a return; then a load, six in-game loads 10 days apart and a return. A load from the main menu made no world reset of its own, so each cycle was one generation. Of the C runtime's heap blocks made in each generation, still live after the later resets: 70 MB of the first (what the game keeps once it has been in a game); 8.2 to 9.3 MB, 46,000 to 47,600 blocks, of each later cycle; 5.2 to 6.6 MB of each in-game load. Of each, about 2.2 MB are 747 blocks of 0xbf8 bytes made at `0x153a61`, where `ai_king.cpp` starts new agents; then blocks of 0x178 bytes made at `0x931693` and `0x93dcc3`, 1,600 to 2,700 of each, 0.6 to 1 MB; and 1,585 blocks of 0x120 bytes made at `0x299db2`. They are the game's: the world reset does not let them go, at the game's own in-game load as at a return. Elements in the GUI root grew by 1,034 with each cycle, and by about 300 with each in-game load.
- **Not seen in the running game**: a return with "return without restarting" off, after this build; a failing ironman exit save; cloud saves; a multiplayer game. What makes a sprite type count was found by its name only: the windows that hold the sprites were not looked for.
- **Cleanup**: the game was closed by ending its process each time. `tools/player-state.ps1 -Restore` listed what the runs changed (the framework's logs, `continue_game.json`, `pdx_login_cache.txt`, `settings.txt`, the autosaves, `Austria-37_4-1.eu4` and `Castilla-5.eu4` with their backups, the test save added), put each back, removed the test save and the crash folder of the 20 rounds that crashed before this repair, and found every file as the backup had it. The three framework files in the game folder were put back and compared equal to the copies. The copies, logs and screenshots of the run were deleted; the scripts that drive the runs are kept in the session's scratch folder for the work on what a return leaves.
