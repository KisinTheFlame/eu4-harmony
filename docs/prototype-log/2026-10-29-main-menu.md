# 2026-10-29 The main menu (remote control C5, tested by me)

Every request went through `eu4-harmony game`, from scripts that also started a second client a moment after a load or start; `eu4.exe` was started directly. Chinese playset with the unchanged regional-combat extension, system fonts; backups as above. Three runs, each with the build of the time; none of them with the branch as it was merged later.

- **First run**, with the capabilities as first built (the commit `Load a save, start a game and return to the main menu from remote control`): `menu` said `starting` for the first answers after startup, then `main_menu`; `session` `not_in_game: the main menu is open`; `menu.saves` listed the 139 saves. `menu.load` Castilla-5 was answered `rejected: the game could not load the save`: the build checked, right after asking the single player setup to load it, that a load had happened, but the setup loads by a command at a later frame, 1.7 s later, and by then the main menu had been sent back to its first page. `menu.start` ZZZ (Zazzau) then reached the game, which crashed at its first frame (`eu4+0x7395e8`: a command the setup's animation queues, run once the setup was gone; research/main-menu.md). The hung process was ended.
- **Second run**, with that code on C9's merge and the load changed to two halves (load, then select and start once the save was loaded), a change never committed, since the third run's way replaced it: `menu.load` Castilla-5 answered after 12.4 s with session 2, `CAS`, but 1444.11.11 and Castile's starting army: a new game, not the save. A second client's `session`, sent 0.3 s after the load request, waited and was answered at the same first game frame. `menu.load` in the game: `unavailable: only in the main menu`. `menu.return`: `{"place": "ending", "process": …}` at once; `session` right after it `not_ready: the game is returning to the main menu …`, and so was every `menu` for 2.2 s, until the pipe broke (exit code 3); the new process answered `menu` 45 s later with a larger `process`. `events --since 5 --process <old>` there: no events, `missed` true. At the new main menu `menu.start QQQ` `not_found: no country QQQ`, `menu.return` `not_in_game: the main menu is open`, and `menu.start FRA`, the setup shown without animation, answered after 9.4 s with session 1, 1444.11.11, `FRA`; the second client's `session` again waited for the game's first frame. Returning again worked as before.
- **Third run**, with the branch on C9's merge as it was up to this record (`Load a save as the continue box does, and start without the setup's animation`: the load as the continue box does it, at one frame, with the player from the save's header). That code was rebased onto the merges of C10 and C3, then of C4 and C2; those builds passed the build, the tests and the offline checks and were never started in the game, and the review changed the code after them ("The main menu after review" below): `menu.saves` took 11.1 ms for 139 saves and gave each its player and date (Castilla-5 `CAS` 1470.3.13, the autosaves `ETH` 1445.1.1). `menu.load` Castilla-5 (ironman) answered after 7.1 s: session 2, 1470.3.13, `CAS`; the second client's `session` waited and read the same. `menu.return`, then at the new main menu `menu.load` 法兰西1445_02_20 (a compressed text save) answered after 5.9 s: 1445.2.20, `FRA`, with France's army in 183. `menu.return`; at the new process's first answer `menu.start QQQ` was `unavailable: only in the main menu` (the main menu's first frame came 2.3 s later), then `menu.start FRA` answered after 8.4 s with session 1, 1444.11.11, `FRA`, the second client's `session` the same. `menu.return` once more; the new main menu answered `menu` `starting`, then `main_menu`. The core logs of the four processes have no error, and no crash folder was made.
- **Costs**: requests answered at once took at most 11.1 ms (the first `menu.saves`, which reads every save's header), the rest under 1 ms.
- **Not seen in the running game**: a request queued in one session and refused `session_changed` in the next (unit test; no load was started in a game); a request waiting (such as `events` with `wait_ms`) when the game returned, answered `not_ready` (unit test); a load the game refuses, or a save it cannot load, which would be answered by the 5 s check or not at all if the game started anyway; `rejected` because the setup did not take a start; a start as a country that does not exist at the start date; a save named with characters Windows-1252 has (only ASCII and Chinese names were loaded); `menu.return` with the in-game menu or the end-of-game summary open, or while time runs.
- **Cleanup**, after each run: the loads rewrote `Castilla-5.eu4` and its backup, and `settings.txt` changed; they were put back from the backups and, with both save folders and the other settings files, compared equal to them. The first run's crash folder was deleted. The framework was uninstalled, which put back the earlier `version.dll`; the backups were deleted.
