# 2026-10-29 Recruiting (remote control C6, tested by me)

Two runs. The first, of two starts, used `eu4-harmony game recruit` and the core built from this branch before it was rebased onto C4, with the `trace` feature (`EU4HARMONY_TRACE` set to the recruit command's check `0x26e080` and its execute `0x26cfe0`, 60 calls each) and two log lines of the run's own around the post to the session: they read the session's kind, `+0x54`, `+0x55` and `+0x80d` and the player mode, and the build set `+0x80d` around the post, as the map manager's frame does (removed afterwards, see below). For the extension side, a probe of the run's own: a mod made with `eu4-harmony new` in a scratch folder whose `on_session` recruits through `Game::recruit` and logs each answer, linked and added to `dlc_load.json` for the run only. `eu4.exe` was started directly; Chinese playset with the unchanged regional-combat extension, system fonts; backups as above, `dlc_load.json` too. What the game showed was seen with `eu4-harmony game screenshot` and `tools/screenshot.ps1`.

- **Startup**: 409 dependency points match; 104 hooks (two of them the trace's), 4 writes; both extensions loaded.
- **Main menu**: `recruit 219 infantry` answered `not_in_game: the main menu is open`, exit code 1.
- **Castile, 1470.3.13** (the continue box's ironman save), never unpaused at first. The probe's orders at the session's first frame: a galley in Seville (224) `Ok(())`; infantry in Toledo (219) `Rejected` "没有足够的manpower。"; artillery in Toledo `Rejected` "the player has no unit type of the kind artillery"; cavalry in Constantinople (151) `Rejected` "卡斯蒂利亚不是君士坦丁堡的控制者。\n没有足够的manpower。", one reason a line; `UnitKind::Unknown` `InvalidArgument` from the SDK; province 0 `NotFound`. From the command line the same refusals, exit code 1; 0 and 99999 `not_found`; `recruit 224 transport` printed `null`, exit code 0. Seville's province window then counted 0 regiments and 2 ships in its queue: the probe's galley and the cog.
- **Manpower**: Castile had none, and two years at speed 5 (to 1472.6.5) gave none, its armies at war taking every man back as they reinforced; the game console, opened with its key, refused `manpower 20000` "Command not available in multiplayer or ironman mode." So the game was ended, the France save of 1444.11.11 was made the newest save (its modification time) so that the continue box offered it, and the game was started again.
- **France, 1444.11.11**: `province.get 183` (Paris) allowed infantry and cavalry. Paused, `recruit 183 infantry` printed `null`; the outliner's list of units being recruited showed "50d 巴黎", its tooltip "我们正在巴黎招募拉丁中世纪步兵。". `recruit 183 cavalry`, still paused: the top bar went from 585 ducats and 10,798 men to 560 and 9,798. Running, on 1444.11.16, `recruit 183 infantry` printed `null`; paused again on 11.25, the outliner showed "36d (+2)" in Paris. Refused: `183 heavy_ship` "没有足够的sailors。"; `183 transport` "the game does not let the player recruit it there, and gives no reason" (Paris is inland); `219 infantry` "法兰西不是托雷多的控制者。"; `183 artillery` no unit type. The probe's orders, for Castile's provinces, were refused as not France's.
- **The game carrying it out**: for every order the trace had the framework's call of the check, and at the next frame, 2 to 9 ms later, the session's own check of a copy of the command (from `0x14cab33`) and its execute (from `0x14d4e62`), both answering 1, paused and running alike.
- **The session**: at every order, in both saves, of kind 2, `+0x54` 0, `+0x55` 1, `+0x80d` already 1, player mode 0, and the post took the command. Setting `+0x80d` around the post so changed nothing; it was taken out of the code, with its two dependency points, before the second run.
- **Costs**: each `recruit` took 0.1 to 0.2 ms in the engine; the probe's six orders in `on_session` 15 to 19 ms. The core logs have no error, and no extension was stopped.

The second run used the final build of this branch, rebased onto C4, where `recruit` comes after `console_run` in `GameApi`, without the trace or the run's own log lines, and the probe rebuilt with its SDK, now ordering for France: infantry and a transport in Paris, infantry in Toledo, `UnitKind::Unknown`, province 0. The France save was made the newest again.

- **Startup**: 408 dependency points match; 102 hooks, 4 writes; both extensions loaded. `recruit 183 infantry` in the main menu: `not_in_game`.
- **The extension**: infantry in Paris `Ok(())`; the transport "the game does not let the player recruit it there, and gives no reason"; Toledo "法兰西不是托雷多的控制者。"; `Unknown` `InvalidArgument`; 0 `NotFound` (18 ms for the five).
- **The command line**: paused, after the probe's regiment, the top bar read 585 ducats and 10,798 men, as after the first run's first regiment; `recruit 183 cavalry` printed `null`, and the top bar read 560 and 9,798; the outliner showed "50d (+1)" in Paris. `recruit 183 heavy_ship` "没有足够的sailors。".
- **Not seen in the running game**: the command's own rule for ships refusing an order the recruit check allows ("the game's recruit command refuses it, and gives no reason"; the restriction `0x40d2b0` was not met); a session that is not a client (a multiplayer host), which would take the order only within the map manager's frame and otherwise be answered "the game takes no orders from the player now"; a refusal for money or a siege; the player mode 7; an order the game's own check refuses at the next frame, the state having changed in between; special regiments and mercenaries, which `recruit` does not offer.
- **Cleanup**: the ironman save `Castilla-5.eu4` and its backup were rewritten while the game ran, the France save changed (its modification time by hand), and so did `settings.txt`. Those were put back from the backups, and both save folders, the three settings files, `continue_game.json` and `dlc_load.json` compared equal to them after each run. The game was ended from outside (its process stopped) each time; no crash folder was made. The link file `mod\eu4-harmony-recruit-probe.mod` and the probe's logs were deleted. The framework was uninstalled, which put back the earlier `version.dll`; the backups, the probe mod, the screenshots and the copies of the logs were deleted.
- **Changed after the run, not run in the game**: the second run's build was this branch rebased onto C4's merge, at the commit that was then 676e229 ("Write down in the plan what recruiting gives"; its code was that of "Post the recruit command as the button does, without the frame flag", two commits before, since the two only wrote documents). Since then the branch was rebased onto the merge of C2, which put `recruit` behind the country snapshot's field in `GameApi` (the SDK's tests check its place against a table built as the core builds its own), and, after review: the recruit command's class, size and methods are named in `objects::campaign`, and the allocator is `unicode::fill`'s, with the same numbers and bytes and one dependency point fewer (the allocator was kept twice); the session is found before the command is allocated, where the run's build found it after the command's check, so that a session that cannot be read leaves no command behind; `FakeGame` answers a recruit order as the core does; and the docs of `recruit` say that the game checks an order again at its next frame and name the ship rule a province's snapshot leaves out. On the path that ran, the game sees the same calls, but the map manager's method `0x811aa0` now comes before the allocation, and is called for an order the command's check refuses too. That build, with 421 dependency points, passed the build, the tests and the offline checks against `eu4.exe`, and was never started in the game.
- **Rebased onto C1, not run in the game**: the branch was then rebased onto the merge of C1, which put `recruit` behind time control's four fields (`time_speed`, `time_set_speed`, `time_pause` and `time_resume`) in `GameApi`, where it had come right after `country`; that build, with 430 dependency points (C1's included), passed the build, the tests and the offline checks against `eu4.exe`, and was never started in the game.
