# 2026-11-05 A save's countries and provinces on threads, and the zip's copy (tested by me)

This branch's builds (docs/plans/game-speed.md, S8), installed with `cargo xtask install` within one claim (`cargo xtask game`, the game started hidden), the player's playset; the saves loaded with `menu.load`. An ironman game saves as it is loaded and as it is left, which made the saves watched here; the player's settings made no autosave in 50 days of 1724, and a plain autosave on the first of January.

- **The first start**: the first save ended the game with the framework's fatal error, "the framework used 0x1d92200, which no dependency point checks": the memory stream's class was told by its vtable's address, which no point checks. It is now told by the vtable's write, which one does, and a unit test checks every address the module takes.
- **`compare-saves`** (a developer build with the test switches): the threads' bytes and the game's loop's, compared in the log, the same each time: Austria-37_4-1 (1724, binary) at its load and when it was left, the provinces 22,876,653 bytes and the countries 24,396,272; Hungary-37_4-1 (1548, Georgia) twice, 14,281,018 and 33,745,776; Ottoman-37_4-2 (1496) twice, 9,482,489 and 32,959,578 (32,959,479 the second time, the game having gone on); 英格兰1444_11_11 (England, not ironman) at its autosave of 1445.1.1, a plain `EU4txt` file, 8,685,607 and 24,282,124.
- **The stop**, by the framework's new log line from the start of the local save to its end, the same Austria save loaded three times (five saves each, the load and the leaving ones): with `game-writes-saves` (the game's own loops and deflate) 986, 1233, 1256, 1362 and 1116 ms; with the framework's 431, 438, 437, 447 and 308 ms. The provinces took 35 to 63 ms and the countries 46 to 76 ms on eight threads. The parts of one save of 310 ms, from a call trace, are in research/saves.md, "Where a save's zip goes". A sampler at 500 Hz held the main thread 98.5% of the time and its shares were not used.
- **Saves the framework wrote were read**: each later load of Austria-37_4-1 read the file the framework's threads and copy had written, and the game loaded it. One of them the background thread had left uncompressed, its move refused ("拒绝访问", os error 5) while the game was loading the same file; the game read that file with its stored blocks too. That refusal is S3's, not this branch's: inferred, the in-game load opens the file before its loader begins, and the loader is where a load waits for the thread.
- **The write watch** (a build with it alone) over the world write of the Austria save, the pool's seven threads left running: 53.4 million writes in five and a half minutes; what the threads wrote is in research/saves.md, "What writing the game state writes". The game went on afterwards.
- **Not verified**: a save of a game in a random new world (`rnw.zip`), a multiplayer game's save, the cloud save (which takes another path and keeps the game's code), a save on a machine with fewer than two threads (where the game's loops run), and the game without the framework loading a file whose entries the framework stored, which the framework's own reader and the game with the framework did.
- **Cleanup**: the game closed with `cargo xtask game stop`; releasing the claim put back every player file and the game folder's framework files and found each as the backup had it. The repository's `dev.toml` is as it was before the run.
