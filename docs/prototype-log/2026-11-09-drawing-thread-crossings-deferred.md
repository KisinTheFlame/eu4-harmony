# 2026-11-09 The drawing thread's last fault, its crossings deferred and its waits (tested by me)

This branch ([drawing-thread.md](../plans/drawing-thread.md), after [the first runs](2026-11-09-drawing-thread-first-runs.md)), built with `dev-test-games`, and with `dev-write-watch` for the watches; two test games one after the other; the 1780.7.1 save ([research/late-game.md](../research/late-game.md), "Saves to test with") copied into each one's `save games`, `menu.load`, `console run observe`, `session.view TUR`, `time.set_speed 5`, `time.resume`; the player's playset and settings, "Smooth map", 3840×2160 borderless, vertical sync on, a 144 Hz display, hidden. Other sessions' test games ran on the computer at the same time. What came out is weighed in [research/drawing-beside-the-day.md](../research/drawing-beside-the-day.md).

- **The fault left, waited for**: with a diagnostic of this run only (the main thread's stack taken when a frame of the drawing thread faults, since dropped), 4 minutes and then 17 game years (1780.7.2 to 1797.5.1) with the drawing thread: no fault. The cause was then read in the game's code instead: the unit's destructor lets its model go before the call the crossing was caught at ("The day's crossings read again").
- **The units' crossings caught where a model is let go**: the crossings fell from 320 to 490 in 10 s to 130 to 230; the main thread's wait for the lock did not change (1.4 to 1.9 s in 10 s). Split by where it waited: 0.4 s at application frames, 0.85 s for the last frame to be drawn, 0.3 s at crossings.
- **The write watch on the 3D map's drawing**: the first start crashed at the main menu in the map's markers' update (`0x10a6d16`), the watch's observer of it forwarding no arguments, as the framework's count read the function's prologue alone; with that fixed, a start hung once the watch began, as the day waited for the framework's army searches the watch held (`game-paths = ["ai", "saving"]` then); then two rounds with the markers' and the GUI's updates before it, and two with the day before it. What they found is in the research note.
- **The update not waiting for the last frame to be drawn**, the 3D map given the drawing thread's own frame length: the first build faulted in every frame at `0x818907`, its stub having changed `rax`, which the drawing goes on to read; kept, the main thread waited 0.9 to 1.1 s in 10 s.
- **Frames held back, by crossing**: in 10 s, the interface's daily refresh 90 to 140 times for 0.6 to 1.1 s, the floating texts 16 to 125 times for 0.4 to 1.8 s, the monthly refresh, the minimap and a province's owner told to the map for 0.03 to 0.1 s each.
- **The daily refresh deferred**: the crossings fell to 5 to 9 in 10 s, some 170 calls deferred. **The floating texts deferred**: the first build ended the game with heap corruption (`0xc0000374`, no crash folder) at the first day, three times: the function frees its two strings, which the framework had made itself; with the game's own strings made for it and the caller's freed for it, both deferred: 4 to 6 crossings, 175 to 256 calls deferred, frames held back about 0.1 s in 10 s, 114 to 124 frames a second; the main thread waited 1.2 to 1.3 s in 10 s, 0.8 at frames and 0.4 at the days' ends.
- **The lock let go for Present**: the main thread waited 0.3 to 0.5 s in 10 s, the drawing thread drew 120 to 138 frames a second.
- **Paused**: 117 frames a second, the main thread waiting 38% of the time and the drawing thread 52%, the main thread's frames no longer paced by Present; with a frame that runs no day waiting for the last one to be drawn, 144 frames a second, the main thread waiting 0.4 to 1.5 s in 10 s for the lock and 6 s for frames drawn.
- **Days in 60 s**, the last build, taken in turn: 968 and 790 with the drawing on the main thread, 854 and 944 with the drawing thread; before, in a quieter hour, 1,070 against 885 and 1,000.
- **Not verified**: the map following the mouse, or the floating texts and the windows' daily values as they look, in a game the player sees; saves other than 1780.7.1; more than a few minutes a run with the last build; a game loaded or left with the drawing thread on, beyond the one load each run; the instruction of the day that read the map interface's `+0x308`.
- **Cleanup**: both releases kept the test games' logs and said how each game ended (the heap corruptions above, the rest by stop); `dev.toml` removed; the diagnostics' copies are in the session's scratchpad.
