# 2026-11-08 A crash before the main menu, a command after observe, stacks past the stubs (tested by me)

Three troubles the test tools gave while measuring [sets of modifiers added through an index](2026-11-08-modifier-sets-through-an-index.md), each fixed on `claude/test-tool-fixes` and tried in one claim of a test game: the developer build with the test games' pipes and the test switches, the 1780.7.1 observer save copied into the test game's own user folder, hidden, from 14:53 to 15:04.

- **A crash before the main menu**: a start with `fail-startup` on ended with exit code 3 before the main menu (`startup failed in a hidden start, ending the game`). The start now writes that end into the claim's `game-ends.tsv` itself, as no `follow.exe` follows such a game, and the release listed it, `eu4.exe 21956 had ended by 14:53:14: the framework ended it after a fatal error ... (exit code 0x3)`, and said `the game crashed`. Before, it said the game did not crash.
- **A command right after `observe`**: the game console's `observe` builds the game's command, which the game carries out at its next frame, so that `console.run` answered in 0.1 ms and the session ended 160 ms later, at the next frame: a `time.advance` sent at once was refused, `it was sent in session 2, which ended before it ran; this is session 3`, in both of two runs. A check after each request whether the player's own tag had changed found nothing to see, since it had not yet. `console.run` now answers at the next safe point: in a third run it answered after 155 ms, after `session 2 ending (Country)`, and the `time.advance` sent at once ran in session 3 and advanced a day.
- **Stacks past the stubs**: the core names its jump stubs with the places in the game that jump to them (`eu4h_jump_stubs`), and `cargo xtask profile` steps over a stub's frame to that place. In two runs of 60 s at speed 5 (1055 and 1054 days), all 54 and 42 samples in the framework's search for a modifier fell under `0x8ea420`, the stub, and then the search, with the whole stack down to the thread's start; before, every one of them stopped at the stub.
- **Not verified**: 5 and 6 samples of 3000 still began in the core, at `eu4_harmony_core.dll+0x2eed`, code of the core's that is no jump stub, not looked into. A crash before the main menu other than the framework's own end at exit code 3, such as the access violation that first showed the trouble, was not caused again; it takes the same way, through the start's exit code.
- **Cleanup**: no `dev.toml` left; the release removed the test game's folder, its logs kept in `kept\`; the profiles deleted from the scratchpad.
