# 2026-11-04 What writing the game state writes (tested by me)

This branch's developer build with the write watch (`dev-write-watch`), `function = "0x74ff30"`, `calls = 3`, installed with `cargo xtask install` over the framework files another session had there, which were copied aside first; the player's playset; the game claimed with the game-lock skill. Austria-37_4-1 (ironman, 1724) loaded with `menu.load`; the game saves an ironman game as it starts, and that save's three calls of the world write were watched.

- **First try, the developer build with every tool**: the game stopped as the watch began, the main thread waiting in `RtlAcquireSRWLockExclusive` under `KiUserExceptionDispatcher`, from `HeapUnlock`. The exception handler's entry in the process's list is a heap block, whose count of calls under way the dispatch writes while it holds the list's lock; read-only, the first exception waited on itself. The process was ended. The watch now keeps that entry's pages, and those of the count it points to, writable.
- **Second try**: the watch began (94 threads, 8,060,495 blocks, 2,651 MB read-only in 639 ms); 90 s later the game ended in `CoreMessaging.dll` (`0xe0464645`, Windows' error report; no crash folder of the game's). The other threads had gone on, and a write the kernel makes into a heap buffer for a system call fails on a read-only page instead of stopping. The watch now suspends the other threads while it runs, and the build has the write watch alone, without the census and its lock. The crash dump Windows wrote (`%LOCALAPPDATA%\CrashDumps\eu4.exe.59096.dmp`) was removed.
- **Third try**: the three calls were watched and the game went on afterwards, the loaded game shown and its save compressed by the thread as always. The game state (`#0`): 94 other threads held, 8,060,390 blocks, 2,121 MB read-only in 669 ms; 25,821,586 writes in 13,172 groups, about a minute. The meta (`#1`): 2,526 writes; the AI (`#2`): 41,710.
- **What came of it** is in [research/saves.md](../research/saves.md), "What writing the game state writes": under the countries' and the provinces' loops, besides the save's own buffer, the C runtime's data of the thread, two static objects that hold the value being written (`0x15bf70`, ten copies of its code inline, and `0x2c59b0`), a pointer each country's objects keep (`0x29cd80`), and statics set up once. Not verified: code this save's countries and provinces did not reach.
- **Cleanup**: the game closed by ending its process. The framework files put back and compared equal to the copies (SHA-256), and the `dev.toml` the install put in the game folder removed. Releasing the game restored the player's files and found every file as the backup had it.
