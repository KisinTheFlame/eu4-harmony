# 2026-11-02 What an in-process return leaves behind (tested by me)

The run above left Poland's max manpower unexplained. This run looked at the whole game state after a return instead of what remote control reads, and timed each world reset. The build was the one above with the still notice, the time and memory of each reset in the log, and the history no longer read when the single player setup is entered for a save; built with `trace`. Two processes, `eu4.exe` started directly, the same playset and extension, driven by `eu4-harmony game`; backups as AGENTS.md says, the framework files copied aside first. At each point a save was written with the console's `autosave` (plain text) and copied aside, and the world object (`[0x233fe78]`, 0x7600 bytes) was read from outside the process.

- **Poland is no leftover**: a new game as France in a new process gave Poland's max manpower 26,430 in the first process and 26,305 in the second, as the run above had in its two. After a return from that France game, 26,430; after a return from Austria's game of 1724, 26,305; from the Netherlands' of 1592, 26,430. Poland starts with a regency whose dynasty is chosen at random, and its whole block differs between new starts in rivals, enemies, AI personality, mercenary leaders and income; its 22 provinces were the same in all saves. Which random choice moves the manpower was not looked for.
- **Left behind by a session**: compared section by section, a new game after the 1724 game had `hre_religion_status=2` against 0 after a new start or a trivial session, and that game's `achievement={ ... }` list, which a new start does not have. In the world object, `+0x2418`, which the game's loader and saver read and write as `hre_religion_status`, was 2 after both late sessions and 0 otherwise. The empire, the Celestial Empire, the great powers, the religions, the global flags and the revolution were as after a new start; the countries, provinces, trade and advisors differed as much between two new starts as after a return, so a leftover hidden among them would not show this way.
- **The gameplay options were put back to their defaults**: after every return, even from a game just started, the save's `gameplaysettings` differed from the player's `gameplaysettings.txt` in three of its 32 values, which a new start had as the file has them. The single player setup reads that file into the world (`+0x2140`) when it is made, with the main menu; at startup that is after the world reset, but after an in-process return the new main menu is made before the setup's own reset with the history, which comes after it (research/main-menu.md).
- **Where the time goes**: the reset at the return took 2.38 to 2.89 s, of which the country tags and database (`0x207310`) 1.73 s and the world's own reset (`0x749020`) 0.14 s; the reset with the history as the setup was entered took 2.98 to 4.78 s, of which the same country tags step 2.30 s and the history with what follows it 1.95 s. A return then a new game so sets the country tags up twice. Returns answered after 3.3 to 4.8 s, ironman ones with their exit save (1.1 s for the 1724 game).
- **Memory**: the framework's heap stayed at 1.9 MB from the first return on. Each reset gave memory back (private bytes 13 to 147 MB less) and each load took it (55 to 138 MB); at each return the process had 3,994, 4,090, 4,098 and 4,202 MB, with two large saves loaded in between. So the growth is the game's; whose part of the game was not looked for.
- **The still notice**: shown at each return ("正在返回主菜单……", over the game), at each in-game load and as the setup read the history ("正在准备新游戏……", over the main menu), in the middle of the screen with the rest dimmed: a screenshot taken while the notice showed was half as bright in the corner as the main menu after it. Gone at the next frame.
- **Not seen in the running game**: a load from the main menu after a return, which now skips the history (only in-game loads and new games were run); the odd moments, a failing ironman exit save and the setting off, as in the run above.
- **The trace tool**: tracing `0x9f9500` (with 15 other functions, through `EU4HARMONY_TRACE`) stopped the second process at startup, as the trace began writing the arguments of its first call; the game wrote a crash folder and did not answer. Started again without it, the game ran.
- **Cleanup**: `-Restore` listed what the run changed (the framework's logs, `continue_game.json`, `pdx_login_cache.txt`, `settings.txt`, the autosaves, `Austria-37_4-1.eu4` and `Castilla-4.eu4` with their backups, the second added, and `Castilla-4.tmp`, which an ironman save deleted), put each back, removed the added file and the crash folder of the trace, and found every file as the backup had it. The framework files in the game folder were put back and compared equal.
