# 2026-11-04 Achievement rules, and the save checksum of an in-game load (tested by me)

The achievement rules of ADR achievement-rules-can-be-relaxed, and why a save loaded in a session lost achievements. Runs of `eu4.exe` started directly, driven by `eu4-harmony game`: `menu.start CAS`, a normal game, run to the autosave of 1445.1.1 answering every question with its first option, then `menu.load autosave` and on to the autosave of 1445.7.1. Plain text autosaves (`compress_autosave=no`). The settings were written into `eu4-harmony/settings.txt` between runs. The Chinese playset, whose Chinese Language Supplementary Mod (`common`, `events` and others) and Graphical Map Improvements (`map`) change the game checksum; for the runs marked vanilla checksum both were taken out of `dlc_load.json`. Which salt a save's checksum was taken with was found by computing it from the file with the memory stream's sum (research/saves.md), with eight zero bytes and with `I_am_such_a_cheater`. The game was claimed with `game-lock`, which backed up and restored the player's files.

- **Both settings off, changed game checksum**: the log said the game checksum is not vanilla's, taken as not vanilla's; the save of 1445.1.1 had `achievement_ok=no`.
- **Outside ironman on, changed game checksum**: the same log line; `achievement_ok=no`.
- **Both on, changed game checksum**: "not vanilla's, taken as vanilla's"; `achievement_ok=yes`, salted with eight zero bytes.
- **Both on, vanilla checksum**: "vanilla's, taken as vanilla's"; `achievement_ok=yes`.
- **A defect of the game's, found here**: after an in-game load of such a save, the autosave of 1445.7.1 had `achievement_ok=no`. A build tracing `0x97500` and `0x14e3390` showed the check failing at the in-game load with the same salt the save was written with, the digest it computed not the save's; with both settings off and the vanilla checksum too. Loaded from the main menu of a new process, the same kind of save passed: the save after it was salted with eight zero bytes. Traced in one process, the menu's load summed the save with `0x171f3f0` and passed; the in-game load did not call `0x171f3f0` and failed: it checks a local save through a file's stream, whose sum differs (research/saves.md). The run of 2026-11-02 loaded only from the main menu. The build of that run (`ac48cae`), built and run again for comparison, has no in-game load, and told nothing more, its saves salted with `I_am_such_a_cheater` as the playset then changed the game checksum.
- **The repair**: with the file summed as the save was, an in-game load of a save written with the vanilla checksum and both settings off left the next save salted with eight zero bytes. With both settings on and the changed game checksum: the save of 1445.1.1 `achievement_ok=yes`, the in-game load, the save of 1445.7.1 `achievement_ok=yes`, both salted with eight zero bytes, and no line in the log saying the repair fell back to the game's sum. The repair's stub then went through the shared frame for calling Rust, as the stubs' test asks; the last run, again, gave the same.
- **Not seen in the running game**: the single player setup's text about achievements with the ironman checkbox clear (`menu.start` does not show the setup); a change of the settings in the settings window, which these runs made in the file; an ironman game, and an in-game load of a zipped or an ironman save, whose entries may not be read through a file's stream; why the salt was eight zero bytes.
- **Cleanup**: each game was closed by ending its process. Releasing the game restored the player's files (the autosaves, `continue_game.json`, `dlc_load.json`, the framework's settings and logs among them) and found every file as the backup had it. The comparison build's worktree was removed; the test saves and scripts were kept outside the repository and deleted afterwards.
