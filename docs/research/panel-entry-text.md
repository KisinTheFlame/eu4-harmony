# Panel-entry text and shared tooltip presentation

This note looks into the independent number below a panel button and the final tooltip-content path shared by the game and the main menu. The framework's panel entries and managed-element tooltips use these methods. Evidence is static reading of the installed EU4 1.37.5 baseline on 2026-11-12 and 2026-11-13; runtime claims belong to the separate prototype log. It extends [extension-windows.md](extension-windows.md) and [gui-drawing.md](gui-drawing.md). RVAs are into that baseline.

## Independent floating numbers

The complete `0x830700` body obtains three independent objects by name: `f_button_<slot>`, `menubar_floating_bg_<slot>` and `floating_number_<slot>`. Showing the number calls its own show method and writes a formatted number through the text setter `0x152ae10`; hiding the entry calls the number's own hide. The declarations in `menubar.gui` place the first number at (-364, -18), the button at (-360, -58); the number has `vic_18`, width 50, height 32 and centered text, with LOWER_RIGHT orientation. There is no shared button/number rectangle or number subscription in this setup. The absence of a subscription alone does not establish click passthrough.

### Positioning

The text-box vtable is `0x1d8fd10`. Its slot `+0x288` is **not** the button's position method: `0x152b7d0`, read to its return, handles a scrollbar callback and eventually adjusts the text's scroll offset through `0x152b390`. Reusing the button slot would pass an integer coordinate as an object pointer.

The position method is slot `+0x260`, `0x152af90(text_box, i32[2]* position)`, read completely. It calls the renderer at `text_box+0x118`, slot `+0x168`, with the two coordinates. A scrollbar, if present at `+0x1a0`, is placed beside the text afterward. Entry numbers have no scrollbar.

The text-box constructor `0x1529d20` was read to its end. It constructs the renderer with `0x15f3b40` and keeps it at `+0x118`; that complete constructor sets the renderer vtable to `0x1da1d40`. Its slot `+0x168` is `0x15f45d0`, which writes only the supplied x and y to renderer `+0x220` and `+0x224`. Its position getter, slot `+0x178`, `0x15f4240`, calls the already-known orientation resolver `0x152dce0` with renderer `+0x240`, `+0x24c` and the stored pair, then applies its animated offsets. Thus the setter takes the declaration's oriented coordinates, not already resolved screen coordinates. The text-box getter `0x152b060` calls that renderer getter and converts its float result back to integers.

### Visibility and input

The complete text-box show `0x152ac90` and hide `0x152ad10` bodies write the existing element-visible byte at `+0xc5` and call renderer slots `+0x60` and `+0x68`. For this renderer those are `0x15625a0` and `0x1558b80`, each a single store of 1 or 0 to renderer `+0x120`. Their scrollbar/animation branches are skipped for a number with no scrollbar. The framework checks the text class and these methods before calling them.

The complete text-box input method, slot `+0x48`, `0x152ab70`, handles a mouse-wheel event only when a usable scrollbar is attached. Only that branch adds the element's mask to the input's handled flags. Other input falls through without marking it. The base dispatcher `0x1552800`, also read completely, dispatches to that input method, with the animation step only for its own event kind. These facts distinguish the number's input from a subscribed button's. A native run must still check the resulting number hover and click independently of the icon.

## Final tooltip content

The complete update `0x1414ef0` calls `0x1415390` with the current cursor. Its direct caller is the main-menu frame at `0x10d3c4d`; the in-game update reaches it through `0x6eb6e0` ([drawing-beside-the-day.md](drawing-beside-the-day.md)). Both the presentation body and its final-content helper `0x1415bf0` were read through their returns.

For the normal camera, `0x1415390` calls `0x14debe0(scene, out_pair, cursor)` at `0x141548a`, returning at `0x141548f`. That complete hit-selection function takes the drawn nodes under the scaled cursor and scans them from topmost to bottommost. A node contributes its element at node `+0x118` when the element is visible (`+0xc5`) and not marked dead (`+0xc4`). The returned pair keeps the chosen element at `+8`. This test does not read the button's enabled state. The alternative-camera branch uses another scene query; the existing view callbacks can supply its actual element to the same presentation cycle.

The presentation builds an aggregate with a main game string at `+0`, a delayed game string at `+0x20` and native presentation flags after `+0x40`. It asks the view/provider for content and may append the native shortcut. Only then does it call `0x1415bf0(tooltips, aggregate)` at `0x1415703`. The aggregate move `0x81f4a0`, read completely, independently moves those two strings and copies the following flags. The final-content helper normalizes the main text, adds delayed text when its native timer permits, compares the result to the previous text and rebuilds the text texture only when that result differs. Empty content hides the native tooltip. Its font parsing, wrapping and texture construction remain the existing game's paths described in [font-textures.md](font-textures.md); they are not replaced.

The framework uses one final-content observer. A managed native hit replaces both strings with its current content, including an explicit empty value, while retaining native placement flags. An unmanaged hit leaves both strings and all flags untouched. A hit pointer is held only for this presentation call, reset at its entry and return; it cannot persist across destroyed rows, closed windows or sessions. Window elements, entries and supported hosted elements use the same bound-element content and visibility gate. No new tooltip timer, layout engine or screen-position calculation is introduced.

## Drawing the native tooltip over framework-drawn controls

Framework-drawn windows follow the native scene. Their tooltip uses the same native content preparation, but its prepared text-texture node must be drawn after those windows. The ToolTip declaration is a text box, with the dialog background included in the same texture. The complete creation chain is `0x1414c00` → `0x14e8cf0` → `0x15e6d60` → `0x15a0d20` → `0x14dbdc0`. The holder at owner `+8` keeps the node at `+0xd0`. The text-holder constructor initially sets the node's hit target at `+0x118`, but the tooltip-specific rebuild deliberately clears it at `0x1414de9`, after removing it from the manager's ordinary lists. A tooltip must not become its own hover target. Consequently, readiness checks follow owner → holder → node and the current draw vector, not a non-null hit-target pointer. Its fallback constructor `0x15506e0`, reached through sprite construction `0x15da800`, installs class `0x1d933b0` at `0x155072c`. The constructor operand checks the class address itself; checking only draw slot `+0x58` does not cover reading the class address at runtime. Draw slot `+0x58` is `0x1550950`. Holder `+0x1e8` is a font, not another drawing node.

The complete draw-list helper `0x14dd350(graphics, list)` reads a `std::vector` of node pointers, applies clipping, alpha and layer, and calls each node's draw method with its already prepared transform. Its header has begin and end pointers; it is not the game's linked-list representation. The adapter uses the shared vector-pointer reader, and a regression checks filtering against that exact storage shape without mutating it. The normal GUI traversal supplies that transform; repeating traversal `0x14dd7a0` would mutate lists and walk siblings. The two ordinary draw calls return at `0x14dd2bd` and `0x14dd742`. The implementation replaces the helper's argument with a private list that omits only the exact prepared managed tooltip node, preserving the game's own list. After framework drawing, a private one-node list goes through the same helper once. This avoids blending the tooltip twice during its fade.

The ready path of `0x1550950` continues through `0x1551840` and `0x15bd180`, all read through their returns. It uses the existing texture and mesh; the mesh-frame selector write at node `+0x2c0` is deterministic. A dirty node (`+0x2db`) or missing texture (`+0x278`) can instead build an offscreen texture scene, so such a node is never filtered for late drawing. The adapter also checks holder visibility, its dead byte, the exact class, owner/holder/node relations, current content and actual membership in this frame's list.

Native BeginScene `0x16d4e00` and EndScene `0x16d4e50` take the renderer in RCX, returning a Boolean in AL. The graphics object's renderer is at `+0x88`. BeginScene also resets the renderer's vertex-declaration cache. After a successful begin, GUI setup `0x14dcf90` establishes the viewport, blend and rasterizer state, the single node is drawn, and EndScene runs even if setup or drawing returns an error. This occurs after the framework backend has restored its D3D state block and before screenshot capture or release of the presentation lock. Restoring only device state after the native pass would leave the native cache inconsistent.

Tooltip owner constructor `0x1414780` sets class `0x1d83788`. Rebuild/invalidation `0x1414e50` releases its graphical holder; owner deleting destructor `0x1414b60` does not call that invalidation function. Holder deleting destructor `0x15a1240`, class `0x1d99230` slot `+0x38`, returns its node to the manager. Observers on all three clear a shared generation before destruction, invalidating saved drawing-thread state as well as main-thread state. Holder kill `0x15a1540` only deactivates and marks it dead; holder slot zero is not its destructor. Session end and device reset also clear the presentation. Refreshing identical owner/holder/node/content preserves its generation: a presentation call between ordinary drawing and Present must not invalidate the same already-filtered node. A changed target, changed content, missing self-drawn target or failed presentation invalidates it. These static paths establish the implementation's checks, not runtime success.

## List visibility

The list's visual interface is root `+8`, class `0x1d90fd8`, rather than its root class `0x1d90ea0`. Show thunk `0x1533224` subtracts eight before `0x15315e0`; hide thunk `0x153320c` does the same before `0x1531710`. Both root bodies were read through their returns: show sets root `+0xcd`, activates its graphics, rows and scrollbar and requests layout; hide clears that byte, calls `0x1532c60`, then hides the scrollbar. This extends the existing list-object evidence in [window-elements.md](window-elements.md); the hide helper was not independently expanded in this investigation.

## Runtime evidence and limits

- The [managed-tooltip run](../prototype-log/2026-11-13-managed-tooltips.md) verifies direct DDS images, independent number hover and entry activation, disabled-element tooltips, stationary changes, row replacement, clearing across close/reopen and ordinary map tooltips. It also records the corrected native tooltip above a framework window at the lower screen edge in main-menu and drawing-thread frames.
- The run does not exhaust device loss, reload/unload while visible, every idler switch, language changes while hovering, alternate tooltip resources or every destruction interleaving. A failed late scene or a state change after filtering can omit that frame's tooltip; the static guards alone do not establish successful presentation.
- The renderer size getter `0x15f3ea0`, text-box renderer reparent/reset helpers `0x152b0a0`, `0x152b120`, `0x152b220`, size forwarding `0x152b2c0`, size-pair forwarding `0x152b6f0`, the Boolean accessors `0x152b2f0`/`0x152b300`, and the thunk `0x152b8c8` were inspected to reject incorrect position-method candidates; they are not used to move an entry number.
