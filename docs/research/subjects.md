# Subjects (for `game::subjects`)

Baseline 1.37.5. All addresses are RVAs. Read from `eu4.exe` on 2026-11-05 for part A6 of [player-actions.md](../player-actions.md); what was checked in the running game is in [prototype-log.md](../prototype-log.md). Annexing and integrating a subject, and the other subject actions of the diplomacy panel (`vassalaction`, `designate_march`, `tributary_state_action`, `abandon_union`), are diplomatic actions ([diplomacy.md](diplomacy.md#the-diplomacy-panel)).

## The interactions

- **A fixed set.** The game has 41 subject interactions, each a static object of a class of its own made by a static initializer between `0x81ca0` and `0x83840`, which stores the class into the object and hashes the object into a table (buckets `0x1fd5230`, size `0x1fd522c`, count `0x1fd5228`) under the token of its key, and appends it to a vector (`0x23581c8`–`0x23581d8`). The object is 16 bytes: its class and its number (u32 at `+8`), which is the token of its key in the game's token table: `placate_rulers` (`0x31d9`), `knowledge_sharing`, `change_colonial_type`, `upgrade_subject_type`, `embargo_rivals`, `place_relative_on_throne` (`0x31dd`), `enforce_religion`, `scutage` (`0x31df`), `subsidize_armies`, `enforce_culture`, `siphon_income`, `seize_court_resources`, `request_extra_levies`, `grant_administrative_autonomy`, `support_loyalists`, `send_officers`, `divert_trade`, `fortify_march`, `seize_territory`, `start_colonial_war`, `replace_governor`, `grant_province`, `grant_core_claim`, `sacrifice_ruler`, `sacrifice_heir`, `increase_tariffs`, `decrease_tariffs`, `customize_subject`, `takeondebt`, `bestow_gifts`, `send_additional_troops`, `demand_artifacts`, `demand_additional_tribute`, `force_seppuku`, `return_land`, `contribute_to_capital`, `conscript_general`, `force_isolation`, `press_sailors`, `allow_settlement_growth`, `block_settlement_growth`. The table in `game::subjects` holds each with its object and class; the initializer's two instructions are dependency points.
- **Their methods** (vtable `0x1ce6dc8`, `place_relative_on_throne`'s; each class has the same slots): `+0x10`(interaction, out) writes its name, localized (`PLACE_RELATIVE_ON_THRONE`); `+0x28`(interaction, command, reasons) its own conditions, with the reasons appended to a `std::string` or null; `+0x30`(interaction, overlord's tag) whether the overlord may use it at all; `+0x38`(interaction) the bit of a subject's interactions going on that is its, 0 for one that does not go on. Not read: `+8`, `+0x18`, `+0x20` (`+8` takes the command and makes a diplomatic action of class `0x1c578f8`, presumably the one the subject is told of).

## The `subject` command

- **The command** (`subject`, token `0x31d8`, vtable `0x1c3a650`, write `0xaf3bc0`): `overlord` (a tag, `+0x50`), `subject` (`+0x58`), `third_party` (`+0x60`, when its tag is valid), `cancel` (`+0x90`, a bool, written only when set), `interaction` (the interaction's number, from the object at `+0x98`), `index` (`+0x68`, when not negative), and a string under token `0xf` (`+0x70`, when not empty; presumably a name, for `customize_subject`). Written as `subject={ overlord="TUR" subject="SER" interaction=12767 }`.
- **Its check** (`+0x40`, `0xaf3e20`): the interaction's `+0x30` with the overlord, then `0xaf3e70`(command, reasons): the overlord has provinces or is the special country 7, the subject's overlord is the overlord, the subject's type (`0x3d79f0`(subject)) allows the interaction (`0xb22910`(type, interaction)), the command stops the interaction (`cancel`) exactly when it goes on (the bit `+0x38` answers in the subject's bit set at `+0x78`, read while the subject has an overlord, `+0x18f7`), and last the interaction's own conditions `+0x28` with the reasons.
- **What the framework does**: `subject.options` lists the interactions whose `+0x30` allows the player and whose type check allows them, with whether each goes on (`active`); it writes the command (with `cancel=yes` for one going on), has the game read it (`commands::with_command`) and asks `0xaf3e70` without and with a string, the reasons being the bulleted lines it writes (every line, when it bullets none). `subject.interact` does the same and then posts the command through the command layer.
- **What `index` and the string are** (read from each interaction's methods at its vtable's `+0x18`, `+0x20` and `+0x28`, the command at their third argument; 2026-11-05): `grant_province` (`0xb0c8c0`), `grant_core_claim` (`0xb0d920`), `return_land` (`0xb147a0`), `fortify_march` (`0xb07d50`) and `seize_territory` (`0xb08bc0`) read `index` (`+0x68`) as a province's number, the province array (`world+0x1ca8`, `0x2e10` bytes each) indexed by it, a negative one taken for none. `upgrade_subject_type` (`0xaf90a0`) reads `index` as a mode (1 rescinds the upgrade, `RESCIND_UPGRADE_SUBJECT_TYPE_SPECIFIC_DESC`) and the string (`+0x70`, its length `+0x80`) as the upgrade's key. `start_colonial_war` (`0xb09dd0`) reads `index` and `third_party`: it looks for an entry whose `+0x40` equals `index` among the subject's entries for the third country (country `+0x1510`, `0x48` bytes a country), the entry's `+0x40` indexing a database array at `+0xd0`; what that is was not followed. No other interaction reads either. The framework writes `index` from `subject.interact`'s `province`; the command log showed `subject={ … overlord=HUN subject=CRO interaction=12874 index=1864 }`.

## Rivals

- **The commands** `add_rival` (`0x2fae`, vtable `0x1c55138`) and `remove_rival` (`0x2faf`, `0x1c54a68`) share their writer (`0x2ab380`): `country` and `rival`, both tags; `replace_rival_command` (`0x3005`, `0x1c54b10`) is the third. The framework posts `add_rival={ country="TUR" rival="BYZ" }` and `remove_rival` likewise; their checks (`0x2ab780`, `0x2ad400`) give no reason, so a refusal has none. Where the diplomacy view lists the countries the player may rival was not looked for.
