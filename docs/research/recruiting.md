# Recruiting (for `game::recruiting`)

Baseline 1.37.5. All addresses are RVAs. Found by reading eu4.exe on 2026-10-29; what was checked in the running game is marked "tested" (the run is in [prototype-log.md](../prototype-log.md), remote control C6). The recruit command itself, its fields and its check, and what the province snapshot asks of it, are in [provinces.md](provinces.md).

## The recruit button

- **The province view's recruit button** is `0xe214b0`(entry, click): the clicked entry's index into the panel's list of unit types (`+0x170`, its length `+0x180`), the province at `[entry + 8]`. It does nothing when the province is under siege (`+0x388` not null) or its owner has no core there (`0x98840`(province, tag), which looks for the tag among the province's cores, a vector of tags at `+0x490`/`+0x498`). The recruit check `0x346570` has reasons of its own for both ("MACRO_UNDER_SIEGE" at `0x34688b`, "MACRO_NOT_CORE").
- Then, at `0xe2151f`: `operator new`(`0xa0`) (`0x1a332d4`), the constructor `0x26ce40`(command, the player's tag as the world gives it, the player mode's switched tag included, the unit type, the province's ID `+0x20`, no mercenary company), the session from the map manager's method `+0x80` (`0x811aa0`: `[[map manager + 0x330] + 0x370]`), and `0x14ca2d0`(session, command), which posts it. It neither asks the command's check first nor frees a command the session does not take. Afterwards it hands `0xb30f60` the date, the player, the unit type's kind and the source "province_view"; that builds a record named "unit_construction" for the object at `[0x242bf50]` (not worked out further). The framework does not call it.
- **The macro builder** (`0x11c1d80`) does the same with "macro_builder" as the source, but asks the command's check (its vtable's `+0x40`) first and posts with `0x14ca210`(session, `std::unique_ptr` to the command), the same post taking the pointer out of its owner.
- The other constructor, `0x26cf20`, is called once, at `0x16b0a4`, which works out the command's cost (`0x348330`) and keeps the command in a container of its own (`0x11eda0`) instead of posting it (not worked out further).

## The session

- **The game's session** is Clausewitz's `CSession` (`0x14ca360`, its update, says "CSession::Update called from other than main thread" and names `clausewitzlib\session.cpp`), of class `0x1d8c900`, made by `0x14c83e0` and set up again by `0x14c97e0`. Its kind (`+0x4c`, i32) sets `+0x54` for kind 1 and `+0x55` for kind 2 (u8 each). `+0x58` is where taken commands go (its method `+0x30` takes one), `+0x8c` and `+0x68` what a taken command is stamped with.
- **The post `0x14ca2d0`(session, command)** answers whether the session took the command: not without `+0x58` or without a command; when neither `+0x55` nor `+0x80d` is set, only a command whose method `+0x80` or `+0x58` says it may come at any time (the recruit command's both answer no, `0x8f450`). A taken command gets `+0x38` = `[session + 0x8c]` and `+0x48` = `[session + 0x68]` up to `0x7fff`, and goes to `[session + 0x58]`'s method `+0x30`; the session owns it from then on. One not taken is still the caller's: the framework destroys it with its destructor `0x26cda0`(command, 1), the vtable's `+0`, which frees its `+0x98`, its text at `+0x18` and the `0xa0` bytes. The engine's own observer of this function (`game::events`) looks only at movement commands.
- **`+0x80d`** (u8) is written only by the map manager's frame `0x8137c0`: saved at `0x813c56` (and cleared in the player mode 7), set before the session's update `0x20f810` (`0x813f8e`), cleared after it in the player mode 7 (`0x814012`), and put back as it was at the frame's end (`0x816607`).
- **Tested**: at the framework's safe point, in a Castile save of 1470 (ironman, as the game console said) and a France save of 1444, the session was of kind 2, `+0x54` 0, `+0x55` 1, `+0x80d` 1, the player mode 0; the post took every recruit command. A single player game's session so takes the command at any time. A session of kind 1, which was not seen (multiplayer, out of scope), takes it only while `+0x80d` is set, within the map manager's frame or outside it when the frame found it set.

## When the game carries it out

- **At the next frame**: the map manager's frame calls the session's update (`0x20f810` → `0x14ca360`), which asks the recruit check again (`0x26e080` from `0x14cab33`) of a command object of its own, not the one posted, and then executes it (`0x26cfe0` from `0x14d4e62`), which queues the construction. Tested with the call trace: 2 to 9 ms after each post, paused and running, both answering 1. A command the check refuses then is not executed: the update writes "Discarding invalid command! ID: %u, Type: %s" to the game's log (`0x14cab85`, naming `session.cpp`; under a flag, also "Discarding command … due to failed IsValid check: ", `0x14cad56`) and goes on to the next command (`0x14caed3`). The framework, which answered when the session took the order, does not hear of it. So orders posted at one safe point or in one extension callback are each checked by the framework against the same treasury, manpower and sailors, and those the first ones leave too little for are dropped at that frame (not tried in the running game).
- **The cost is taken at once**: tested, a cavalry regiment in Paris took 25 ducats and 1000 men (585 to 560, 10,798 to 9,798) while the game stayed paused. The regiments waited in the outliner's list of units being recruited ("我们正在巴黎招募拉丁中世纪步兵。"), and Seville's province window counted the two ships in its queue.
- Other call sites the trace saw while the game ran, not followed: the check from `0x16e50e` on worker threads, and the check from `0x1dc58f` and `0x1dc973` and the execute from `0x1dc661` on the main thread.

## What the framework does

`game::recruiting::recruit`: the player's unit type of the kind (`game::provinces::unit_type`), refused without one; the recruit check with the game's reasons (`game::provinces::can_recruit`), refused with them; then the session, as the button finds it (`0x811aa0`); the command as the button makes it (`0x1a332d4`, `0x26ce40`), its own check (`0x26e080`), which adds the command's rule for ships the snapshot leaves out, and the button's post to the session (`0x14ca2d0`). A command its check refuses, or the session does not take, is destroyed (`0x26cda0`). The session is found before the command is made, so that between the two only a call into the game can fail, and a command is left behind only when the game faults on it. The command's class, size and methods are named in `objects::campaign` (`classes::RECRUIT_COMMAND`, kept where its constructor sets it, and `recruit_command`), with the map manager's method that answers its session (`map_manager::SESSION`); the session's class and that method are in `objects::session`. The dependency points in `game::recruiting` keep the constructor, the check and the destructor as the class's methods, and the button's code from the allocation to the post, which uses the command's size, the player, the province's ID, the absent mercenary company and the map manager's method. The allocator is `unicode::fill::ALLOCATE`, the post `game::events::DISPATCH`.
