I. Conclusions and entries usable for the next runtime verification

1. Preferred "daily computation finished" candidate: RVA 0x758430, ABI void fn(World* RCX).
   Above it, the DailyTick command execution is RVA 0xB79520, ABI void fn(Command* RCX).
   B79520 has the string "DailyTick without gamestate"; with a non-null world it calls 758430(world) directly.
   758430 sets world.byte(+0x1E10)=1 on entry; world.i32(+0x1DD0)+=0x18; runs the daily update and the month/year boundary work; clears +0x1E10 before a normal return.
   Exact instructions: 0x1407584A2 writes 1, 0x140758Aef calls 0x14075BBE0 (the body of the day), 0x140758EEE writes 0.
   Reading the date in 758430's onEnter gives the old day; midway through the function the date has advanced but the world update is not finished. So verify onLeave first.
   The function does not depend on a selected army, the army panel or the vanilla rebel-suppression mission.
   Not yet verified at runtime: the thread identity, ordering relative to the full FOW refresh, and nesting/synchronization with the task system. The static call/return and the update flag are strong leads, not a confirmed promise of cross-thread safety.

2. A frame entry independent of the army panel: RVA 0x8137C0, ABI void fn(Manager* RCX, uint8 flag DL).
   Confirmed: manager = *(world+0x1E00), main vtable RVA0x1CB8460, slot +0x20 points to 8137C0.
   The entry saves DL; there is no evidence that it is a multi-parameter structure. Keep the unknown flag as it is.
   This function checks the pause state, runs UI/manager updates and, when not paused, calls 757AD0(world, the time value at manager+0x310).
   It does not depend on a selected army panel, but contains conditional branches for particular UI objects. This round lists it only as a candidate for observation and for a future main-thread queue pump.
   It must be observed whether its threadID equals the thread already seen for normal UI/FOW, and whether daily events are nested inside this thread's frames.

3. Per-army daily update: RVA 0xD3E110, ABI void fn(Unit* RCX).
   The logs tied to the source path unit.cpp inside the function are plainly "CUnit::DailyUpdate - Start, %u, %u, %d" and "CUnit::DailyUpdate %u %i".
   Land army vtable RVA0x1C42540 +0xD0 -> 0x1A2D30; this wrapper calls D3E110 first. The navy's 0x90E410 also calls D3E110.
   This proves a timing for army updates that does not depend on the selected panel, but it is not a boundary for a consistent snapshot of the whole world: other units may not have been updated yet that day.
   Just because one army's daily update has returned, do not treat the whole map's roster/FOW as updated for the day.

4. The vanilla mission path can serve only as cross-evidence:
   army.pointer(+0x1F8) points to the mission object; the mission's main vtable is RVA0x1C440C0; slot +0x80 is 0x1C9D30.
   Address 0x1C440A8 is the vtable of another container inside the object; do not use it to wrongly label the main mission tick as a call through slot +0x98.
   0xD3C560(Unit*) checks +1F8 and mission slot +50, then calls +78 and +80; a non-zero return code from +80 is passed to D3B8B0 to handle.
   D3C560 sits at land army vtable+0x140. It depends on a mission existing and being in a valid state, so it cannot replace general daily scheduling.

II. Date and the limits of a safe snapshot
world = *(module+0x233FE78), manager = *(world+0x1E00).
world.i32(+0x1DD0) is the native date scalar. It grows by 24 per ordinary game day; it is not a day number that "goes up by 1 each time".
758430 also maintains world.i32(+0x1DF0)=floor((rawDate-43800000)/24).
The observer records day (raw +1DD0), absoluteDay (+1DF0) and dailyUpdating (+1E10) together.
The core only needs same-day deduplication and rollback detection; using the raw date as an opaque day token still gives once per day. Host field names should avoid suggesting that 24 means 24 game days.
Even when +1E10 is 0, the world/session, army identity and FOW completeness must be verified; it cannot replace a load lifecycle marker.
A date rollback, a changed world pointer and loading a save all invalidate the old session. An unchanged world pointer does not prove there was no load.

III. Pause: the full predicate can be recovered, and cannot be reduced to one force byte
0x7E01B0(PauseState* RCX) -> bool AL.
Call site 0xB7F87B uses manager.pointer(+0x418); a non-zero AL goes with the GAME_PAUSED string, AL of 0 with GAME_UNPAUSED.
PauseState layout: +0/+8 are begin/end of the pause request vector, +0x48 is the force flag, +0x50 the manager pointer.
Exact meaning: force48 != 0 || (!helper6EAA10(ownerManager) && ((end-begin)&~7) != 0).
Reading +0x48 alone does not stand for every cause of pause.

helper6EAA10(Manager*) -> bool AL:
  If manager.vslot(+0x318) is 0, it returns false.
  For this manager type slot318 is 0x80FF80, whose leaf machine code reads manager.byte(+0x19F1).
  manager.vslot(+0x80) is 0x811AA0, which returns *(*(manager+0x330)+0x370), called the network/session object below.
  If network.byte(+0x54)==0 and byte(+0x55)==0, the helper returns true.
  Otherwise it walks the world.pointer(+0xA50) chain, next=+0x60; if any node.i32(+0x18) differs from network.i32(+0x8C) it returns true, otherwise false.
The fields' domain names are not fully recovered; do not guess single-player/host identity from +54/+55 alone.
The observer reproduces the logic above with pure reads, and passively listens for 7E01B0's real return so the parent task can cross-check; it does not call the function.

IV. Land army battle, retreat and lock
The following is limited to the verified land army vtable RVA0x1C42540; it does not automatically apply to other unit types.

inBattle: army.pointer(+0xC0) != NULL.
  In 0xD45DE0 this condition enters the NO_REORGANISE_UNIT_IN_COMBAT explanation branch;
  0xD55E70 also references UNIT_IN_BATTLE in the branch where +0xC0 is non-null.
  +0xC8 is not a "retreat pointer": 0xA9E160 explicitly works on +0xC8 in the branch with the log "Removing REB unit from siege", so its meaning must be kept separate.

movementLocked: army.byte(+0x202) != 0.
  Land army vslot+0x118 -> RVA0xD4F2A0; the full leaf bytes are 0F B6 81 02 02 00 00 C3.
  0x141229425 calls this slot, and the true branch then uses MOVEMENT_LOCKED_DESC.
  It can be read without calling the function; a runtime test still needs one comparison past the march-lock threshold.

retreating: army.byte(+0x203) != 0 || army.byte(+0x204) != 0.
  0xD45DE0 uses NO_REORGANISE_UNIT_RETREATING when either is non-zero.
  +0x204 also takes part in the UNIT_MOVEMENT_RETREATING and SHATTERED_RETREAT_DESC branches.
  0x21EB30 writes word(+0x203)=0x0101, which shows the two bytes cannot be merged into one bool or a mutually exclusive enum.
  Naming them as normal/shattered retreat should rest on cross-evidence from the UI; not all writers of +203 have been recovered.

canAcceptOrders: this round does not claim to have found a complete, unified predicate.
  The submit function D50340 also checks vslot70 of the object at army+C0; the actual game may allow some retreat requests from battle, but our automatic combat explicitly forbids issuing orders during battle, retreat or lock.
  The host can first make these three required blocking conditions, then combine them with verified facts such as ownership, disappearance, transport, session and legal path.
  D55E70 also mixes in conditions such as embarking, so its return cannot be named "ordinary movement allowed" directly.

V. Source of manual moves: a narrower candidate exists, but it is still not full proof
D5D680 ABI: void(Unit* RCX, int32 destination EDX, uint8 replaceExisting R8B, uint8 alternatePolicy R9B).
  It chooses the ordinary or alternate policy and, once a path is found, calls D50340(army,path,replaceExisting,0x18).
  The measured returnRVA D5D978 matches this direct submit call exactly.
  D5D680 is called by D5CF90; D5CF90 also has direct callers from automatic missions, such as 0x1D0E20.
  So a move through D5D680 or D50340 that "we did not issue" is not the same as "a manual move by the player"; treating it so would wrongly stop AI, subject or vanilla missions.

Narrower candidate: D5CF10 ABI void(MovementCommand* RCX); its pointer is in the vtable area at RVA0x1D1D440.
  It calls 1414CF730 on command+0x58 to resolve a TypedRef; if the result is non-null it subtracts 0x10 to get the army, and writes it back to the command+0x50 cache.
  It uses target arrays such as command+0x60 and +0x78 and the bytes at +0x90/91/98/99, then calls D5CF90.
  This function is a lead at the command execution layer; the chain a player's right-click enters can be passively observed here.
  It is not proven that all its creators are the local player, and neither the issuer's country/client fields nor the command types for Stop, split and merge have been recovered.
  The adapter should keep track of which orders it issued itself and actively watch for manual commands; a changed path alone must not be taken as a manual takeover.

VI. Defeat: the main open item; do not simply use the retreat flag in place of a "defeat event"
0x21EB30(Side* RCX) walks the armies in the side+0xE8 chain, removes them from the battle/siege and sets the retreat state;
in the branch where there is a line of retreat and the removal is not special, it sets army.byte(+0x205)=1, then writes +203/+204.
Its code comes from combat.cpp, but it is general handling for one side leaving/retreating:
  0x22BEA0 calls it; that path has the log "Combat ended (regular)".
  0x23FCE0 also calls it; that function handles siege/land morale state, so all calls cannot be lumped together as land battle defeats.
  The command execution path 0xD6B910 can also set +204=1, so watching only the rising edge of +204 cannot tell a retreat the player chose from a defeat.
  The only assignment of constant 1 to byte205 found is in 21EB30, but without proof of all its reads, writes and lifetime it cannot currently serve as an exact defeated event.
The identity of losingSide in the battle resolution and its unit list (including annihilation and removal with no line of retreat) must be confirmed further before core.defeated fires once.
This round's observer names this entry side-retreat and explicitly does not pass it off as defeat.

VII. Passive observer the parent task can run
File: tools/native_scheduler_observer.js.
It only listens with Interceptor and reads; no NativeFunction, replace, write, native function calls, or attach/launch of its own.
To start it requires a unique stage path, x64, and all 10 entry prefixes matching; the parent task verifies the full SHA separately.
Observation points: manager-frame, daily-command, world-daily, unit-daily, mission-dispatch, pause-predicate, movement-command-execute, move-builder, path-submit, side-retreat.
Each kind of event has a global log cap; per-unit daily updates log at most 3 groups per date, 24 in total. counts/threadCounts keep accumulating for status.
manager-frame prints enter/leave for the first 4 frames and on date/pause changes, at most 32 groups in total.
Each record contains threadID, the raw date, world and the daily-update flag; daily-update and command records log enter/leave, callerRVA and a short call stack.
RPC status() reads the counts/current state; dispose() only detaches these listeners.

Suggested steps for one observation:
  1. Load the observer while a confirmed test campaign is paused, close the selected army panel, and keep the usual map view.
  2. Unpause, advance 2 to 3 days at low speed, and pause again.
  3. If evidence of the manual source is needed, select an army and right-click once as normal; no risky combat order is needed.
  4. Read status and dispose. Check whether the manager frame/day boundary thread is the same as the known UI/FOW thread.
Success means: rawDate increases by 24 across world-daily, with dailyUpdating=0 at leave; manager-frame and daily events still appear with no panel; while paused the manager frames continue but day does not increase; the real pause return matches the pure-read formula.
Even if all of this holds, the FOW refresh timing and the load/save boundaries must be wired into the full adapter before it is declared safe for production.

Runtime verification addendum (2026-10-26, scheduler-trace-01.jsonl)
Isolated PID43680, on the normal map with the army panel closed: manager-frame, daily-command
and world-daily were all on thread 23700, the same as UI/FOW. The first daily update entry had rawDate56679696,
absoluteDay536654; leave had rawDate56679720, absoluteDay536655, dailyUpdating0.
The pause predicate's actual return matched the pure-read formula; manager frames continued while paused. The log also shows
nested manager frames during dailyUpdating1, so manager.onLeave alone cannot be taken as a stable boundary;
a production pump must also check world+1E10==0 and avoid re-entry. Normal automatic advance also produces many
movement-command-execute events, so this command execution entry cannot be equated directly with manual user actions.
