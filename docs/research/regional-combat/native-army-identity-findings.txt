Persistent army identity: targeted static reverse engineering
Date: 2026-10-26
Baseline SHA256: 97dd63a811487fbe2c917f2c15b1e68f7222bef74a833889cf943c8010049d5e.
Only the frozen exe and existing static material were analyzed; no running game process was read, attached to or manipulated.
All RVAs are relocated against the actual load base. Ghidra 12.1.4, -noanalysis -readOnly; the raw results are kept in work/native-identity.

Conclusions
The full 64-bit value at army+0x20 is indeed the object identity that native saving and loading write and read, not a raw object address:
  low32 = type; high32 = id sequence number.
Example: 28394028793910 = 0x000019d300000036 = type54, id6611.
The save path examined writes only these two parts, with no extra generation field; no generation can be split out of this qword.
Recommended: the external persistent key uses the full uint64 native ID, generation stays 0, and the boundaries are guarded separately by an exact slot + save hash and a check of the new session.
This is not a proof that covers every allocation/reuse path; that a real save and reload keeps the same ID should still be confirmed by a runtime test.

1. Key finding: the serialization interface is in the second vtable
The early slots of the army's main vtable RVA0x1c42540 are mostly game/UI behavior; do not mistake the large function at +0x18 for serialization.
ctor0x1a20a0 and ctor0x1a21a0, which takes arguments, both explicitly set:
  *(army+0x00) = module+0x1c42540
  *(army+0x10) = module+0x1c424f0
The second vtable's this is army+0x10, so its this+0x10 is exactly army+0x20.
Second vtable slots:
  +0x10 -> 0x1a6320, army writer;
  +0x18 -> 0x17068b0, candidate for the generic read entry;
  +0x20 -> 0x1a5e50, army token-reader;
  +0x40 -> 0x14cf190, object ID registration;
  +0x48 -> 0x14cf120, not named further.
Evidence: work/native-identity/pseudocode2.txt; the second-level vtable read directly as 8-byte pointers; vtable-xrefs.json.

2. Save path: confirmed to write army+0x20
0x1a6320(this=army+0x10, writer) first calls the generic unit writer 0xd3d2f0.
The first effective serialization call in 0xd3d2f0:
  0xcd8f0(writer, token=0xb, this+0x10)
This writes the 8-byte identity at army+0x20 as an ID block.
0xcd8f0 writes the block name token, then calls 0xce610 to write its value.
0xce610 uses:
  ID pointer+4 -> token0xb, written with %u;
  ID pointer+0 -> token0xe1, written with %u.
Exactly two 32-bit parts are written: no object address, separate generation or run-time epoch.
Evidence: work/native-identity/pseudocode3.txt:3-115, pseudocode4.txt:3-35, pseudocode5.txt.
No full token dictionary has been exported independently yet for the tokens' text names; the bit layout and the data flow of the two fields are directly visible and do not depend on guessing the text names.

3. Load path: confirmed to read back into the same 8 bytes
The army token-reader 0x1a5e50 delegates tokens it does not recognize to the unit reader0xd3c640.
When the unit reader meets token0xb:
  0x14cece0(reader, secondary_this+0x10)
that is, it reads the ID into army+0x20.
The generic ID reader0x14cece0:
  token0xb reads the unsigned id sequence number;
  token0xe1 or 0x15 reads type;
  finally it writes *output = CONCAT44(id32,type32).
In the implementation, type is parsed, taken as a ushort and then zero-extended to 32 bits; the high 16 bits of the low 32 bits must not be assumed to be a persistent generation.
The code also tolerates token0x16, read into temporary space, but that temporary value takes no part in the final 64-bit identity.
No recoverable generation output field was found here.
Evidence: the param_3==0xb branch at the end of the unit delegation in work/native-identity/pseudocode3.txt;
pseudocode4.txt:510-866, especially the final CONCAT44 write.

4. Identity allocation for a new unit
The army ctor0x1a21a0 first calls the shared unit ctor0xd3b0a0.
0xd3b0a0 first runs the default initialization 0xd3acd0, then:
  type = 0x36;
  id = 0x771be0(world_global, 9, 0xffffffff, ...)
  if id==0 the whole identity is set to 0; otherwise it is joined as CONCAT44(id,0x36);
  0x14cf190(army+0x10, &identity, 0) registers it in the native object table.
The default initialization sets army+0x20 to the global null ID (RVA0x233fea8) and clears the registration flag at army+0x28.
army+0x28 is a boolean registration state; it cannot be used as a generation.
Evidence: the two ctors at the end of work/native-identity/pseudocode3.txt.

The 0x771be0 allocator:
  world+0x2508/0x2510/0x2518 is a vector of 32-bit counters; argument 9 selects the matching counter;
  argument 0xffffffff means take the current counter and add 1 to the counter;
  with an explicit candidate ID, it updates the counter to the upper bound; on reaching -1 it throws "ID range overflow".
This supports the conclusion that "normal creation allocates increasing sequence numbers". This round did not trace every save/load and reset path of the counter vector,
so it cannot be claimed that IDs are never reused across all exceptional, scripted and third-party-modification cases.
Evidence: work/native-identity/pseudocode4.txt:1030 onwards; string RVA0x1cb1298.

5. Registration and conflict handling
Before assigning, 0x14cf190 calls 0x14cf730 to look up the same ID; for an existing ID it logs:
  "Failed to create id ... Already exists in game." (source file clausewitzlib/id.cpp)
Low types and high types have different conflict branches; a generic high type can be given a new generic number.
On success it writes the object into the native table indexed by type and id, and sets the registration flag.
The function does not read any separate generation field for the lookup or the write.
So after reading the full ID, uniqueness still has to be checked: the target army must exist exactly once, be a player land army and belong to the current session.
Do not accept it because the low-32-bit type matched, and do not ignore a collision log/registration conflict and go on restoring the mission.
Evidence: work/native-identity/pseudocode4.txt:868-1028.

6. Adapter recommendations and limits
Persistence:
  StoredArmy.armyKey = the full native 64-bit ID.
  StoredArmy.generation = 0, until there is independent, reliable evidence of a persistent generation; do not use raw addresses.
  Restore must first be tied to the exact slot + full save hash, and after loading look up the unique player land army again by the full ID.
  This round cannot guarantee that this reload mapping has been verified in the actual game.
At run time:
  Every load/return to the menu switches session and clears the old pointers and targets; when an object disappears, its mission is closed.
  In-session pointer/instance tracking can also be recorded to detect changes, but it cannot serve as a generation that persists across loads.
  Even if the ID is kept, the lifecycles of splitting, merging and change of control need handling separately.
Object type:
  0x36 comes from the shared unit ctor; this round did not prove that it belongs only to land armies. The land army vtable/type check must stay,
  and fleets must not be brought into regional land combat on type54 alone.
  owner+0xd0, for example 0x010000b900534143, is a separate representation of country identity, with CAS visible in the low bytes; it is not an army generation.

Minimal runtime verification checklist (not run)
1. Record one army's full ID and land army type, save, return to the menu, load the save with the same hash, and check that the ID is the same and unique.
2. After creating/splitting, check that the new army gets a different full ID and the original army's ID is unchanged.
3. After a merge, check that the main army's ID is kept and the merged-in object is gone; on capture/change of control, check player ownership again.
4. Destroy an army, then create a new one, and watch whether the counter increases and the old ID disappears; do not compare object addresses only.
5. Armies with the same name, armies of the same type, and different saves that happen to have the same ID must not be restored across saves; the exact hash/session check must pass first.
