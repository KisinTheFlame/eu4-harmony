Current player's vision: the complete static chain from the console FOW entry to the province cache and the unit tooltip
2026-10-26. Approved baseline SHA256: 97dd63a811487fbe2c917f2c15b1e68f7222bef74a833889cf943c8010049d5e.
All addresses are RVAs. Only the frozen exe was analyzed; no running game process was attached to, read or manipulated.
This report supplements and updates the "FOW not yet located" conclusion of native-hostility-findings.txt.

Result
There is now direct static evidence for the native fog-hidden cache of the current player:
  bool FogHiddenForCurrentPlayer(Province* p) {
      return (read_u8(p+0x959)&0x20) != 0 && (read_u8(p+0x958)&0x02) != 0;
  }
This is not a camera viewport filter, not the separate bitset of discovered provinces, and it does not require calling a native function.
0x8275e0 recomputes these caches with the effective player's CountryTag; the unit tooltip0xd47780 filters enemy armies with the same expression.
When the target belongs to this world, the player tag and the latest completed vision refresh, FogHidden=false for the province a non-own army is in is the static basis for it being visible under native FOW.
This answers only for "the current player"; you cannot pass an arbitrary country tag to query another country's vision. The cache update timing and the country-switch/load boundaries have not been verified at run time yet.
Before the main adapter goes live, passive observation should confirm: FOW on by default, results for nearby and distant provinces, refresh as the game normally advances, and invalidation on country switch/load.

Evidence 1: the console fow messages clearly tell the two bits apart
string 0x1d2ef60="Fog of War is now ON.", 0x1d2ef78="Fog of War is now OFF.".
The function that references both, 0xe7a990, is the fow console handler (do not call it as a query).
Without arguments it calls 0x76ed60(world,!world+0x23a6), then picks the ON/OFF message by world+0x23a6.
0x76ed60 goes through the province pointers in world+0x1c90..0x1c98, updating province+0x959 bit0x20 on each, and writes world+0x23a6.
So province+0x959 bit0x20 is the FOW enable switch; it cannot be used on its own to decide that the province is hidden.
With a province argument, the handler checks the conjunction of the two bits above, then calls 0xa0b150(province,1 or 0) and prints the FOW on/off message for that province.
0xa0b150 sets province+0x958 bit0x02, and +0x228 bit0x04 of mapdata=*(province+0x28), to match the argument.
On a change, it puts mapdata+0x154 into the +0x340 queue of the render object linked at province+0x2d8, and sets the +0x338 refresh flag.
This setter really does write state; it may only be observed passively and must never be called as a visibility query.
Evidence: work/native-hostility/fow1.txt, fow2.txt.

Evidence 2: the visibility calculation is explicitly tied to the effective current player
At entry 0x8275e0 reads world=*(base+0x233fe78); the effective tag rule is the same as in 0x811b20:
  byte(world+0x1e66)==7 && byte(world+0x1e6f)!=0 ? qword(world+0x1e68) : qword(world+0x1e60)
The normal country/FOW mode branch allocates a temporary byte array over the provinces, all initially hidden=1.
Provinces the country owns or controls, and their adjacent provinces, are cleared to zero; the country relation helper0x3bb250 takes part in filtering for shared vision.
It then walks the armies country+0xd18 of the countries that meet the relation, clearing by each army's current province army+0xe8 and its adjacent provinces.
There are also affiliation/special army/relation paths; this implementation does not need to copy these rules and consumes the native result directly.
Finally it scans the provinces at world+0x1ca8, stride0x2e10; no case was found of a province being forced hidden by the country bitset at province+0x5e0.
For entries that changed it calls 0xa0b150(province,newHidden). So the discovery bitset and the current FOW cache really are two different layers.
Branches such as FOW off or no valid observable country clear hidden on every province; the adapter needs to verify a controllable player separately, rather than treat an observer's whole-map vision as a valid mission identity.
The function allocates a temporary array and writes the cache; it must not be called actively on a worker thread. The refresh epoch and the effective tag can be recorded in onLeave of the native call.
Evidence: work/native-hostility/fow3.txt, ADDRESS1408275e0.

Evidence 3: direct consumers keep hidden armies from being shown
The province info function 0xa075a0 returns the localisation key CANT_SEE_UNDER_FOW (string RVA0x1cd9270) at once when the two-bit conjunction holds.
Army main vtable+0x18 ->0xd47780 is in fact unit tooltip generation, not a daily tick.
It enumerates the unit linked list of its province (province+0x350; payload+0,next+0x10) and, when the two-bit conjunction is true, skips units whose owner is not the effective player.
There are other checks too, such as telling armies from fleets by terrain, and empty regiments. So being visible under FOW does not mean every unit can be chased by a mission; separate conditions such as hostility/land/current-state are still needed.
This generator allocates text and reads the whole tooltip, so it should not be called as a query; the observer only listens at the entries of native calls.
Evidence: work/native-hostility/fow2.txt, ADDRESS140a075a0 and 140d47780.

Minimal usable read-only adapter contract (awaiting runtime verification)
  1. Confirm the current session/world, the controllable effective player tag and army ownership.
  2. Build the snapshot only at a stable moment on the native game thread; borrowed pointers must not be kept across a load.
  3. Confirm from the latest completed 0x8275e0 refresh that world/tag match; on country switch, on load, or while a refresh is in progress, invalidate first.
  4. EnemyArmy's province is taken from army+0xe8; read the cache above once the province id matches the snapshot graph.
  5. If FogHidden=true, exclude it. false only passes the FOW condition; it does not replace hostility, access, mission range and army state.
  6. A native UI exception lets the player's own armies show under fog; automatic missions looking for enemies should not copy this as "any own army can be attacked".
  7. This function uses the native FOW switch directly; if the user turns FOW off themselves, the native visible range grows. The tool does not change the switch on its own.
Cache freshness is still a condition for integration: one past refresh on record with the same world/tag cannot prove the current state indefinitely. Consume the cache along with the native refresh epoch, and check the timing against the native daily advance.

Passive verification tool
tools/native_fow_observer.js: a Frida script; it matches only /work/game-stage/eu4.exe and checks the prefixes of 3 entries.
At entry 0x8275e0 it records the refresh completion epoch/world/tag; at 0xa0b150 it records the bits before and after, and the caller, for the first 32 setter calls; at 0xd47780 it records the army/province of the first 12 tooltips.
For the first 8 completed refreshes it outputs the hidden count over all provinces and samples of the default provinces 149/151/4703; what is visible on screen is not taken as the FOW verdict.
RPC status() gives the counts and the epoch; samples([province ID...]) takes at most 32; snapshot() only reads the current cache; dispose() removes its own hooks.
resetlog() only resets the observer's counts and does not change the game. It does not call NativeFunction, console commands or game data writes.
The script has only passed a syntax check with node --check; it has not been attached and run yet. First check the full baseline hash with inspect_baseline.py; the entry prefixes are no substitute for the identity of the whole file.
Suggested: first observe the values while paused, then check the updates after game time advances normally/armies move; confirm the difference between provinces next to the current player's home territory and distant unknown provinces.
If there is no refresh callback, the initial lastCompleted=null must not be dressed up as a verified completion; passive observation of the known native UI refresh paths can continue, but calling the setter at will for testing is forbidden.
