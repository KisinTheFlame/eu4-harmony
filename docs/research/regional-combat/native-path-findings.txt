Conclusions
1. 0x14096C520 is a search with variable edge weights, a heuristic and policy virtual functions. It is not a BFS for the fewest province steps.
2. Its normal output list can describe the route actually chosen, but count is only the number of edges in that weighted route. It cannot stand in for a proven shortest hop distance.
3. 0x140D50340 is a void path submitter. It may reject early, and it may copy only an adjacent, legal prefix. The army's path after submission must be observed; "the function returned" must not be taken as Accepted.
4. The normal move policy and the vanilla rebel-hunting policy are different vtables. The rebel-hunting policy adds strength checks, so it cannot be reused as is to get "ignore the odds of winning".
5. A passive observer script is provided at work/native-path/observe-path.js. The parent task ran the first version and recorded the real normal policy and the path copy; see section IX.

I. Machine-level ABI of 0x14096C520
Return value: a boolean success value in AL. The other bits of RAX must not be used as the result.
Windows x64; RSP at entry is called S:
  RCX / arg1: policy object Policy*; its first word is the vtable.
  RDX / arg2: Army/Unit*.
  R8  / arg3: origin Province*, the first node of the search.
  R9  / arg4: goal Province*, passed to the goal predicate and the heuristic.
  [S+0x28] / arg5: PathList*, may be nullptr.
  [S+0x30] / arg6: Options*, read up to at least +0x40.
  [S+0x38] / arg7: no read before a write was found. The entry zeroes its low 32 bits, then uses it as scratch for an exception-cleanup bitmap.
  [S+0x40] / arg8: optional visited-byte-buffer*, may be nullptr.
So the bridge's declaration should keep all 8 ABI slots: pass 0 for arg7, and nullptr for arg8 when it is not needed. Do not declare the function from the six-argument call shown in some of the pseudocode.

Direct evidence:
  prologue: 0x14096C53A sub rsp,0x200, after 7 pushes; 0x14096C541 rbp=rsp+0x40, so rbp=S-0x1F8.
  0x14096C561 reads [rbp+0x228], that is arg6.
  0x14096C598 reads [rbp+0x220], that is arg5.
  0x14096C555 writes [rbp+0x230], that is arg7; after that it is used only as an internal bitmap.
  0x14096CE39 reads [rbp+0x238], that is arg8.
  The rebel-hunting callsite 0x1401C87D5 writes [rsp+0x38]=0 before the call, that is the callee's arg8; the arg7 slot is not initialized.

II. The policy interface and how the policies differ
Normal policy vtable: 0x141C3AF98
  +0x00 0x1400D0210: destructor entry, not expanded in this round.
  +0x08 0x14096F860: 7-argument edge feasibility predicate.
  +0x10 0x14096F510: 5-argument check that the origin/goal can be entered.
  +0x18 0x14096FD50: goal predicate; it only compares the pointers target == candidate (49 3B D0 0F 94 C0 C3).
Vanilla rebel-hunting policy vtable: 0x141C3AF78
  +0x00 0x1400D0240
  +0x08 0x140970F60: calls the normal edge predicate first, then adds checks on strength, enemy armies/fleets and so on.
  +0x10 and +0x18 are the same as in the normal policy.
The rebel-hunting policy object also has a one-byte switch at +8, initialized to 0 in 0x1401C8420.

Edge predicate ABI (0x14096F860/0x140970F60):
  (Policy*, Army*, goalProvince*, currentProvince*, adjacentProvince*, adjacencyRecord*, Options*) -> AL bool.
  The register/stack assignments at 0x14096CC5A..0x14096CC7A prove this argument order.
Initial predicate ABI (0x14096F510):
  (Policy*, Army*, originProvince*, goalProvince*, Options*) -> AL bool.
  When opts+2 is 0, it calls army vtable+0x120(goal, ..., tag@opts+0x14, ..., ptr@opts+0x38).

Besides the normal legality checks, 0x140970F60 compares goal+0x590 /10 with regiment count*1000, and in some type branches calls 0x14096FD60 and 0x1409713D0.
0x14096FD60 enumerates the armies in the province and adjacent provinces and computes a ratio threshold. So "no threshold on the odds of winning" at least cannot be had by just choosing this rebel-hunting policy.
This does not mean the normal policy has been verified at run time: it still contains checks for normal movement, access, special types, sea-land transitions and path history.

IV. List format and return semantics
PathList object:
  +0x00 head node*; +0x08 tail node*; +0x10 signed int count; +0x14 mutation/deferred-delete flag.
Node size 0x20:
  +0x00 int payload; +0x08 prev*; +0x10 next*; +0x18 deleted/tombstone flag.
Normal mode (opts+0x40==0):
  0x1400E9720 walks the predecessor chain back from the goal and push_fronts province IDs, for now including the origin;
  at the end of the search, 0x14096CE31 calls 0x14010C9B0 pop_front, which removes the origin.
  The output order is next stop -> ... -> goal; count is the number of edges in this chosen path.
  When the origin is the goal, it can return success with count==0; count==0 alone cannot tell you that the search failed.
  The fast one-hop success pushes the goal ID directly and returns true.

Chain length encoding mode (opts+0x40!=0):
  0x1400E9850 counts the vertices in the predecessor chain, 0x1400E9720 makes two nodes holding the same number, and one is popped at the end, leaving a single node.
  payload=number of vertices in the path, that is the chosen path's hops+1; not a province ID, and not the list count.
  Note in particular: the opts+8 fast one-hop path bypasses this logic completely and still outputs a province ID. So turning both switches on at once leaves the payload without one consistent meaning.
  This mode is not suitable for handing directly to 0x140D50340.

All the lengths above refer to the route the weighted search chose; it is not proven to be the shortest-hop route.
outList must be managed under allocation/free rules compatible with the game. The search does pop_front, so do not pass in a list that is non-empty by accident.
Temporary nodes are allocated by 0x141A332D4(0x20) and freed by 0x1417394F0(node,0x20). The parent mission tick frees the original temporary list after submitting, which shows that the submit function copies the nodes rather than taking over the temporary list.
visitedMask(arg8) receives a copy of the closed/visited byte array indexed by province ID; its length comes from the element count of gameState+0x1C90..0x1C98.
The search stops early once it finds the goal, so visitedMask is not the full reachable set; the fast one-hop success does not even go through the copy at the end.

V. Search cost: clearly not hops, and not to be claimed as the shortest pure travel time either
The 0x14096BD00 edge cost takes the int at adjacencyRecord+0x0C as its base and adds country/control/zone-type/policy penalties, with values such as 2000, 8000, 24000, 32000, 160000, 200000, 400000.
The 0x14096C400 heuristic comes from the distance between the provinces' map coordinates, including horizontal map wrap-around, then scaled in fixed point.
0x14096CC9D..0x14096CD3F: gChild=gParent+edgeCost, fChild=gChild+scaledHeuristic, pushed into the priority queue.
So it is at least a route weighted by "map distance base + strategic penalties". This round did not prove that the edge base equals the real marching time.
The 10x heuristic of opts+7 also means the result cannot be called a strictly optimal cost without proof.
Core's ExactRoutes needs the fewest legal province steps; this function's list count, as is, cannot meet that contract.

VI. Path history, and the facts a snapshot must include
0x140D45250(army,candidate,current,opts+9) reads:
  army+0xE8 the current province, +0xF0/+0xF8 two history/return-context province pointers, +0x100 the actual existing path;
  when opts+9 is non-zero, it copies the current path and analyzes it in reverse, adding the army's current province when needed; it also calls functions about province forts/country relations.
So changing only pathfinder arg3 to a fixed center does not set up the full context of "the army imagined as stationed at the center"; army still points at its actual location and history.
You cannot ask each edge once, true or false, in the current army's context, piece the answers into a static graph, and claim that settles all path history.
Until a real center path context and a fewest-hop search method have been recovered, production ExactRoutes should stay Unavailable rather than pass off a weighted route length as the answer.

VII. The minimal submit shape of 0x140D50340, and confirmation
ABI: (Army* rcx, PathList* rdx, uint8 replaceExisting r8b, uint8 fourthFlag r9b) -> void.
Vanilla automatic rebel hunting calls: submit(army,&temporaryPath,1,0).
A non-zero replaceExisting clears the old army+0x100 path and resets related state. The fourth flag can trigger extra mission handling; its meaning is not fully known, so do not set it to 1 casually.
At entry, if army+0xC0 is non-null and its virtual function +0x70 returns false, the whole update body is skipped.
The update body starts from the end of the existing path or from the current province and walks the IDs passed in. For each one it looks up the adjacency record and copies it to the army+0x100 path. It stops at the first ID that is not adjacent, and may keep the prefix.
The function also clears or changes several army missions and the state of attached units. It is in no way a side-effect-free "validate path" function.

The minimal verifiable evidence for Accepted should be:
  1. Submit on the same game thread, in the same session, with the same full ArmyKey, after confirming the snapshot is still valid.
  2. Read army+0x100/+0x108/+0x110 and confirm the full expected path and the final goal. If only a partial prefix was updated, treat the expected order as not done.
  3. During the check, do not reuse unconfirmed pointers across saves or across army rebuilds.
  4. A zero-edge path, where the current province is already the goal, needs its own check; it is not required to produce a non-empty path.
  5. The native call for Stop, and the criteria for movement lock/combat/retreat, still need checking in a run by the parent task. Submitting an empty list must not be passed off as a verified Stop.
The vanilla mission tick returns at once in cases such as army+0x110 being non-zero or +0xC0 being non-null, so this idle-only call path alone cannot be used to infer all the rules for changing orders while marching.

X. Can a custom policy give the fewest hops? Conclusion from static evidence
This section only examines the existing machine code and decompilation; no patching, process calls, object cloning or run-time injection.

Conclusion: the normal policy's four-slot vtable cannot override the edge cost or the heuristic, and the existing options have no provable mode with cost=1 on every edge and heuristic=0.
You cannot keep the existing admission rules while switching to BFS by "copying the normal policy vtable and replacing only the cost/heuristic slots", because those two slots do not exist.

Normal vtable VA 0x141C3AF98 (RVA 0x1C3AF98 verified in the run log):
  +0x00 -> 0x1400D0210: destructor.
  +0x08 -> 0x14096F860: edge admission, including checks on the actual army context and path history.
  +0x10 -> 0x14096F510: admission at entry for origin/goal.
  +0x18 -> 0x14096FD50: goal pointer equality test.
The search loop dispatches the edge cost with a direct call:
  0x14096CC9D puts Options* in the 6th argument slot; 0x14096CCA2 puts adjacencyIndex in the 5th argument slot;
  0x14096CCA7 R9=currentProvince, 0x14096CCAB R8=army, 0x14096CCB2 RDX=&cost, 0x14096CCB6 RCX=policy;
  0x14096CCB9 CALL 0x14096BD00 (a direct address, not CALL [vtable+slot]).
The matching ABI is int* edgeCost(policy, int*outCost, Army*, currentProvince*, uint32 adjacencyIndex, Options*).
The policy parameter takes RCX but is not used for vtable dispatch. At 0x14096BD0F the function stores it in its home slot; later that stack slot is used as the buffer an army virtual function writes a tag into.
The CALL [R8+0x138] at 0x14096BDEC is an army virtual function: R8 is loaded from [army] at 0x14096BDDE, and RCX=army. Do not mistake it for a policy cost callback.
0x14096BD65 reads the base from adjacencyRecord+0x0C; after that the cost is modified depending on terrain/country/control/zone/army and the options.

The heuristic is also dispatched with a direct call:
  0x14096CCC8 R8=candidateProvince, 0x14096CCCB RDX=goalProvince, 0x14096CCD2 RCX=&heuristic;
  0x14096CCD6 CALL 0x14096C400.
Its ABI is int* heuristic(int*out, goalProvince*, candidateProvince*), with no policy argument.
0x14096CCDF checks opts+7; the non-zero branch uses 10*h, the zero branch computes 900*h/1000 starting at 0x14096CCEF.
0x14096CD2F adds edgeCost to parent.g; 0x14096CD39 then adds scaledHeuristic to form the queue priority.
So even if only the edge cost were changed to 1, the directly called map distance heuristic would also have to be turned off to guarantee the fewest hops.

How far the options could serve instead:
  +0x05 only changes some zone/type transition branches; some of them can return 0 or add 400000. It is not a constant weight over all edges.
  +0x10 adds 8*value only when a particular army predicate holds; it cannot cancel out each edge's different base and conditional penalties.
  +0x07 is the 0.9/10x choice; it has no value that turns the heuristic off.
  +0x40 only changes the final output encoding; it still searches the same weighted path.
No switch was found that gives constant weights through a per-call private Options object alone. Do not take this as a reason to try changing the global adjacency bases or coordinates to get this behavior.

The definition of the fixed-center pathstate is still to be settled:
A. If it is defined as "the army imagined as stationed at the center, with no existing march path", then a legal and consistent current province, history/return provinces and queue context must be set up for the center. Changing only the origin argument, as now, does not do that.
B. If the army's actual current location, history and existing path are kept and only origin is changed to the center, the result is a mixed-context query. It changes as the real army marches, and cannot be called the range of an army imagined as stationed at the center.
This section does not choose or fake army+0xF0/+0xF8 values before their meaning has been recovered.

A separate fewest-hop search can reuse the native admission rules only once "the admission state and how it changes along each path" has been recovered correctly.
Calling 0x14096F860 for each pair of provinces while always passing the same real army object is not enough to show that all history dependencies hold; that interface does not explicitly take the imagined history of the search node.
The next minimal static task should focus on the logic that produces/updates the history values 0x140D45250 reads, and pin down the center root state and the step state. Until then, production ExactRoutes stays unavailable.
This conclusion does not mean the enhancement cannot be built. What it rules out is the shortcut of swapping weights through the policy vtable alone, without recovering the path state.

3. The strait through field is not a path node to strip
When 96C520 expands adjacencies, it takes the province ID at record+00, resolves the candidate with province stride0x2E10,
and stores this candidate and its predecessor; in the end 0E9720 outputs each predecessor's province ID.
The through sea zone at adjacency record+08 is not inserted into the output chain here.
So the sea zone metadata of a land→land strait does not make this module reject a normal land chain. If the real output chain does contain a sea zone,
you cannot delete it, join up the land on both sides, and claim a legal native route. Nor can opts+01 be used as a no-transport switch,
because it rejects type1 adjacencies, which include land straits that must be kept.

4. The conservative contract that can be implemented now
For each goal, first verify the full output chain, the endpoints and each province's real geometry, then decide whether automatic missions may use it.
  - Native returns false: no route steps for that goal.
  - Native returns true and the whole chain is land: keep the original hop count.
  - Native returns true and the chain contains non-land: result reason=chosen_route_non_land, native_reachable=true,
    reachable=false and no steps; all nodes are freed along the original chain. This goal goes into unreachable, so core skips it conservatively.
    This means "the native route chosen this time does not meet the no-transport requirement", not that no other legal all-land route exists.
    It does not rewrite the policy, strip nodes or transport automatically, and does not claim to have found a new optimal land route.
  - Unknown province, unreadable geometry, broken chain, wrong endpoint, world/army changed, or failure to free: the whole batch fails.
    Even after a non-land node has been met, verification continues to the end, so that a later ABI/memory error is not hidden as the candidate being unreachable.
A sea zone in the chosen route of a single goal no longer invalidates all the other legal candidates and the geographic range preview.
core routes.complete now means "every decision goal has had its chosen route classified for usability";
it gives no proof of reachability for goals not queried, and proves neither the shortest hops nor the non-existence of an alternative land route.

5. Bounded diagnostics for the next live run
routes.rejections holds at most 8 entries, plus the actual rejection_count; the fields are goal, origin, offending_province,
path_index, previous, next, path_length, flags228, flags229, list_flags, policy_rva,
options_09, options_40, native_success and cleanup_confirmed. Neither the full path nor any partial enemy-army scan content is returned.
A successful snapshot puts them in evidence.route_rejections; a failed snapshot uses route_diagnostic.query/rejections.
