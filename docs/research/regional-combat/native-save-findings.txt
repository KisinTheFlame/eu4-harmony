Save/load lifecycle candidates: targeted static reverse engineering
Date: 2026-10-26
Target: the frozen copy of the specified unrestricted exe, SHA256
97dd63a811487fbe2c917f2c15b1e68f7222bef74a833889cf943c8010049d5e.
All addresses are RVAs; a runtime address is the actual module base plus the RVA.
This round read only the manifest and the program bytes, with targeted decompilation in Ghidra 12.1.4 under work/native-save.
No running game process was attached to, manipulated or read. No hook was installed or written.

Conclusions
Found candidates for the save dispatch, the final file move and load completion, usable for controlled runtime probes.
The third party's existing save_result == 0 alone does not prove that the final .eu4 file was replaced: the local save functions
do the .tmp -> .eu4 rename only after setting the serialization result, and the rename-failure branch shows no correction of that return value.
Externally stored configuration must not, on hearing only this return value, bind the "current configuration" to a save on disk that may still be the old version.

1. Seeds from the third-party manifest, and an independent byte check
Original manifest: unrestricted/patch-manifest.json, historical_metadata.native_hooks.
menu_save_call  0x815cc3: e8 38 ae dc 01 -> 0x25e0b00.
save_result_call 0x5cbec3: e8 38 4d 01 02 -> 0x25e0c00.
The actual bytes at both sites match the manifest's after; the check is recorded in work/native-save/manifest-hooks-verified.json.
The manifest's symbol names were used to find seeds; the behavior below was confirmed independently by targeted decompilation of the specified baseline.

2. Start of a save: preferred probe candidate 0x5cbde0, range [0x5cbde0,0x5cbed6)
The argument RCX is seen to point to a save request object. It first records and sets a pause/scheduling flag, then dispatches:
  request+0x20 == 0 and request+0x21 == 0 -> 0x5c6500;
  request+0x20 != 0 and request+0x21 == 0 -> 0x5c7ac0;
  other combinations, after a network/service availability check -> 0x5c8ba0; it may return 4 when the service is unavailable.
When request+0x40 is non-zero and the result is non-zero, it calls 0x5cb110 for error handling.
It then restores the pause/scheduling flag it had on entry, calls the third party's capture_result at 0x5cbec3, and finally returns that result.
0x25e0c00 is an 11-byte trampoline: it stores EBX at RVA 0x26cc010, then tail-jumps to the original function 0x4708d0.
From this context 0x4708d0 is a function that propagates pause/scheduling state; it should not be misnamed a "save completed function".
Evidence: work/native-save/pseudocode1.txt:1586-1646 and after 1869; the manifest and the actual call bytes.

Candidate layout of the save request object:
  +0x00..0x1f the save name, an MSVC std::string-like object;
  +0x20..+0x26 several flags for save mode, compression and so on, not yet named one by one;
  +0x28 candidate vector of path components; +0x40 candidate switch for error messages.
Basis: 0x5cbee0 builds this object and calls the dispatch function at 0x5cc04e; 0x5ca070 builds the final virtual path from the name,
the path components and the .eu4 suffix. request+0x00 cannot be taken directly as an absolute disk path.
Evidence: work/native-save/pseudocode3.txt:484-732.

A scan of raw E8 bytes found candidate call sites of the dispatch function:
0x5cace8, 0x5cc04e, 0x5cc615, 0x5cca17, 0x5ccc18, 0xe95e5e.
Of these, 0x5cc04e is confirmed by decompiling its containing function; the rest are only leads for targeted probes, and the list is not claimed to cover every call.
Scan record: work/native-save/direct-call-candidates.json.

3. The menu wrapper does not cover all saves
0x25e0b00 stores the third party's own idler/world/date, sets result to -1, then calls 0x5cc160.
0x5cc160 first checks world+0x24d0 and returns at once if it is 0; from the context this is inferred to be the Ironman path.
The third party replaced only the one call at 0x815cc3 in the menu with this wrapper; the other native direct save calls are still there.
So 0x25e0b00 cannot serve as one snapshot entry for ordinary saves, Ironman saves and autosaves.
Confirmed third-party state:
  world global pointer RVA0x233fe78; world date field +0x1dd0;
  third-party save_idler RVA0x26cc000; save_world +8; save_result +0x10; save_date +0x14.
The return-to-main-menu logic at 0x25e0200 checks that idler/world/date match and result==0; this is only its guard on leaving,
not the full-content hash, final slot and persistent army identity binding the current enhancement needs.
Evidence: work/native-save/pseudocode1.txt:1651-1849.

4. Writing local saves to disk and the final rename
0x5c6500 candidate for ordinary local saves; 0x5c7ac0 candidate for local Ironman saves.
Both build a .tmp path, call 0x74ba20 to serialize world, check the length/result, PHYSFS_close,
deal with backups/existing files, then call 0x1715bb0 to move the final file.
Serialization call sites: 0x5c68e6 (in 0x5c6500), 0x5c7ea4 (in 0x5c7ac0).
Final .tmp -> .eu4 call sites:
  0x5c7888 -> 0x1715bb0 (in 0x5c6500);
  0x5c88ef -> 0x1715bb0 (in 0x5c7ac0).
0x5c76ab also calls the same move helper, but for another backup move; it cannot be generalized to mean the final save is complete.

0x1715bb0(src,dst) uses PHYSFS_getRealDir, UTF8->UTF16 and GetFullPathNameW,
and calls 0x1a5ed40 to do the actual move; when that returns 0 the helper returns low byte 1, otherwise it returns 0 and logs an error.
It is a candidate for a passive probe that filters on the return address to pick out the two call sites above; not every call to it is a save.
Evidence: work/native-save/pseudocode3.txt:737-1124; save-io-call-candidates.json.

Important limitation:
0x5c6500 has already set the return result to 5 or 0 at decompiled lines 310-312; 0x5c7ac0 does the same at lines 1017-1019.
The final rename-failure branch prints "Failed to rename new save file" or "CRITICAL SAVE ERROR",
but is not seen to update the return result the save dispatch receives. So result==0 at most stands for the save result it reports;
it still needs verification that the final move succeeded, the target file is closed and the snapshot is correctly linked, and cannot by itself grant Commit::Confirmed.
Evidence: work/native-save/pseudocode2-annotated.txt:310-317, 636-689, 1017-1024, 1218-1272.
This conclusion comes from local static data flow; it has not been proven with a real disk-failure scenario, and the original program's error handling was not changed.

5. Load candidates
0x5cdc60 is a useful point for observing a load's call and return:
  arguments RCX=reader candidate, RDX=success-byte output pointer, R8=world candidate, R9=progress-related argument;
  on entry it first writes *RDX=0 and starts a helper thread named SaveSessionUpdateThread;
  it lays out {world, reader, success_ptr} on the stack and calls 0x5cf740 synchronously at 0x5cdd58;
  before returning it joins the helper thread; finally it returns the success pointer.
Evidence: work/native-save/pseudocode3.txt:3-109; name string RVA0x1c8cb10.

0x5cf740(task) is the candidate for the body of loading and initialization, range [0x5cf740,0x5d01b0).
  task[0]=world, task[1]=reader, task[2]=success-byte pointer;
  if getting the gamestate data or parsing fails, it writes *task[2]=0 and returns;
  the branch that loads compressed saves handles meta and AI;
  after a successful parse it sets the save name at world+0x2430 and the path components at world+0x2450;
  it calls 0x7751b0 to initialize the world, then cleans up local objects, and finally writes *task[2]=1.
0x7751b0 is the source of "Initializing savegame"; it walks the world structures doing post-processing, which is not the same as the whole UI being ready.
Evidence: work/native-save/pseudocode2-annotated.txt:2260-2625 and after 2626.
The successful-return candidate can be used to create a new session and then attempt a restore; only once the adapter can produce a complete world snapshot
with consistent identity may army tasks be restored and orders issued. *success==1 alone does not prove that all UI has been rebuilt.

6. Minimal plan for later runtime verification (a design, not a connected implementation)
A. Only observe entering/leaving 0x5cbde0: record the thread ID, request flags, length-limited name/path components,
   the world pointer, date and return result; verify whether ordinary/Ironman/autosaves are covered and whether the world stays still meanwhile.
B. For 0x1715bb0, record the arguments and low-byte return value only when the return address is 0x5c788d or 0x5c88f4,
   and not unrelated file moves; check the final path, how an existing file is handled, and the success or failure result.
C. On entering/leaving 0x5cdc60, observe world, the success output and the slot identity, then wait for a complete world snapshot.
D. Only when A/B have proven that the current save snapshot matches the task configuration and the final slot was really committed may the full SHA256 of the locked
   file be computed and the externally stored state committed. On failure, a cloud save with no definite local file, an abnormal exit, or an identity
   that cannot be proven, write no state. Never bind on matching date/mtime/name alone.
E. Detect session changes around a load; look up externally stored state by slot+hash, then verify the armies' persistent identities and generation.

Unresolved
The exact meaning of each mode's flags, the mapping from virtual paths to local/cloud saves, syncing the task configuration snapshot during a save,
where persistent army IDs/generation come from, full coverage of asynchronous saves and autosaves, actual save-and-reload for ordinary/Ironman,
and actual compatibility with going back to vanilla. None of the entries above may bypass these preconditions to claim the save hook is done.
The latest-save refresh wrapper 0x25e1600 only refreshes a front-end cache (it calls 0x17139c0/0x212810),
and should not be taken as an event for a successful save or a finished world load.
