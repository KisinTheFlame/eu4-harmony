# The main menu (for `game::menu`)

Baseline 1.37.5. All addresses are RVAs. Found by reading eu4.exe on 2026-10-29 (disassembly, and Ghidra's decompiler on single functions without analysis); what was checked in the running game is marked "tested", and the runs are in [prototype-log.md](../prototype-log.md) (2026-10-29, remote control C5). See also [safe-points.md](safe-points.md) and [notice-window.md](notice-window.md) (the main menu object and its frame).

## The main menu object

- **Class and frame**: vtable `0x1d5a8c8`; its frame `0x10d2e80` (`rcx` the object) runs on every page. It is also the current idler while it shows: the start command reaches it through `world+0x1e00` (below). That slot is set by `0x756a30(world, idler)`, which the main menu calls when it shows (`0x10d5c4d`) and the game idler's constructor `0x803270` calls with the new map manager (`0x80a00c`): so once a game is made at the start, `world+0x1e00` is no longer the main menu, though the main menu still shows until the idler switch. Tested: in the frame the game took over in, the main menu's frame still ran, and none of the start's flags read as set any more.
- **Pages**: the page shown is the u32 at `+0x900`; the pages are an array of pointers at `[+0x8e8]`, by page number, each pointing to the page's interface. `0x10daf60(main menu, page, animate)` shows a page: the old page's interface method `+0x18` (leave), then the new one's `+8` (enter), then, when `animate` is set, its `+0x10`. Page 0 is the first page; 3 is the single player setup; 4 the multiplayer lobby.
- **The application** is at `+0x330`. Its idler switch: `0x14c2530(application, &idler, keep)` sets `application+0x48` (pending) and keeps the new idler at `+0x70`; the application's frame `0x14c25a0` switches when `+0x48` is set (notice-window.md).
- **Starting a game**: `+0x714` (u8) is set by the main menu's method `+0x320` (`0x10dc290`), which the single player setup's start command calls when it runs (`0x738f10`, the command's execute, through `world+0x1e00`). The single player setup's frame (`0x1117670`, its interface's `+0x20`) then calls `0x1120dd0`, which sets `+0x715` (u8). The main menu's frame calls `0x10da520` every time (`0x10d3c55`); with `+0x715` set it logs "Launching SINGLEPLAYER-game" and the start date, makes the game idler (`new(0x5bc8)`, `0x803270`) and queues the switch through `+0x330`. So "a game is starting from the main menu" is any of the single player setup's `+0x2cb0` while it shows (below), `+0x714`, `+0x715`, `application+0x48`, or a save being read. The start command's execute calls `+0x320` whatever the setup's state, so once it runs `+0x714` is set. The main menu's constructor clears `+0x714` and `+0x715` (`0x10d258e`, one word for both); no later write that clears them was found, so the game leaves them set until the process ends. The single player setup's frame tests `+0x714` (`0x11192d5`, `cmp byte [rax+0x714], 0`): entered again while it is still set, the setup carries out the accepted start at its first frame. So when `game::menu` gives up a load or start, it clears `+0x714` itself, as the constructor does, unless `+0x715` is set and the start is to happen at the main menu's next frame. Not tried in the game: no run left an accepted start untaken.

## The single player setup (page 3)

- **Class**: `gamesetup.cpp`; the page object's vtable `0x1d5e278`, its interface (what the pages array holds) `0x28` bytes into it with vtable `0x1d5e320`, its main menu at `+0x30` (constructor `0x1108700`, `0x11087b0`).
- **Entering it** (`0x110dda0`, the interface's `+8`): in single player (`world+0x747c` 0) it sets up a session and the setup's windows; unless `main menu+0x910` is set (continuing, below), when the text at `0x1fd39a8` (a `std::string`) is not empty, it finds that tag (`0x286120`, the country manager's lookup by letters), selects that country (`0x111cb80`), empties the text and starts the game (`0x1120280`). That text is the `-start_tag` launch option's (read in `0x8757e0`; the main menu's constructor `0x10d23c0` logs "start_tag is set, skipping main menu" and sets `+0x730`, and the main menu's frame then shows page 3, `0x10d3a68`).
- **Selecting a country**: `0x111cb80(setup, &tag, 0)` posts a command (`0x277310`) to the session (`main menu` method `+0x80`, its queue at `+0x58`); `0x763840(world, tag)` makes the country the world's player at once.
- **Starting**: `0x1120280(setup)` sets `+0x2cb0` (u8; set nowhere else but by the start paths, `0x111f880`, `0x111f930`, `0x111fe10` and `0x1120280`, and cleared only by the constructor, `0x110b5c1`) and posts the start commands (one with vtable `0x1caef90`, whose execute is `0x738f10`). `0x1120740(setup, continuing)` is what the continue box calls: it stores `continuing` at `world+0x7482`; in single player, not ironman, with a save chosen (`0x111bfa0`: the path at `+0x338`), it calls `0x1120280`; without a save it opens a window first, a question whose answer calls `0x1120280` (`0x13b7190`); for ironman it calls `0x111f930`.
- **The save chosen**: `+0x338`, a `std::string` with the save's PhysFS path (`save games/<file>.eu4`, UTF-8); `+0x358`, u8, the save is in the cloud; `+0x35c`, i32, the save list's selection (-1 for none); `+0xc48`, the tag of the country it is played as. `0x1132ca0(setup, null)` reads that file (PhysFS; a zip when it starts with `PK`); without a session (`main menu` method `+0x80`, its bytes `+0x54` and `+0x55` clear) it hands it to `0x110d760(setup+0x58, path, bytes, 0)`, which loads it into the world at once (`0xd84b80` → `0x74b8a0` → the save loader `0x5cdc60` that `saves` observes) and shows "SAVE_LOADED" or "LOAD_GAME_FAILED" in the setup; with one, it posts a command (`0x37bd`) that loads it at a later frame. Tested: with the setup shown as below, the save was loaded 1.3 to 1.8 s after `0x1132ca0` returned, so by the command. `0x74b8a0` sets `world+0x7480` (the world comes from a save) and empties `world+0x7490`; after the load the world's player tag (`world+0x1e60`, or `+0x1e68` while switched) is the save's player.
- **Once started**: with `+0x2cb0` set, the setup's check for selecting a country (`0x111ca30`) answers no, and `0x112daa0` shows or hides one of the setup's elements by it (the element's methods `+0x88` and `+0x90`); `0x11175e0` reads it too (not followed further). A start that never reaches the game so leaves the setup started until the process ends: shown again, it does not let a country be selected (inferred), and `menu` says `starting` while it shows.
- **Leaving it**: its back button ends the process and starts `eu4.exe` again, as returning to the main menu does. Tested: remote control's restart observer (research/time.md) ran 1 to 2 s after the click, and a new process answered 45 s later. The button (`back_button`, bound by the constructor at `0x110bd42` to the delegate at `+0xd30`) calls `0x111dec0`, which posts a command (`0xbb8`) to the session (`main menu` method `+0x80`, its queue at `+0x58`) and sets the application's `+0x83` and `+0x84` itself, with "-skiplauncher" at `+0x88` (`0x111dfd7`): not through `0x14c2500`, so what replaces that does not see it.
- **The gameplay options**: the constructor reads `gameplaysettings.txt` from the user directory into the world's game settings (`0x747680(world+0x2140)` at `0x110cada`; the path from `0x747030`); `0x7475d0`, called once from `0x13b9e8e`, writes the file. The setup is made with the main menu, so at startup after the world's reset. Tested: after the world was reset with the history once the setup had been made (an in-process return, 2026-11-02), a new game's options differed from the file in three of their 32 values; a new start's were as the file has them.
- **Choosing a save**: `0x1130f40(setup)` posts a command (`0x280e`, which reaches the setup's interface method `+0x50`) and calls `0x1132ca0`; then it selects `+0xc48`'s country, or, for an ironman world, the world's player, and resets `+0xc48`.
- **Loading first and starting later starts a new game**: tested, the save loaded into the setup and, at a later frame, its player selected and the game started as the continue box starts it (`0x1120740(setup, 1)`, by then on an ironman world) gave a game at 1444.11.11 as that country, not the save. The continue box asks for the load and the start at one frame, so that the start's command runs after the load's.

## The continue box

`0x10ef410` (inferred: the box's click, on an object of the first page whose `+8` is the main menu): reads the continue information (`0x210a80(application)`, a copy of what the application keeps at `+0x5d8`, read once at startup from `continue_game.json` by `0x5d1670`; after each save `0x5d1050` rewrites the file but not this copy, see "The continue information" below), checks it can be continued (`0x10da420`), then:

1. sets `main menu+0x910` to 1 (continuing), `world+0x747c` to 0 (single player) and `world+0x23b4` to 1;
2. shows page 3 without animation (`0x10daf60(main menu, 3, 0)`), then finds the setup in the pages array;
3. writes `-1` to `setup+0x35c`, the save's path to `setup+0x338`, the cloud flag to `setup+0x358`, and, with a path, the player's tag to `setup+0xc48`, and calls `0x1130f40(setup)`: it loads the chosen save (`0x1132ca0`) and selects `setup+0xc48`'s country (an ironman save: the world's player, through `0x111cb80`);
4. makes that country the world's player (`0x763840`) and starts (`0x1120740(setup, 1)`).

`game::menu::load` does the same with the save asked for, taking the player's tag from the save's header (below) instead of the continue information. Tested with a copy of a compressed text save whose game state no longer inflates: the save loader failed (its success flag not set; `saves` logged that the load did not establish the current world), the start command ran anyway, and the game began with the save's date and player, the player's country not playable (no controllable player at the first frame). Tested: Castilla-5 (an ironman save, 1470.3.13) and a compressed text save with a Chinese name (1445.2.20) were loaded and played as their countries.

## A save made with other mods

Tested: a compressed text save made with a gameplay mod the playset lacked (its `meta` names the mods in `mods_enabled_names`) crashed the game when `menu.load` loaded it: after the save loader `0x5cdc60` returned, in the load command under `0x110d760` in the main menu's frame, `0x88a1fb` read the 8002nd record (0x230 bytes each) of an array past its end. Whether the game loads such a save when the player picks it from the game's own list of saves was not tried; the continue box's path, which `menu.load` takes, did not stop it. Saves made with the playset's mods loaded as before.

## Starting a game as a country

`game::menu::start` writes the tag into the `-start_tag` text (`0x1fd39a8`) and shows page 3 without animation (`0x10daf60(main menu, 3, 0)`); entering the setup selects the country and starts. Tested: France at 1444.11.11. Prussia, which has no land then, was started too: its first frame read `PRU` as the player, and the next requests found no controllable player, the game left spectating. A load does the same (Z1): a save made for the run from a 1445 one, its player changed to `PRU` (in `meta` and `players_countries`), loaded with Prussia as the player at the game's first frame, and the game was spectating from the next request on. So the game turns a player with no land to observing after the first frame, not at it; where it does was not looked for. The main menu's own `-start_tag` path shows the page with animation (`0x10d3ab3`); done so from remote control, the game crashed at its first frame: the animation (the setup interface's `+0x10`, `0x110f670` → `0x112c2b0`) posts a command (`0x2814`, vtable `0x1caea08`, built when `world+0x7480` is set, as it was after an earlier load in that run) whose execute (`0x7395c0`) looks an object up in a registry (`0x14cf730` on `0x1fc23b0`) and calls through the result without checking it; at the game's first frame the object was gone (crash dump of 2026-10-29, `eu4+0x7395e8`, under the command processing `0x14ca61a` in the game idler's frame).

## Startup

At startup the main thread presents frames for 2 to 3 s before the main menu's frame first runs (tested: the framework's "memory at the main menu" line, written at that first frame, came 2.6 to 2.7 s after the first request was answered). Remote control answers there, outside a game and outside the main menu.

**Continuing from the command line.** The startup at `0x876500` reads two arguments through the command line object (`0x1719c40` finds an argument, `0x1719b50` copies its value; an argument is a 0x40-byte record, its name at `+0`, its value at `+0x20`):

- `continuelastsave` (`0x876558`): reads `continue_game.json` (`0x5d1670`) and, when it holds a save, sets the flag `[0x233fe9c]` and copies the file name into the path `[0x1fd3a08]` (a `std::string`).
- `continue <file>` (`0x876865`): sets the same flag, and the path to `save games/` followed by the value.

The main menu acts on the flag once its timer at `+0x720` has passed a threshold (`0x10da573`), through the continue box's own steps (`0x10edb80` clears the flag and calls `0x10eda80`, which checks the save with `0x10da420`). Tested (2026-11-04, the game without the framework): `-continue eu4harmony_vanilla_test.eu4` showed the save in the continue box and opened a window with two buttons (its Chinese text unreadable without the framework), which Enter answered, and the save loaded. `-continue` without a value crashed the game at startup ("Could not open file: save games/"). `-continuelastsave`, and `-continue=<file>`, left the game at the main menu; why was not looked into.

## A save's header

A save is plain text that starts with `EU4txt`, or a zip file (deflate) whose entries are `gamestate`, `meta` and `ai`; `meta` starts with `EU4txt` or, for ironman saves, `EU4bin`. In text, the header has `date=1470.3.13` and `player="CAS"`; in the binary form a field is a u16 token, `01 00` (`=`), a u16 type and the value: the date is token `0x284d`, type `0x000c` (i32, the date as the game keeps it, docs/research/dates.md), and the player token `0x2a38`, type `0x000f` (a string: u16 length, then the bytes). The mods the save was made with are the list `mods_enabled_names`, in the playset's order, a block per mod with its descriptor and its name: in text `mods_enabled_names={ { filename="mod/ugc_2976470733.mod" name="Chinese Language Mod for 1.37" } ... }`; in the binary form the token `0x3b51`, `=`, `{` (`03 00`), then for each mod `{`, its `filename` (token `0x03b6`) and its `name` (token `0x001b`), each `=` and a string, and `}` (`04 00`), and last `}`. A string there is type `0x000f` or `0x0017` (quoted or not in text), its u16 length, then the bytes. `saves::file` reads the player, the date and this list, and no mods from a header without it. Of the 139 saves in the test folder, 93 were zipped binary, 44 zipped text and 3 plain text (the autosaves).

## Returning to the main menu

- **The flag**: the map manager's (the game idler, `campaign::classes::MAP_MANAGER`, `world+0x1e00` in a game) `+0x12e9`, u8 (`campaign::map_manager::RETURN`). The answer to the return question (`0x11bddf0`, a method of the question's window, vtable slot at `0x1d65a08`) sets it, and so does the end-of-game summary when it is left (`0x8156ba`, from `0x140cdc0`).
- **What the map manager's frame does with it** (`0x8137c0`, at `0x815c9f`; only when the frame's second argument is set, as in a normal frame): `0x80fee0(map manager)`, `0x5cc160()` (the ironman exit save, below), then `0x14c2500(application, "-skiplauncher")`, which sets `application+0x83` (quit) and `+0x84` (start again) and keeps the extra argument at `+0x88`; the rest of the frame is skipped (`0x815d5c`). `0x80fee0` frees `[0x2349528]` and, in multiplayer, sends a leave message; nothing else needs it before `0x5cc160`.
- **Every return restarts**: `0x14c2500`'s only caller is `0x815cf3`, and the main menu's constructor `0x10d23c0` has one caller, at startup (`0x205855`). So vanilla makes the main menu once per process and never shows a second one.
- **The application's run** (`0x14c2d00`, from `0x8757e0`) loops over its frame while `+0x83` and `+0x2f8` are clear; after the loop it shuts down (vtable `+0x50`) and, with `+0x84` set, calls `0x14c3a10`: the command line (`GetCommandLineA`, rebuilt by `0x14c3100`, which handles `continue` and the login arguments) is started with `CreateProcessA` on the module's own path ("Failed to restart process: " when that fails). Then `0x14c2d00` returns and the process ends.
- Remote control answers every request at `0x14c3a10`, before it runs (`game::time` observes it, docs/research/time.md), so a return the player makes answers waiting requests as `menu.return` does.
- Tested: `menu.return` answered at once; the old process's pipe broke about 2 s later, and a new process answered about 45 s after that (prototype-log.md).

The sections below come from reading eu4.exe on 2026-11-02; none of it was tried in the game.

## The ironman exit save

`0x5cc160()` returns nothing and does nothing unless the world's ironman flag (`world+0x24d0`) is set. A local save then goes `0x5cc6e0` → `0x5cbde0` → `0x5c7ac0`, on the calling thread, with the request at `0x1fd2dd0` (ironman, report). `0x5cbde0` returns the save's result (held in `ebx` from before `0x5cbec3` to `0x5cbec9`), but `0x5cc160` drops it: to its callers a failure shows only as the window `0x5cb110` opens ("SAVEGAME_ERROR_WRITING", through `world+0x1e00`). A cloud save goes through `0x5cc370`, which on result 4 opens a window and pauses the game.

## The world reset

- **`0x826c20(map manager, save)`** (ingameidler.cpp, "ResetGamestate"): with `save` set it first calls `0x5cc160`; then it goes through two lists of the map manager's (`+0x78`, calling each item's method `+0x28`; `+0x498`, freeing it), resets the world through the application's `0x210000`, makes the map manager the world's idler again (`0x756a30`) and logs "Gamestate successfully resetted." Its only caller is `0x5d0580` (below).
- **The second argument does two things**: `0x826c20` hands it on to `0x210000` (`0x826f89`, `movzx edx, dil`), which skips the game's history when it is set (`0x210485`, `test r13b, r13b; jne`, past `0x7ea2c0`). So the in-game load, which passes 1 (`0x5d0a29`), writes the ironman exit save and keeps the history unread, which the save it loads makes up for; a reset with 0 reads every history file again, the slow part of a reset.
- **`0x210000(application, without history)`** (eu4application.cpp, "ResetGame", with progress strings 10% to 100%): the world back to the start date without loading the game's content again. It resets the DLC (`0x974310`), sets the country tags and the country database up again (`0x207310`, "CountryTags Initialized (After reset)"), reads `dlc_metadata` (`0x2060f0`), reads every file of `history/provinces` and `history/countries` again (`0x7ea2c0`, which startup also calls, `0x20f30e`) and checks them ("History PostValidate", `0x7e9b70`), sets the date (`0x76d260`), and works out ports (`0x10ad9f0`), each country's knowledge (`0x93fe30`) and the modifiers (`0x327dc0`, `0x9f9500`). Its other caller is a method of the single player setup, `0x112aba0` (vtable slot at `0x1d5e408`).
- `world+0x24d0` (ironman) is cleared by `0x74a260` (`0x74a836`), from the reset (`0x749020`) and again from the loader (`0x5cf7a1`); the world's handler of top-level entries sets it at the `is_ironman` entry (`0x754c52`), which the header writer writes only for an ironman game (`0x74f3e5`). So a session takes ironman from its save.
- **Where its time goes** (tested 2026-11-02, by tracing its calls): without the history 2.4 to 2.9 s, of which the country tags and database (`0x207310`) 1.7 s, what comes before it (`0x45ba90` to `0x74c080`) 0.2 to 0.4 s, and the world's own reset (`0x749020`) 0.1 s; with it 3.0 to 4.8 s, of which `0x207310` 2.3 s and the history with what follows it 2.0 s.
- **What it leaves**: vanilla resets the world this way only on the way into a save, whose loader sets what the reset does not, or in the single player setup, on a world that has not been played. Tested, after a game of 1724 then the reset with the history, against a new start: the save's `hre_religion_status` was 2 against 0, and the save's `achievement` list, which a new start does not have, was the old game's. Neither is the world reset's:
  - `hre_religion_status` is `world+0x2418` (u32; the loader sets it at `0x753893`, the saver reads it at `0x75117b`, the world's constructor zeroes it with `hre_leagues_status` at `+0x241c`, which `0x74a260` resets and this not). Setting an Empire's emperor (`0x704760`, which the history calls for the emperors of 1444, at `0x4e2738`) compares the emperor's religion with the Empire's religion and, when they differ, makes the emperor's the Empire's religion and its original religion and sets the status to 2 (`0x7048ca`..`0x7048e3`). The religions (`[0x242bd98]`, made on first use by `0x99b60`, kept until the process ends) hold the Empire's religion at `+0x60`, its heretic religion at `+0x68` and the original two at `+0x70` and `+0x78` (saved as `hre_religion`, `hre_heretic_religion`, `original_hre_religion`, `original_hre_heretic_religion`, `0xa7bdb4`..`0xa7beaa`); the 1724 session had changed all four, so the history's emperors differed from the Empire's religion and set the status to 2. The framework keeps the four as the first main menu of the process has them and puts them back, with the status 0, after every world reset and again after a reset that read the history. Tested: a new game after the 1724 session then had `hre_religion_status=0`.
  - The achievements are a global made on first use (`0x96080`, `[0x233d890]`, 0xa8 bytes): `achievement_ok` comes from `0x96810`; the saver writes `achievement` from the vector at `+0x38` when achievements can be earned or at `+0x88` when not, and `completed_achievements` from `+0x50` (`0x751b02`..`0x751b38`), each a vector of i16 (`0x4213a0` steps 2 bytes). Nothing empties them before a new game; a load fills them from the save. The framework empties the three after every world reset. Tested: no `achievement` list after the 1724 session.
  - The gameplay options are read once the reset is done, by the single player setup (below), so a reset after the setup is made puts them back to their defaults.

## Loading a save in a game

- **The way in**: `menu_load_button` → `0x824dd0` (the map manager's delegate at `+0x26f0`; it refuses only in multiplayer, `+0x19f1`) hides the in-game menu (`+0x12f0`) and shows the load window (`+0x12f8`, vtable `0x1d62ca8`, made by `0x8318f0`). Its load delegate `0x11756b0` takes the save chosen in its list and asks "CONFIRMLOADSAVETITLE"/"CONFIRMLOADSAVETEXT" (`0x11be0b0`, shown by `0x6ecae0(map manager, window)`), or "SAVEGAME_WARNING_OLD_VERSION" for a save of an older version (`0xb29ca0`). Accepting (`0x11be2d0`, vtable `0x1d65aa0` slot `+0x50`) calls `0x1176020`, which calls `0x5d0580(&request)` and then `0x824810(map manager)`. The game console's `savegame_check` (`0xe95610`) calls `0x5d0580` too.
- **Ironman**: only the interface refuses. The button is turned on only when the game is neither multiplayer nor ironman (`0x8322c6`, `!map manager+0x19f1 && !world+0x24d0`), and the menu's tooltip says "NOT_LOAD_IN_IRONMAN" (`0xb7d0b6`, through the game settings `0x95750`, `world+0x24c8`, and its `+8`). Nothing after the button checks ironman, and an ironman save loads like any other. `0x5d01b0` refuses a save ("Loading ironman in modded game") when the entry after `player` is `ironman` or `is_ironman` and `[0x233d890]+2` is clear; inferred never to apply to saves of this version, which put `displayed_country_name` there (5 saves on disk looked at).
- **`0x5d0580(&request)`**: the request holds the save's name (`std::string` at `+0`, from the window's `+0x3c0`; the path is put together by `0x5ca070` from the folder, the subfolders at `+0x20` and the name), the map manager (`+0x38`), whether the save is in the cloud (`+0x40`), and `0x8bf160()`'s object (`+0x48`, which may be null). It opens the file, calls `0x826c20(map manager, 1)` (`0x5d0a29`), so an ironman game always gets its ironman exit save first and a plain one is not saved, reads the header (`0x5d01b0`), and loads (`0x74b8a0` → `0x5cdc60` → `0x5cf740`), then rebuilds the game's interface (`0x81af10`, "RestoreDeviceObjects", then `0x81ab20`).
- **What it answers**: 1, no name, and 2, no file, change nothing; 3, the header refused, comes after the world has been reset; 0 otherwise, even when `0x74b8a0` failed. The load window ignores the answer.
- **The interface after it**: `0x81af10` destroys and makes again the top bar (`map manager+0x12d8`, at `0x81bdf4`), the in-game menu and the load window (`0x8318f0`), sets the game console up again (`0x6e90f0`), and calls `0x5cc160` again (`0x81d8c8`), so an ironman save is written again right after it is loaded. Whatever pointed into those windows points at freed memory afterwards.
- **Threads**: everything runs on the calling thread; `0x5cdc60` starts a "SaveSessionUpdateThread" and waits for it before returning. It sets the busy bit (`0x245adc0` bit 0) and clears it when done, and shows no loading screen.
- **`world+0x7481`** (an ironman game in the cloud) is written only by `0x1132310` and `0x13b8d40`, in the main menu, so it is not brought up to date by a load in a game.

- **The save after it, in ironman** (tested 2026-11-02): `0x81af10` writes the ironman save of the session it sets up (`0x81d8c8`, `call 0x5cc160`), but `0x5d0580` lets the file it read go only afterwards (the reader at `rbx`, deleted at `0x5d0f58`, after `0x81af10` at `0x5d0d73`). Replacing that file then fails: `error.log` says "Failed to rename save games/Castilla-5.eu4 to save games/Castilla-5_Backup.eu4 Back up failed", "PHYSFS_delete … tried to modify a file the OS needs" and "SAVE ERROR: Failed to rename new save file save games/Castilla-5.tmp", the game shows "备份文件失败", and a `.tmp` is left. Vanilla never meets it, since its load button is off in ironman. The framework makes that save once `0x5d0580` has returned (`game::menu::leave`); so made, it was written with no error.

- The return question's answer does not return at once: it shows the end-of-game summary (`endgame_dialog` in `interface/endgamedialog.gui`, with "退出" and, at the end of the game, "继续"), whose quit button returns. Tested 2026-11-02: letting it go again then corrupted the heap (`0xc0000374`); letting it go as the reset leaves it, only when the reset did not, went well three times running.

## The memory a world reset and a session leave

Counted with the framework's census of the C runtime's heap blocks by call site (`trace` feature, `EU4HARMONY_CENSUS`), 2026-11-02:

- Every in-game load of the same save left 27,450 blocks, 4.3 MB, that no later reset let go, from about forty call sites, the same at each load: among them `0x283d8d` (1,380 blocks, 0.73 MB: the country tags' setup in the reset, `0x207310` through `0x283d20`, gives every country with an empty `+0x10a0` a new array; the old ones are never freed) and `0x861d41` (3,115 blocks, 0.5 MB: `CLeader::CreateFromReader` makes the save's leaders; the old session's are never freed). - An in-process return left 8 to 10 MB, those leaks and the GUI elements above among them.

- **Still counted, `GFX_messageicon_bg`**: the diplomatic message icons, a list in the message icon holder (`+0x4c78`, nodes of `{entry, previous, next, removed}`; each entry 0x160 bytes, its window at `+0x18`), which neither the holder's destructor (`0xdf5180`, the nodes only) nor `0xdffca0` (the other icons only) lets go. `0xdffcf0(holder)` does: each entry's objects, its window killed (`+0x130`), the entry deleted. The in-game load calls it before its world reset, with the rest of its taking the session's interface down: `0x5d05ac`–`0x5d0653` (a flag `0x4707b0` gives, set and signalled, `0x4708d0`; the map mode back to the first, `0x821ff0(map manager, 0, 0, 0)`; `0xdffcf0`; each popup's method `+0x28`; the message windows marked closed, `+0x1d0`; a vector at `+0x19f8` emptied; a method `+0xb8` of `[[+0x12d0]+0x70]`). With no save's name it stops there and answers 1 (`0x5d06c4`). The framework's in-process return now calls it so, before its reset.
- **Still counted, `MessageSettingsButton`**: a message window (`0x123f800`, 0x1d8 bytes, one of the map manager's `+0x4b8`, shown in the menubar's message list, which lets it go) holds the popup it is made with (`+0x130`, `0x123f9e1`; a dialog of `eu3dialog.gui` and the like, whose settings button shows that sprite) and never lets it go: its destructor (`0x123ff50`) leaves it. Its frame closes the popup (`+0x58`, `0x838b20`, which only asks it to close) when the message goes out of date and is not closed (`0x8147f5`); a popup not in the map manager's popups (`+0x78`) is never deleted, and its window keeps counting. The in-game load marks every message window closed. Counted with an observer of the show, hide, load and unload of that sprite type: three popups shown, one hidden at the return, the type unloaded by the main menu with two still counted. The framework now deletes, before the return takes the interface down, the popup of every message window not closed, unless open among the map manager's popups, which the idler switch's `0x81e8f0` deletes with the others (`0x6ea1c0`). Deleting the message windows too was tried: the message list, deleted with the menubar, deleted them again (`0xc0000005` at `0x152df34`, in the GUI root's update).
- **Still counted, others**: those two did not end it. In twenty rounds of a load, 30 days, an in-game load, 10 days, a return, a new game, 10 days and a return, the fourth round's load crashed the same way on `MessageSettingsButton`: popups of message windows the in-game load had marked closed, and of messages gone out of date, which nothing lets go, still counted. What a session leaves counting has more ways than the framework can follow one by one.
- **The repair**: the framework replaces the sprite type's unload (`0x156d730`, the method `+0x48` of the class `0x1d9cf40`; the group unload calls it at `0x14dc2a5` once it cleared `+0x44`). A sprite type loaded lazily that shown sprites still count stays loaded, its `+0x44` set again, and its texture is let go as usual when the last of them hides (`0x15bd500`); any other unloads as before. Vanilla makes the main menu only at startup, before any sprite of the game shows, so the repair changes nothing there. Each sprite type kept so is logged with the count, "repair: the sprite type … stays loaded with its group".
- **Tested** (2026-11-02): after those two, four returns in a row each after 30 days at speed 5, and a fifth session run 30 days, no crash and no lazy-load error; a return with the end-of-game summary open, in-game loads after time ran, and a new game after a return, as well. With the repair, 20 rounds of a load, 30 days, an in-game load, 10 days, a return, a new game, 10 days and a return, no crash and no lazy-load error. At each return it kept 32 sprite types loaded: the 30 building icons (which `macrobuildinterface.gui` shows), `GFX_government_boost_states` (`countryreformview.gui`) and `MessageSettingsButton`, their counts growing with every session or in-game load. About 1,030 GUI elements still stay in the GUI root after each return, and about 400 after each in-game load.

## The continue information

`0x5d1050` (called once, at `0x5ce3ec`, after a save is written) writes `continue_game.json` (title, desc, date, filename) through `continue_game.temp`. It does not write the copy the application keeps at `+0x5d8` (inferred: no store to it was found there), which `0x5d1670` reads once at startup. A process that goes on after a session is left so has continue information as old as its start.

- Startup fills the copy with `0x2111c0(application, path)` (`0x204ea4`); `0x212810(application)` fills it from the newest save in `save games` (`0x211960`, then `0x2111c0`). A task of startup's at `application+0x5d0` reads it in the background, and whatever touches the copy waits for that task first (`0x17139c0`): `0x210a80`, and `0x2110c0`, which then calls `0x2111c0`. The framework waits for it, then calls `0x212810`, after an in-process return. Tested: the continue box then offered the save the session had just written.

## The application's idler switch

- **Asking for it**: `0x14c2530(application, &idler, keep)` sets `+0x48` (pending), moves the idler into `+0x70` (letting go of one already pending) and keeps `keep` at `+0x80`.
- **The switch**, in the application's frame after the idler's frame (`0x14c282f`): the current idler (`+0x40`) moves to `+0x78`, its methods `+0x50` and `+0x38` run, and unless `keep` is set it is deleted (its slot `+0`, with 1); the pending idler becomes the current one, `+0x48` is cleared, and its methods `+0x48`, `+0x28` (with the device), `+0x30` and `+0x40` run.
- **Startup makes the main menu** (`0x205830`): `new(0xb48)`, `0x10d23c0(memory, application+0x350, application+0x358, application)`, then `0x14c2530(application, &main menu, 0)`. The constructor's only caller is that one.
- **The map manager's destructor** `0x80b570` (slot `+0` is `0x80b420`) lets its windows go through their destructors (`+0x10e8`, `+0x10c8`, `+0x12f8`, `+0x1300`, the top bar at `+0x12d8`, among others), all but its minimap, `+0x10e0` (`minimap_panel`, made at `0x80b241` by `0x1247ed0` when `0x1248850` says so; its destructor is `0x1248740`). Tested: after the map manager was let go at an idler switch, its minimap stayed on the main menu, until the framework let it go before the switch.
- **What the main menu does when it takes over**: its vtable is `0x1d5a8c8`; slot `+0x30`, which the switch runs, is `0x10d5bc0` (frontend.cpp). It makes the main menu the world's idler (`0x756a30`), draws and presents one frame of the loading screen with the status `LOAD_GFX` (`0x11bb4f0`): with no loading screen window at that time, the painting alone over the whole screen. Then it loads the country flags and restores the device objects twice (logging the memory used before and after each, "Used video memory after second restore device: "), makes the main menu's windows (`mainmenu`, `lobby`, `country_selection_panel` and the others), and last lets the loading screen window go (`0x11bbbc0`) and makes a new one for the next load (`0x11bb850`, `load_screen` from the GUI, with a tip; `0x11bbc10` sets its background `bg_load_screen2`; its third argument, set here, keeps it from drawing). An in-process return, which makes the main menu as startup does, presents the painting again, once (traced 2026-11-06), and the new window's marks and tip then stay over the main menu as its map fades in from black, for about 2 s (tested 2026-11-03, prototype-log.md).
- **The loading screen** is a window of the GUI kept at `[0x242bef8]`. `0x11bb450(gui root)` draws the GUI root and presents through the renderer's function pointers (`[0x1fd1290]`, `[0x1fd1298]`, `[0x1fd1300]`). `0x11bb4f0(graphics, text, new picture)` sets the window's status and tip texts and calls `0x10b3600(graphics, text, draw, new picture)` (eu3graphics.cpp), which draws a picture from `gfx/loadingscreens/` (`load_0.dds` to `load_36.dds`) over the whole screen, the GUI over it, and presents; it loads a picture (`0x10b2ee0`, at random, kept at `graphics+0x32690`) when asked for a new one or when none is loaded, and with no loading screen window it draws the picture alone. With `draw` false it only draws the text, as for `SCREENSHOT_TAKEN`, `MAP_SAVED` and `CANAL_CONSTRUCTION`. `0x11bb850(graphics, gui, without drawing)` asks for a new picture when it draws; the startup loads the first one as it makes the graphics (`0x10b2830`). `0x11bc450` sets the status text alone. Their callers are the main menu (here, and as it starts or loads a game, `0x10da520`, with `CALCULATING_CHECKSUM` and `LOAD_INIT`), startup (`0x2003d0`, `0x202850`, `0x2043a0`, `0x208620`), the map's graphics (`0x12db850`, `LOAD_GFX_PDXMAP_BORDERS`, `LOAD_GFX_PDXMAP_RIVERS` and the others, called at startup by `0x10a2e40` and by the random new world), the random new world, and `0x87b9e0`, `0x10a8930` and `0x10c7280`, which were not followed. The world reset (`0x210000`) calls none of them: its progress texts ("10%" to "100%") are made and let go unused; and the in-game load showed no loading screen (tested 2026-11-03).
- **The map manager's frame after the return's restart** (`0x815d5c`): while its return flag is set it skips the rest of the frame (`jne 0x8165f2`); cleared, the frame goes on as usual.

## The save games folder

`save games` in the user directory (`paths::user_dir`), where the game writes saves; continue information names a save as `save games/<file>.eu4`. Saves are zip files (`gamestate`, `meta`, `ai`, deflated) or plain text. `menu.saves` reads each save's header (above): the first 64 KiB of a plain save, the `meta` entry of a zipped one. What it read is kept until the process ends, by the file's path, size and time written, so a save is read again only once it has changed; the first `menu.saves` of the run took 11.1 ms for 139 saves.
