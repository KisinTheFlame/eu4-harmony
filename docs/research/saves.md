# Saves: how the game writes and reads them (for `saves`)

Baseline 1.37.5. All addresses are RVAs. Read from `eu4.exe` with `core/examples/disasm.rs`, 2026-11-01 and 2026-11-02, for extension save data in the save (ADR extension-save-data-in-the-save). What was tried in the running game is in [prototype-log/](../prototype-log/). The save request, the writing of the file and the loader were first read while regional-combat was developed (2026-10-26) and checked again on 2026-11-03. The ironman exit save and the in-game load, which go through these, are in [main-menu.md](main-menu.md).

## The save file

- A save is a zip of three entries, `meta`, `gamestate` and `ai` (and `rnw.zip` in a random new world), or one plain file holding all three. Either way its content is text (`EU4txt`) or binary (`EU4bin`); ironman saves are binary. `core/src/saves/file.rs` reads the header of both.
- **Text**: `key=value` lines, blocks in `{ }`, tabs for depth; quoted strings escape `\` and `"`.
- **Binary**: a stream of u16 token ids. A key the game knows is its id; `0x0001` is `=`, `0x0003` `{`, `0x0004` `}`; `0x000c` is followed by an i32, `0x000f` by a u16 length and that many bytes (a string), `0x0017` likewise (a string the game made an id for while running).
- An extra entry in the zip is ignored: the loader asks for its entries by name (`0x5cd120` → `0x153bce0`, which checks each one's CRC32).

## Writing

- **The save request** is what `0x5cbde0(request) -> u32` writes: the save's name (`std::string` at `+0x00`; not a disk path), bytes at `+0x20` to `+0x26` that choose how (`+0x20` ironman, `+0x21` cloud; `+0x22` and `+0x26` are handed to the serializer `0x74ba20`, unnamed), the subfolders (`+0x28`, which `0x5ca070` joins with the folder, the name and `.eu4` into the PhysFS path), and `+0x40`, report errors. `0x5cbee0` builds one and calls `0x5cbde0` at `0x5cc04e`; the ironman exit save's request is at `0x1fd2dd0` (main-menu.md). The other calls of `0x5cbde0` are at `0x5cace8`, `0x5cc615`, `0x5cca17`, `0x5ccc18` and, from the game console, `0xe95e5e`; that these are all was not checked.
- **`0x5cbde0`** sets the busy bit (bit 0 of `0x245adc0`, through `0x4707b0`; the loader sets it too), keeps whether it was set, and announces the change (`0x4708d0`). Then: neither ironman nor cloud, the local save `0x5c6500`; ironman alone, the local ironman save `0x5c7ac0`; cloud alone, the cloud save `0x5c8ba0`; ironman and cloud, it records the date at `world+0x24cc`, clears `world+0x24c8`, and calls `0x5c8ba0` only when the cloud service (`[[[0x242bf50]+0x348]+0x38]`, its method `+0x48`) says it is there, and otherwise answers 4. When the request reports errors and the result is not 0, `0x5cb110(result)` opens the error window. Last it puts the busy bit back as it found it (`0x4708d0` again, at `0x5cbec3`) and returns the result.
- **The local saves** (`0x5c6500`, `0x5c7ac0`) write to a `.tmp` beside the save (deleting one left there before, ".tmp file already exists, deleting: "), serialize the world into it (`0x74ba20` at `0x5c68e6` and `0x5c7ea4`), close it, check its size (the local save fails under `0x2800` bytes, "File written to had size … Save failed."; the ironman save has its own " file had invalid size. Local Ironman save failed!"), back up the existing save, and move the `.tmp` onto the `.eu4` with `0x1715bb0(from, to)` (at `0x5c7888` and `0x5c88ef`; the call at `0x5c76ab` moves a backup). `0x1715bb0(from, to)`, both C strings relative to the folder PhysFS writes to (the user folder), turns them into full Windows paths (the write folder from `0x19f7530`) and moves the file (`0x1a5ed40`); it returns 1 when the move worked, and otherwise logs "Failed to rename …" and returns 0. It is the game's general file move, not only the save's.
- **The result says the world was written, not that the file was replaced**: the result, 0 or 5, is set from the serializer's answer (and, in the local save, the size check) (`0x5c6c0f`; `0x5c81d2` for ironman) before the move, and a failed move logs "SAVE ERROR: Failed to rename new save file …" (or "CRITICAL SAVE ERROR …") and returns that result as it is. So `0x5cbde0` answers 0 for a save whose `.eu4` was never replaced. This is read from the code; a move that failed was not made to happen in the game this way (main-menu.md has what an ironman save of a file that was still open did).
- **The path**: every caller ends in `0x74ba20` → `0x5cde60` → `0x5ce5f0`. The callers are the normal save `0x5c6500`, the ironman save `0x5c7ac0` and the cloud save `0x5c8ba0` (which the console's `savegame_check`, `0xe95610`, also reaches); and the multiplayer host's save for a hot-joining player `0x840a60`, the `.hotjoin` debug dumps `0x1ef660`, the out-of-sync dump `0xd81e10` (`savegame_oos_machineid_%i_%s.oos`) and the autotest saves `0x82f9e0`. The last four are multiplayer or debugging.
- `0x5ce5f0` writes the three entries into memory streams through `0x14e3f00(stream, object, …)`, and builds the zip from them (`0x153b9a0` adds an entry, `0x153c350` at `0x5cf163` finishes).
- **The zip entry** `0x153b9a0(zip, name, data, method, level)` writes the local header through the zip's stream (its method at `+0x50`), then the data: method 0 stored, copied in chunks with its CRC (`0x153bb0c`); 8 deflated by `0x153c790` (`deflateInit2_` `0x181fc70` with the level, method 8, raw window bits -15, memory level 9, strategy 0, zlib "1.2.3"; `deflate` `0x181f210`); `0xc` another method (`0x153c440`; _inferred_: bzip2). The save's three calls (`0x5cecbf`, `0x5ced3a`, `0x5cf0e1`) ask for method 8 at level 3. The framework has them deflate at level 0 during a local save (`saving::background`, docs/plans/game-speed.md).
- **Method 0 does not work for a save** (tested, 2026-11-04): the deflate path first moves the data stream back (its method `+0x88`, then `+0x60`), the stored path reads from where the stream stands, after the end of what was written, and copies the zip's zeroed buffer instead. An ironman save written so held 61 MB of zeros, with a CRC of the zeros, and the game's own reader then refused it ("not a save the game wrote"). The game never asks for method 0 itself.
- **`0x14e3f00`** writes the header (`EU4` and `bin` or `txt`), makes a writer on its stack (vtable `0x1dbf7d8`), sets the writer's depth to -1 and calls the object's method at `+8` (`0x14e4026`). That method, `0xd2f410`, opens a block (`0x1708750`, which at depth -1 writes nothing and makes the depth 0), calls the world's method at `+0x10`, the world write, and closes the block (`0x17087e0`, which back at -1 writes nothing). Then `0x14e3f00` takes the checksum of what the stream holds and writes `checksum="…"` (key at `0x14e40e8`, `=` at `0x14e4145`, the value at `0x14e41d6`).
- **The world write** `0x74ff30(world, writer)` picks what to write by the name of the writer's stream: the writer holds the stream at `+0x10`, and the stream its name, a `std::string`, at `+0x18` (read at `0x74ff61`). `ai` gets the AI only (`0x74fa90`), `meta` the header only (`0x74eb20`); `gamestate` gets the game state; any other name (a plain save) gets the header, the game state and, last, the AI, as one block `ai={ … }` (`0x751c92`). The game state ends with `achievement_ok`, `achievement`, `completed_achievements`, `rnw_check_seed`, `unit_manager`, `trade_company_manager`, `tech_level_dates` and `idea_dates`. Both the `gamestate` stream and a plain save pass `0x751c87` once the game state is written, with the writer in `rsi`; there `r15b` says whether the AI follows (`0x751c8c`, a plain save) or not (`0x751c98`).
- **The writer**: `+0x08` its depth of blocks, `+0x10` the stream, `+0x18` a byte set for binary, `+0x19` whether it owns the stream. Its functions, each taking the writer first:
  - `0x1708870(writer, token)`: one token. A token is a u32 type, 512 bytes of text up to a NUL, and a byte at `+0x204` the game's callers leave 0 (`0x1708750` builds one on its stack). Text: the text as it is. Binary: types in the range of ids made while running as `0x0017` and the text; the line break, indent and space types (`0x10` to `0x12`) as nothing; any other as its u16 type, followed for `0xc` by the text read as an i32 (`0x1a48fd8`), for `0xf` by a u16 length and the text, and for a few others by their values.
  - `0x1708750(writer)`: `{`, then a line break, when the depth is 0 or more; the depth goes up either way. `0x17087e0(writer)`: the depth goes down, then, when it is 0 or more, an indent, `}` and a line break.
  - `0x1707d90(writer, text, no_line_break, unquoted)`: a string. Binary: `0x000f`, a u16 length and the bytes (`0x1708ee0`, which cuts the length to 16 bits without a word). Text: quoted, `\` and `"` escaped, or as it is when `unquoted`; then a line break unless `no_line_break`.
  - `0x17084a0(writer)`: a line break (type `0x10`). `0x1708560(writer)`: tabs for the depth, in text only.
  - `0x1708420(writer)` is a space in text but writes a one-byte `0x000f` string in binary: it is not used.
- **The checksum** (`0x14e3390(out, stream, cut, salt, salt length)`): `MD5(decimal(S) ‖ decimal(N) ‖ salt)`. N is the stream's length less 34 bytes in text and 36 in binary (with `cut` set, as when a save is read): the checksum's value is taken to be the last thing in the entry, so N reaches up to and including `checksum=`. S is a 32-bit sum of those N bytes (the stream's method at `+0x98`, `0x171f3f0`: for each byte `a = a + byte`, then `b = b + a`, each kept as it is up to 0xffff and shifted right by 16 above it; S is `a << 16 | b`; above 0xffff each is in fact 1), written in decimal as a signed number; N in decimal too. The salt is `I_am_such_a_cheater` when the game checksum is not vanilla's or the save checksum of the save loaded did not match, unless the developer command `set_achievements_ok` was run (`0x5ce788`; ironman, multiplayer and the game rules play no part, [achievements.md](achievements.md)), and otherwise a string from `[[0x242bf50+0x348]+0x30]`'s method at `+0x40`. Tested (2026-11-02): computed so, the checksum matched every save of the player's that was written with the first salt.
- So an entry written before the checksum is taken, while the world writes itself, is in the checksum; anything added to the file afterwards is not, and anything after the checksum moves N.
- **Which salt** (traced in the game, 2026-11-02): reading a save, the check calls `0x14e3390` with an 8-byte salt, whose bytes the trace does not show; a new game's saves are written with the same salt and pass the check. Once a check has failed, the saves the game writes in that process are salted with `I_am_such_a_cheater`. The digest the check computes, which the trace logs as `0x14e3390`'s result, is the checksum a save with that content should hold.

## What writing the game state writes

For writing the countries and the provinces on several threads (docs/plans/game-speed.md, S8). Watched with the write watch (`dev-write-watch`, [dev-tools.md](../dev-tools.md)) over the world write `0x74ff30` of one ironman save, 2026-11-04: Austria-37_4-1 from 1724, the save the game makes as the loaded game starts, the other threads held ([What writing the game state writes](../prototype-log/2026-11-04-writing-game-state.md)). Writes to the stack and to blocks made during the call are not counted; what is below is every write to memory that was there when the call began, the process heap's blocks and `eu4.exe`'s data.

- **Where the game state's time goes**: the countries are the loop at `0x75179a` (each `0x1707a20(writer, tag, country)`, the tag as the key), the provinces the loop at `0x75170c` (each the key `-id` as two tokens, `0x1708870`, then the province's method `+8`); the other sections are small beside them.
- **The output**: the writer writes through the memory stream (`0x171f33d` in its write `0x171f290`) into one buffer, 0x8c00000 bytes, that was there before: the stream is kept from one save to the next. 22 million of the call's 25.8 million writes went there.
- **The C runtime's data of the thread**, a block of 0x3c8 bytes (`0x1a43386` under `0x1a42041` and `0x1657e88`, from `0x246c36`, the number formatting): written by every number written, 281,000 times under the countries and 95,000 under the provinces. It is the thread's own, so a thread of the framework's writes its own.
- **Two values held in a static object**: `0x15bf70(value) -> object` puts `value` at `[0x2458c00]`, clears the byte `[0x2458c08]` and returns the static `0x2458bf0` (its vtable set the first time, a function-local static), whose method `+8` writes the value; the caller writes the key between (`0x861c55` writes `0x28c0`, then calls it). Ten places have the same code inline (the stores to `[0x2458c00]` at `0x4517c8`, `0x45186e`, `0x451b43`, `0x451c51`, `0x7ccc77`, `0x7ccd3b`, `0x84c5e7`, `0x84c7f5`, `0x84cbb2`, `0x84cc77`). They are five copies, each with two of the stores: `0x4517c8`, `0x451b43`, `0x7ccc77`, `0x84c5e7` and `0x84cbb2` store the value and then take the object's address for the call of its method (`lea rcx, [0x2458bf0]`); the other five are in each copy's setting up of the static the first time, behind its guard (`[0x2458c10]`), which the C runtime's lock keeps to one thread. `0x2c59b0(value)` does the same with `[0x2458e90]` and returns `0x2458e80`. Watched: `0x15bf70` 40,539 times under the countries and 4,878 under the provinces, the copy at `0x451b43` 375 times under the provinces, `0x2c59b0` 2,194 times under the countries. Two threads using one of them at once would each write what the other put there: these are what keep the countries and the provinces from being written side by side as the game's code stands. A search of the code for a store to a static followed within 16 bytes by the address of the static 0x10 below it found these two and no other.
- **A pointer kept in the object it was read from**: `0x29cd80(object, writer)` reads a pointer from `object+0x48` (`0x14cf730`) and keeps it at `object+0x40` (`0x29cd99`, `0x29cdcb`), in blocks of 0x50 bytes, 4,300 times each, under the countries (`0x2dcda2` → `0x297568` → `0x2976ac`). It writes what it reads, into an object of the country being written.
- **Once a process**: function-local statics set up the first time they are reached (`0x9d46dc` to `0x9d4767` into `0x2462ab8`…, `0x2c78ce` to `0x2c7903` into `0x245ad00`…), through the C runtime's lock for them (`[0x233c4e8]`, `0x1a32f2a`, `0x1a32f8a`) and its list of what to destroy at exit (`0x1a635a3`).
- Nothing else under the two loops: no other static, and no other block that was there before. The meta (`0x74eb20`) and the AI (`0x74fa90`) were watched too and are not written side by side.
- **Not covered**: code the countries and provinces of this save did not reach; memory outside the process heap and the image (the game's heap is the process heap, research/main-menu.md, "The heap's free pages"). A write the kernel makes for a system call is not seen; with the other threads held, the call made none that failed.

- **What the world writes after the countries** (`0x7517b4` to `0x751bd3`, read 2026-11-05): some forty more sections, each a key (`0x1709280`) and an object's method `+8`, or a loop of them (`[r14+0x2408]`, `[r14+0x1e30]`, `[r14+0x1558]`, the countries again at `0x7519f7` through `0xd2f410`, and so on), then at `0x751bd3` the name of the writer's stream (`[[rsi+0x10]+0x18]`) against a 9-byte text to choose whether the AI follows, and at `0x751c87` that choice. Nothing in between reads what the stream holds or where it stands. The list above is of everything the whole world write wrote to memory that was there before, these sections' included: so while the main thread writes them, the pool's threads writing the countries and the provinces read nothing it writes but the pointer kept at `0x29cd99` (written with the value already there) and the C runtime's data behind its locks.
- **Watched again with the countries and the provinces on threads** (2026-11-05, the same save, `saving::parallel`, its seven threads left running while the others were held): besides what they wrote into blocks made during the call (their runs' buffers, the game's strings), the pool's threads wrote only their own copies of the two static objects (0x40-byte blocks of the framework's, from `0x861c55` and the other callers, and from the five inline places' stubs), the pointer at `0x29cd99` and `0x29cdcb` in the countries' 0x50-byte blocks, 3,617 times each, and the C runtime's own data: the lock of function-local statics (`[0x233c4e8]`, through `0x1a32f8a`, the first time a thread passes a static's guard), the lock and counts of its locale data when it makes a thread's data (`0x233cdd8`…, `0x1fc1d80`, `0x1a73f6c`, under `0x1a43386`, the number formatting) and the thread's fiber-local slots. No write of theirs went to `0x2458c00`, `0x2458c08` or `0x2458e90`. The main thread wrote the game's objects as before, in its own runs too.

## Where a save's zip goes

Read 2026-11-05 for S8 (docs/plans/game-speed.md), with the times of one ironman save of 1724 (Austria-37_4-1) whose countries and provinces were written on threads, from the framework log and a call trace ([A save's countries and provinces on threads](../prototype-log/2026-11-05-save-countries-provinces-threads.md)).

- **`0x5ce5f0(args)`**, under `0x74ba20` → `0x5cde60`: `args` holds the world (`+0`), the output stream (`+8`, the `.tmp` file's stream the local save opened with `0x1718300(path, 1, 0x20000)`, vtable `0x1dbfa98`), whether the save is zipped (`+0x10`) and where the result goes (`+0x18`). Its memory streams are of the class `0x1dc0358` over slices of one buffer the game keeps, `[[0x242bf50] + 0x338]`, 0x5a00000 bytes, each with a growing part (`+0x38`) for what does not fit.
- **Zipped**: `gamestate` first (`0x14e3f00` at `0x5ce8e2`, the stream named `gamestate`), then `meta` (`0x5ce9ed`, 16 KB of the buffer) and `ai` (`0x5ceadb`); each `0x14e3f00` ends with the save checksum, whose sum (`0x171f3f0`) took 44 ms for the game state's 55 MB and under 3 ms for the other two together. Then a zip of its own (`0x153c9b0` at `0x5cec2c`) into a fourth stream, 10 MB of the buffer and a growing part: `gamestate` and `meta` through `0x153b9a0` (method 8, level 3), `ai` with its local header written here and its data through `0x153c790` at level 3, and `rnw.zip` when the world has one (`[[world] + 0x2260] + 0xb0` not negative); `0x153c350` ends the zip. The zip's bytes, both parts, then go to the output stream with its write (`+0x50`, `0x5cf184` and `0x5cf1ab`), and its `+0x58` ends it. Plain: the one stream named after the file goes to the output stream instead (`0x5cf262`, `0x5cf287`).
- **The deflate** `0x153c790(zip, data, buffer, size, &crc, level)`: `deflateInit2_` with the level, raw (-15), memory level 9; it reads the data stream (its size `+0x88`, a move `+0x60`, a read `+0x20`) half a buffer at a time, deflates into the other half, takes the CRC a byte at a time over what zlib took in (`0x153c8b0`, the table at `0x1d91cd0`), and writes what came out into the zip's stream (`[zip]`, `+0x50`); it returns the bytes written, and the CRC is left inverted. At level 0, a local save's under S3, this was most of the zip's 250 ms; the framework's copy into stored blocks, with its CRC eight bytes at a step, took 45 ms for the three entries.
- **The times** of that save, 310 ms in all: the game state 152 ms (the provinces 32, the countries 45, the rest 66, before them 9), its save checksum 44, `meta` and `ai` 3, the zip 45, its bytes into the file's stream 25, and after `0x5ce5f0` 41, which was taken then for the local save's own steps and was the wait for the update thread (below). With the game's own code the same save stopped the game for 1.0 to 1.4 s.
- **The update thread** (read and traced 2026-11-05): before `0x5ce5f0`, `0x5cde60` starts a thread through TBB (`tbb_thread_v3::internal_start`) named "SaveSessionUpdateThread" when its sixth argument is set, as both local saves set it. The thread runs `0x1720880` over a closure on `0x5cde60`'s stack (`[rsp+0x20]`: the function `0x5c4460`, its argument, and at `+0x10` the byte to stop): while the byte is 0 and the function says to go on, `0x5c4460(arg)`, which calls the method `+0x40` of `[[arg]+0x58]` with 0 (the object is `0x74ba20`'s `[world+0x1e00]`'s method `+0x80`'s answer) and then `Sleep(50)`. Its calls took 60 to 170 ms each while a save was loaded. After `0x5ce5f0`, `0x5cde60` sets the byte (`0x5ce531`) and joins the thread (`0x5ce53c`, `tbb_thread_v3::join`), then lets it go (`0x1712b00`): the join waited 40 to 96 ms in four ironman saves of 1724. The size check (`0x19f6ec0`, at least 0x2800 bytes), `0x5c44f0` (the `.tmp` file opened again, not empty), the backup `0x5c5170` (a move of the old save, "Backing up save as") and the move into place took 3 ms together.

## Reading

- **The path**: `0x74b8a0` → the loader `0x5cdc60` → `0x5cf740` → `0x14e4240` → `0x14e39d0` (or `0x17068b0` for a file without a checksum) → the world's method at `+0x20`, its handler of top-level entries, `0x751cd0(world, reader, key id)` (the world's vtable `0x1cb00c8`). `0x14e39d0` reads entry after entry, skips `checksum` (`0x17099c0`), and stops at a `}` or the end.
- **The loader** `0x5cdc60(reader, &success, world, x) -> &success` writes `success = 0` first, starts a thread named "SaveSessionUpdateThread" (`0x1c8cb10`), which is handed `x` (inferred: for the progress shown), calls `0x5cf740` with `{world, reader, &success}` on its own stack (at `0x5cdd58`), waits for that thread, and returns the pointer it was given. `0x5cf740` sets `success = 0` and returns when the save's data cannot be had or read ("Failed to load meta data!" and the like); after a successful read it keeps the save's subfolders at `world+0x2450` and its name at `world+0x2430`, calls `0x7751b0` ("Initializing savegame", `gamestate.cpp`, which sets the world up from what was read), and last sets `success = 1`. That is the world read, not the interface rebuilt: an in-game load rebuilds the interface after the loader returns (main-menu.md). `saves` observes the loader (`LOAD`): a load counts as read when the loader returned the pointer it was given with `success` 1, the world pointer is still the one it read into, and no daily update is running.
- **A plain save's entries end at the AI**: the AI's case (`0x2bc3`, `0x74f6c0`) reads the block's entries and returns before its closing `}`, so `0x14e39d0` then finds a `}` and stops. Tested (2026-11-02): an entry after the AI of a plain save was never read, with no line in `error.log`. Nothing after the checksum is read as an entry either; the text tokenizer, reading on past the checksum's value, logged "Quoted string doesn't close" (`0x170df00`, `lexer.cpp:400`) once for each long string the test put there. The menu, the continue box, ironman's continue, the queued load command and a multiplayer client's received save go in at `0xd84b80`; the cloud load at `0x5d0580`; the tutorial at `0x74b330`. `meta` and `ai` are read into the same world by the same handler.
- **The checksum check**: `0x97500` (from `0x5cf740` and `0xd84b80`) takes the checksum of `gamestate` again, scanning its top-level entries without the handler. The answer is the byte at `0x233d890+1`. A mismatch never refuses the save and leaves ironman as it was; `0x96900` reports `ACHIEVEMENTS_DISABLED_MODIFIED_SAVE`, and the next save is salted as with achievements off. Besides it, only each zip entry's CRC32 is checked ("Failed to retrieve gamestate data", and the load fails).
- **The stream's sum** is the stream's method at `+0x98` (read at `0x14e33d5`, called at `0x14e33fc`). A memory stream's (`0x171f3f0`, vtables `0x1d92200` and `0x1dc0358`) shifts each 16-bit sum right by 16 when it passes 0xffff, as above; a file's stream (vtable `0x1dbfa98`, the method `0x1710c00`, which hands the file it keeps at `+0x38` to `0x170f9b0`) takes 0xffff off instead, reading the file with PhysFS from its start. Saves are written from a memory stream, and the menu's load reads the save into one; the in-game load (`0x5d0580`) reads a local save through a file's stream (`0x1710440`, at `0x5d09a3`), and a cloud save into a memory stream. So a plain text save loaded in a session never matched its save checksum, in vanilla too, and turned achievements off for the rest of that game; the framework repairs it (`repairs`). Tested (2026-11-04): before the repair, the in-game load's check returned 0 for a save the menu's load passed, and its trace showed no call of `0x171f3f0`; a save's checksum, computed with the memory stream's sum and eight zero bytes as the salt, matched what the game wrote.
- **The reader** (one class for both forms, made by `0x1709570`, vtable `0x1dbf7d0`): when the handler is called, it holds the entry's key (type at `+0x30`, text at `+0x34`), the `=` (`+0x238`) and the first token of the value (type at `+0x440`, text at `+0x444`), and the stream stands after that token: inside the block, after its `{`, when the type is 3.
- **The tokenizer** at `reader+0x28` (text: vtable `0x1dbf958`, next token `0x170e700`; binary: vtable `0x1dbf988`, `0x170ebf0`; base `0x170d1d0`, 0x220 bytes): its method at `+8` reads the next token and returns 0 at the end; the token is then at `+0x14`, its type followed by its text, `+0x10` holds the method's last result, and `+0x21c` says a token was peeked, which the method then returns without reading on. The types: 1 `=`, 3 `{`, 4 `}`, `0xc` a number (a binary i32 as its decimal text), `0xf` a string, `0x13` the end. A word the game has an id for comes as that id, with its text filled in too.
- **Skipping a block**: `0x170a4e0(reader)`, when the value is a block, reads tokens, counting `{` and `}`, up to and including the block's `}`, and records nothing. `0x17099c0(reader)` does the same from before the block. `0x1709e60` skips too but records an error on the reader (a count at `+0x18`, a flag at `+0x20`).
- **An entry the handler has no case for** goes to `0x7552bb`: it asks the content registry (`0x7e2d40`, a lazily made global) for a script object named by the key (`0x8e9f0` with the key's text, read at `0x7552c3`); one found reads the value; otherwise `0x1709dd0` records an error ("Unexpected token", `savegamehelper.cpp:290`, one line in `error.log`) and skips the value. Either way the handler returns through `0x752d61`. A save with errors is still read (`0x14e4240` returns 1), but the fix-up after reading (`0x755c20`, the world's method at `+0x30`, which among other things gives a country an inconsistent tag at `+0x18f0` as `---`) is skipped. In a file without a checksum it is `0x17068b0`'s "Parsing Error … Unexpected token" (`persistent.cpp:88`) instead.
- **Strings**: the binary tokenizer returns an empty string for one of 512 bytes or more; the text tokenizer, for a quoted string longer than 511 bytes, logs "Quoted string longer than max length (512)" and returns it empty; words are cut at 511 bytes.

## What the framework does (ADR extension-save-data-in-the-save)

- **Writing**: a jump at `0x751c87`, where the world has written its game state and the AI may follow. When some extension has data and the writer's depth is 0, it writes with the writer's own functions:

  ```text
  eu4_harmony={
      version=1
      data={
          "<the data as JSON, in base64, at most 500 bytes a string>"
      }
  }
  ```

  In a zipped save the entry comes last in `gamestate`, just before the checksum; in a plain one before the AI. The key, `version` and `data` are written as type `0xf`, so in binary as strings; `1` as type `0xc`. Tested (2026-11-02): the plain, zipped text and ironman saves the game wrote held the entry there, each with a checksum that took it in, and read back; a save the game wrote with the 8-byte salt and the entry passed the game's own check.
- **Reading**: a jump at `0x7552bb`. When the reader's key is `eu4_harmony` and its value a block, the framework reads the block's tokens as `0x170a4e0` reads them, up to and including its `}`, and the handler returns through `0x752d61`: no error is recorded, and the fix-up runs. Any other entry goes on to the content registry as before; the stub calls it with the game's own next instruction as the return address. The data counts only while the loader runs, and is kept once the loader says the save was read into the current world.
- **Not settled**: why the 8-byte salt was eight zero bytes in the runs of 2026-11-04; an ironman game that keeps achievements on, carrying the entry (only a normal game's save was checked so); whether a client without the framework that receives a hot-join save with the entry goes out of sync; whether a zipped save loaded in a session reads its entries through a file's stream; the places writers are made were looked at only in part.
