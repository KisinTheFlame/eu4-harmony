# Time: speed, pause, the daily update, questions waiting, restarting (for `game::time`)

Baseline 1.37.5. All addresses are RVAs. Read from `eu4.exe` with `core/examples/disasm.rs`; what was checked in the running game is marked "tested", from [prototype-log.md](../prototype-log.md) (2026-10-29, remote control C1). Tested also: the speed read and set showed on the top bar's speed dial; the in-game menu, its confirmation to return to the main menu and the end-of-game summary do not hold the game paused once it is resumed. The daily update and the pause predicate were first read while regional-combat was developed (2026-10-26) and checked again with `core/examples/disasm.rs` on 2026-11-03; what was seen in the running game then, before the framework existed, is marked so and is not in the log.

## The speed

- **The world's speed** is an i32 at `world+0x1e08`, 0 to 4, shown to the player as speeds 1 to 5. The speed setter `0x7579f0(world, index)` clamps the index to 0..=4, stores it there and logs `Gamespeed is now <index+1>`.
- **The speed commands** call that setter: the speed-up command's execution `0xb79970` sets `[world+0x1e08] + 1` (its constructor `0xb79920`: vtable `0x1cea1d8`, type `0x165`); the slow-down command's `0xb79ab0` sets `[world+0x1e08] - 1` unless the map manager's method at `+0x3f8` says otherwise at speed 0. Their types, as their `+0x50` answers, are `increase_game_speed` (`0x28db`) and `decrease_game_speed` (`0x28dc`), and they carry nothing of their own, so their written forms are `increase_game_speed={ }` and `decrease_game_speed={ }`. Since 2026-11-03 `time.set_speed` posts one of them for each step, through the command layer (ADR 0035); tested: from speed 1 to 5 and back to 2, paused and running ([prototype-log.md](../prototype-log.md)).
- **How fast days go**: the time step `0x757ad0(world, seconds)`, called by the map manager's frame `0x8137c0` when the game is not paused, adds the frame's seconds up and, once they pass the speed's threshold (the floats at `0x1c33e30`: 2.0, 1.0, 0.5, 0.2 and 0.0 seconds a day for speeds 1 to 5), posts one `DailyTick` command (the game's name for it; vtable `0x1cea280`, id `0x28d6`) through the command dispatch `0x14ca2d0` and starts adding up again. So at most one day is posted a frame; at speed 5 one every frame.
- **The `DailyTick` command** executes `0xb79520` (`timercommands.cpp`), which logs "DailyTick without gamestate" and does nothing without a world, and otherwise calls the daily update `0x758430(world)` (at `0xb795da`; below). The date moves on by 24 inside it.
- **The game console's `gamespeed <n>`** (`0xe913a0`) calls the setter with `n` as the index (so `gamespeed 3` is speed 4), then toggles the pause: on when the index is 0 and the game runs, off when it is above 0 and the game is paused.

## The daily update

`0x758430(world)` runs one day. What it runs, in order, is in [architecture.md](architecture.md) ("Time"); here is what the framework relies on:

- At `0x7584a2` it sets `world+0x1e10` (u8, `world::DAILY_UPDATE`), and at `0x758eee`, before it returns normally, clears it. So the flag is set exactly while a day runs; the map manager's frames that run inside the day (architecture.md, "Frames inside a day") see it set.
- At `0x7584f9` it adds 24 to the date (`world+0x1dd0`, hours, [dates.md](dates.md)), before anything of the new day runs, and 24 to `world+0x1dd4` too. It then keeps the date's parts beside it: the year at `+0x1ddc`, the day of the month (from 0) at `+0x1de4`, the month (from 0) at `+0x1dec`, and at `+0x1df0` the days since the calendar's epoch, `(date − 0x29c55c0) / 24` rounded down.
- At `0x758aef` it calls the day's body `0x75bbe0`.
- So a hook on its entry sees the old date, one in the middle the new date with the day half done, and only its return a day that is over. The framework observes both ends (`DAILY` in `game::events`): the entry makes visibility stale ([fog-of-war.md](fog-of-war.md)), and the return is where `game::time` pauses at a date (below).

Each unit's daily update is `0xd3e110` (`unit.cpp`, logging "CUnit::DailyUpdate - Start, %u, %u, %d"), which an army's method `+0xd0` (`0x1a2d30`, vtable `0x1c42540`) calls first. It runs inside its country's daily update, one army after another, so when one army's update returns others of the same day may not have run yet.

Seen in the running game on 2026-10-26, before the framework existed, with the army panel closed: the map manager's frame, the `DailyTick` command and the daily update all ran on one thread, the thread of the fog refresh; across one daily update the date went from 56679696 to 56679720 and `+0x1df0` from 536654 to 536655, with `+0x1e10` clear at the return; the map manager's frame ran while paused, and ran nested inside daily updates, with `+0x1e10` set. So the frame's return alone is no point between days: `game::context` answers "not ready" while `world+0x1e10` is set, and `saves` counts a load as read only when it is clear.

## Pausing

The map manager's pause state is at `map_manager+0x418` (the manager's method at `+0x100`, `0x8024d0`, returns it; its owner at `+0x50`). It holds:

- `+0x00`/`+0x08`: begin and end of a vector of pointers, **the windows holding the game paused**. `0x7e0a20(state, window)` adds one if it is not there yet. An event window adds itself in its constructor when the game pauses on events (the byte at `[0x242bde8]+0x256`, set by the settings' `autopause_on_events_button`), and its destructor `0x10ba030` takes itself out (`0x1aa090`). The other callers of `0x7e0a20` (`0x820990`, `0x8c07b0` in `messagehandler.cpp`, `0x118a8e0`, `0x118b8b0`, `0x11c4390`, the peace offer and demand windows at `0x1307aa0` and `0x1307d90`, `0x130a4a0`, `0x1347a50`) were not all identified.
- `+0x48`: **the player's pause** flag (u8); `+0x28`: the name of who paused.
- **Paused** (`0x7e01b0(state)`, existing dependency point; the code at `0xb7f87b` asks it to choose between the texts `GAME_PAUSED` and `GAME_UNPAUSED`): the flag, or a window in the vector unless the helper `0x6eaa10(map manager)` (the manager from `state+0x50`) tells it to leave the windows out. The helper answers no when the manager's method `+0x318` (`0x80ff80`, the byte at `manager+0x19f1`) is clear, as in single player; otherwise it answers yes when the session (the manager's method `+0x80`, `0x811aa0`) has neither of its bytes `+0x54` and `+0x55` set, or when some entry of the list at `world+0xa50` (next at `+0x60`) holds at `+0x18` another value than the session's `+0x8c`, and no when all of them hold it. What those fields mean in multiplayer was not worked out. Seen in the running game on 2026-10-26, before the framework existed: the predicate's result matched this reading every time it was called.
- **The pause toggle** `0x7e0250(state)`, which the game console's `gamespeed` uses: when the flag is set, or windows hold the game paused, it clears the flag and the vector (resuming lets go of every window, which stays open); otherwise it sets the flag and the name (the player's). It plays no sound and writes no log line. So it never sets the flag while windows hold the game paused: `game::time` then toggles twice, which lets the windows go and sets the flag. The windows taking themselves out later find themselves gone: `0x1aa090` removes a pointer only when it is there.
- **The pause command** (execution `0x848970`, MP-safe): with its "pause only" byte (`+0x71`) it calls the pause `0x7e02d0` ("Game paused by …", a cooldown timer for multiplayer), which sets the flag beside any windows holding the game; otherwise it toggles: the unpause `0x7e0770` ("Game unpaused.", the `unpause` sound, the vector cleared) when the flag is set, else the pause. The player's pause key and button go through `0x810570` (called from `0x816b73`, `0x82493f`, `0x143777b` and `0x80f382`), which posts this command only when the in-game lobby at `map_manager+0x12e0` has its multiplayer byte `+0xbb` set (set on the hot-join path at `0x84379b`); otherwise it calls the toggle `0x7e0250` itself, at `0x8107f6`. So in single player, pressing pause while only windows hold the game resumes it, and pressing again sets the player's pause: `game::time`'s double toggle is those two presses. This is read from the code; pressing the key in that state was not tried in the game.

## The player's resuming, and the end date

The pause key's function `0x810570(map manager, …)`, when the game is paused, refuses to resume it (returns without toggling) in two cases, before anything else:

- **Past the end date**: `[world+0x1dd0]` (the date) above the i32 at `0x1fc2328` (the end date, 1821.1.2 in the unmodded game), unless the u8 at `world+0x1dd8` is set. The same test in the map manager's frame (`0x814b51`) then shows the end-of-game summary (`0x1089820(…, 1)`) unless it is open, and sets the player's pause (`pause state+0x48`) at every frame; `0x6ec87a` makes the same test. `world+0x1dd8` is set to 1 by `0x1088fb0`, a method of the end-of-game summary, when its `+0x1d0` is 1 (inferred: the summary the end date opened, closed to play on), and cleared by `0x74a260` and `0x74c8b0`. So past the end date time runs only once the player closed that summary; until then remote control's `time.resume` and `time.advance` refuse too (`rejected`, "the game is over"). Tested (Z1), with a save dated 1821.1.1: an advance at speed 1 found the game paused at 1821.1.3, the end-of-game summary up (1444.11.11 to 1821.1.3), and resuming refused; once the summary's lower button (继续, continue) was clicked, resuming ran the game to 1821.1.4, so closing the summary with that button sets `world+0x1dd8` (seen in what it lets time do; the flag itself was not read). Which of the two buttons the other is, and what `0x74a260` and `0x74c8b0` are, was not looked at.
- **No country**: the player's tag not valid (its byte `+7`, `world+0x1e67`, or `world+0x1e6f` while switched, as `objects::campaign::world` names them) and the byte at `world+0x74dc` clear (inferred: a game that lets an observer run time). Remote control's time capabilities need a player country (`game::context`), so they refuse every observer, whatever that byte says.

## Stopping on a date

Since one day is posted a frame and the frame checks the pause before posting, pausing as soon as the daily update returns with the date reached means no further day begins. `game::time` pauses there, after `0x758430` (an `after` observer on the existing daily update point), when remote control's advance holds a stop at that date, and also when a question's event window came up during the day while an advance runs.

Pausing at a safe point instead is a day late at speed 5. Tested: an advance that paused the game at the safe point where it found a question's event window answered 1470.9.22, and the game then stood at 1470.9.23: the next day had been posted before the safe point and ran after it. With the pause at the end of the daily update, the same advance answered 1470.9.22 and the game stayed there, and advances of 30 days at speeds 5 and 1 stopped on their dates.

## Questions waiting for an answer

- The map manager's method at `+0x108` (`0x828c00`) shows one of the game's events to the player: it makes an event window (`0x10b9a50`, 0x3e8 bytes, vtable `0x1d590f8`, a second one `0x1d590e0` at `+8`; `eventwindow.cpp`, `EventWindow`) and adds it with `0x6ecae0(manager, window)` to the manager's **popups**.
- **The popups** are a list of the game's usual kind (`objects::list`) at `map_manager+0x78`: the first node, `+0x80` the last, `+0x88` the count and `+0x8c` a byte set while the list is being walked. A node is 0x20 bytes: `+0x00` the window, `+0x08` the previous node, `+0x10` the next, `+0x18` a byte set when the window closed while the list was being walked (the node goes later). Each frame `0x6ea380` asks every window whether it is still open (its method at `+0x18`) and takes the closed ones out.
- So **the questions waiting** (GLOSSARY: the game's events waiting for the player's answer) were, to C1, the nodes whose window has the event window's vtable and whose `+0x18` is clear. Tested: a question shown during an advance was counted (in front of battle and message popups), and once its option was clicked it was not.
- Since C7, `game::time` counts them as the questions (docs/research/questions-and-offers.md): such a window that is still open (its `+0x124`; choosing an option clears it, while the node stays until the next frame) and whose question the world still holds among the game's pending events, so that an advance stops on exactly the questions `question.list` lists.

## Returning to the main menu

- The application's run `0x14c2d00` loops over frames (`0x14c25a0`) while neither `app+0x83` (quit) nor `app+0x2f8` is set, then shuts the game down, and, when `app+0x84` is set, calls **the restart** `0x14c3a10(app)` (`application.cpp`), which starts `eu4.exe` again with `CreateProcessA` (log `Failed to restart process: ` on failure) and returns; the process then ends. Returning to the main menu ends this way (docs/research/safe-points.md).
- `game::time` observes the restart (before it runs) so that remote control answers what waits while this process can still write to the pipe. Tested: the observer ran 0.1 s after the end-of-game summary's exit button was clicked, an advance waiting on the pipe got its answer there, and the new process started 0.3 s after; nothing in between needed the 2 s the engine allows the transport.
