# 常驻提示窗口：宿主窗口与生命周期的静态研究

日期 2026-10-27。对象：原版 1.37.5 `eu4.exe`（SHA-256 `9ad3efe1af169f40ee577f9dae5debbc87af6fb8b5450fb345ebf110dc4d771a`，映像基址 `0x140000000`）。下文地址都是 **RVA**。

方法与 `ui-injection.md` 相同，只做静态分析，没有启动游戏或附加进程：

- Ghidra 12.1.4 headless 以 `-readOnly -noanalysis` 打开，只对选定函数做反编译或线性反汇编；
- 字符串、RIP 相对引用、`E8` 直接调用、vtable 里的函数指针、`.pdata` 函数边界由自写脚本扫描；
- 本次没有开 REA 会话，直接用了 REA 配置的同一份 Ghidra。

标 **已验证** 的，是在反编译或字节里直接看到的；标 **推断** 的，是根据结构作出的判断。伪代码的函数原型都是暂定。

## 结论

**可行。推荐宿主是顶栏窗口 `topbar`（`interface/topbar.gui`）。** 宿主和生命周期这部分把握高；显示位置和滑出动画需要运行时确认。

- **CreateWindow 原型**（已验证）：`Window* CreateWindow(GuiManager* mgr, const std::string* name)`，只有两个参数，名字是 MSVC `std::string`。只有按名查找元素的 `+0x68/+0x98/+0xc8` 才收 `const char*`。
- **根指针位置**（已验证）：`topbar` 的根窗口由游戏内 idler 创建。这个 idler 就是框架里的 `MAP_MANAGER`，即 `*(world+0x1e00)`，vtable `0x1cb8460`，源文件 `ingameidler.cpp`。它在 RestoreDeviceObjects 中建一个 0x6e0 字节的顶栏对象，根指针在 `*(*(idler+0x12d8)+0x658)`。
- **生命周期**：每局游戏建一次，也就是每个游戏内 idler 一次（推断）。`reload` 该 idler 关注的任一 `.gui` 文件时，根窗口会被销毁重建，指针会变（已验证）。
- **类型通用**（已验证）：CreateWindow 建出的根都是同一个类（0xa80 字节，构造 `0x1543f80`，vtable `0x1d926b0`，`+0x30` 处 `0x1d929d0`）。军队面板用的查找、显隐方法和可见字节，对 `topbar` 根同样适用。
- **销毁挂钩点**（已验证）：所有路径都汇到根窗口的 Kill，即 `0x1547520`（根 vtable `+0x130`）。
  - Kill 只置标记 `root+0xf4=1`，并级联标记子元素；内存要等 GUI 管理器每帧清扫 `0x14e9fa0` 时，经 `0x1546510` 才释放。
  - `0x6ecc80` 不负责销毁，只把根从 idler 的每帧更新链表里摘掉。
- **越界子元素**：静态上没有找到按父窗口 `size` 裁剪子元素的代码，鼠标命中按每个元素自己的矩形判定（部分已验证），与军队面板的运行时现象一致。

## 1. CreateWindow 的调用约定

GUI 管理器单例是 `*0x23494f0`，EU4 子类的 vtable 为 `0x1d58108`，基类为 `0x1d8dc40`。`+0x48` 槽位是 `0x14e9030`。

**反汇编（已验证）**：

1. `rcx`（mgr）存进 `rdi`，`rdx`（name）存进 `rbx`。
2. 调用 `(mgr+0xc8)->vtbl[+0x08](mgr+0xc8, name)` 查类型库，此时 `rdx` 仍是同一个 `std::string*`。
3. 查不到时：
   - 读 `name+0x18`（capacity）：大于等于 0x10 就取 `*name` 作为堆指针，否则用内联缓冲区；
   - 写日志 `Failed to create window "%s"`（`gui.cpp` 第 0x16f 行）；
   - 返回 0。
4. 查到时：
   - 调用 `0x155c260(proto, *(mgr+0xc0), mgr, *(*(mgr+0xc0)+0x490), 0)`。它固定分配 0xa80 字节，并调用构造 `0x1543f80`；
   - 然后调用 `mgr->vtbl[+0x98](mgr, win ? win+0x30 : 0)`（`0x14eb360`）登记；
   - 返回 `win`。

**参数与返回值**：

- `r8`、`r9` 在入口后都先被改写才使用（`0x14e9078`、`0x14e90a0`、`0x14e90b2`），所以**没有第三、第四个参数**。
- 返回值是窗口主对象的指针（偏移 0）。登记给管理器的是 `win+0x30`，即 GUI 子对象。
- CreateWindow 只读名字字符串，不修改也不释放；调用者事后自行释放临时字符串（已验证）。
- 推断：框架可以自己构造 32 字节的 `std::string` 传入。名字不超过 15 字节时用内联缓冲区，不需要游戏的分配器。

**调用点**（全部已验证）：

| 调用点 | 窗口名 | mgr 取自 | 名字字符串 |
|---|---|---|---|
| `0x144fb00` 军队面板 | `single_unitpanel` | `*(*(panel+0x48)+0x58)` | 栈上临时 `std::string`，16 字节走堆（size 0x10，cap 0x1f） |
| `0x1431020` 顶栏构造 | `topbar` | 全局 `*0x23494f0` | 顶栏对象成员 `+0x660` |
| `0x149ad00` 窗口持有者重建 | 持有者自己的名字 | 全局 `*0x23494f0` | 持有者 `+0x10` |
| `0x1431a80` 顶栏绑定 | `speed_controls` | `*(*(topbar+0x648)+0x58)` | 临时 |
| `0x81af10` 游戏内 RestoreDeviceObjects | `status_message_window`、`message_icons`、`countryview`、`alerts_parent`、`hotkey_assign_parent`、`macro_build_interface`、`menubar` | `*(idler+0x58)` | 临时，经 `0x95110(str, literal, len)` 赋值 |
| `0x82b470` 游戏内 GUI 重载 | `menubar` 等 | `*(idler+0x58)` | 临时 |
| `0x10d5bc0` 主菜单 RestoreDeviceObjects | `country_selection_panel` | `*(frontend+0x58)` | 临时 |

`*(idler+0x58)` 与全局 `*0x23494f0` 是同一个管理器（推断，依据是全程只建了一个 GUI 管理器）。

**与旧记录的对应**：regional-combat 笔记说 "Root creation uses a DIFFERENT slot and an engine string"。所说的槽位是**管理器**的 `+0x48`，不是根窗口的槽位；"engine string" 就是 MSVC `std::string`。两者没有矛盾。

另外注意：根窗口自己也有收 `std::string*` 的槽位，用来找**子窗口**（不是元素），不要与上面混淆：

- `+0x180`（`0x1548190`）只是尾跳到 `+0x1c0`；
- `+0x1c0`（`0x15481a0`）原型为 `(root, const std::string* name, bool warn)`。它在 `root+0x958..+0x960` 的子窗口表中查找，表项 0x28 字节，`{std::string 名字, Window*}`。找不到时返回 0；`warn` 为真时还写日志 `Attempt to access nonexistent subwindow`；
- 军队面板用 `+0x180` 取 `mission_settings_win`，顶栏用 `+0x1c0`。

## 2. 常驻宿主：`topbar`

### 2.1 指针链与校验（已验证）

```
world  = *(0x233fe78)
idler  = *(world + 0x1e00)        vtable 0x1cb8460；也就是 MANAGER_FRAME 0x8137c0 的 rcx
topbar = *(idler + 0x12d8)        vtable 0x1d84250，0x6e0 字节
root   = *(topbar + 0x658)        vtable 0x1d926b0；root+0x30 处 vtable 0x1d929d0
```

**顶栏对象的字段**（vtable 只有一项，即删除析构 `0x14317c0`）：

| 偏移 | 内容 |
|---|---|
| `+0x648` | 构造时传入的 idler |
| `+0x650` | 窗口持有者开始：根当前登记到的 idler（owner）。构造时为 0，由 `0x1431a80` 填入 |
| `+0x658` | 持有者 `+0x08`：`topbar` 根窗口 |
| `+0x660` | 持有者 `+0x10`：`std::string "topbar"` |
| `+0x680` | `speed_controls` 根窗口，由 `0x1431a80` 创建 |
| `+0x688` | `timeline_controls` 辅助对象：0x290 字节，vtable `0x1d84238`，自带根在 `+0x30` |
| `+0x698`、`+0x6a0` | 经 `root->vtbl[+0x1c0]` 取到的子窗口 |

**游戏内 idler 的相关字段**：

| 偏移 | 内容 |
|---|---|
| `+0x58` | GUI 管理器 |
| `+0x90` / `+0x98` / `+0xa0` / `+0xa4` | 每帧窗口链表：头、尾、计数、"正在遍历" 标志 |
| `+0x3d0` | GUI 重载监听者，vtable `0x1cb88b8`，`+0x10` 槽是 `0x82b470` |
| `+0x460` | "游戏内重新读档" 标志 |
| `+0x12d8` | 顶栏对象（unique_ptr） |
| `+0x1178` | `menubar` 根 |
| `+0x10d0` / `+0x10d8` | `alerts_parent` / `hotkey_assign_parent` 根 |
| `+0x1148` | `status_message_window` 根 |
| `+0x16f0` | `countryview` 根 |

**`world+0x1e00` 何时变化**：它由 `0x756a30(world, idler)` 写入（已验证）。调用者有：

- idler 构造 `0x803270`；
- 游戏内 RestoreDeviceObjects `0x81af10`；
- 主菜单 RestoreDeviceObjects `0x10d5bc0`，传入的是循环清零用的 `r15`，推断为 0。

推断：在主菜单里 `world+0x1e00 == 0`，指针链会在第一步断开。更稳妥的做法是直接用 `0x8137c0` 钩子的 `rcx` 作为 idler。

**建议每帧校验**：

- `*(idler)==0x1cb8460`、`*(topbar)==0x1d84250`、`*(topbar+0x648)==idler`；
- `root!=0`、`*(root)==0x1d926b0`、`*(root+0x30)==0x1d929d0`；
- `root+0xf4==0`（没有被 Kill）；
- 可选：`topbar+0x660` 处的字符串等于 `topbar`。

### 2.2 创建（已验证）

1. **入口**：游戏内 RestoreDeviceObjects 是 idler vtable `+0x30` 上的 `0x81af10`，日志为 `Start RestoreDeviceObjects`。
2. **重置窗口链表**：函数开头调用 `0x1400d0020(idler+0x90)`。
3. **建顶栏对象**：在 `idler+0x460 == 0` 分支里：
   - 先建 `alerts_parent`、`hotkey_assign_parent`；
   - 再 `new(0x6e0)` 并构造 `0x1431020(topbar, idler)`；
   - 结果放进 `idler+0x12d8`。先换入新对象，再删除旧对象。
4. **顶栏构造 `0x1431020`**：
   - 把 `"topbar"` 赋给 `+0x660`；
   - 调用 `root = (*0x23494f0)->vtbl[+0x48](mgr, topbar+0x660)`，结果存进 `+0x658`；
   - 根非空时：调用 `(root+0x30)->vtbl[+0x88]()` 显示，再调用 `root->vtbl[+0x50](root, 1)`；
   - 最后调用 `0x1431a80(topbar)`。
5. **绑定 `0x1431a80`**：
   - 把根登记到 idler：对原 owner 调用 `0x6ecc80`，对新 idler 调用 `0x6ecbd0`，owner 记在 `+0x650`；
   - 用 `+0x68`、`+0xc8` 等方法查找按钮并订阅；
   - 新建 `speed_controls` 根（`+0x680`）和 `timeline_controls` 对象（`+0x688`）。
6. **重新登记**：无论走哪个分支，`0x81af10` 随后都调用 `0x149ade0(topbar+0x650, idler)`，把根重新登记进刚清空的窗口链表。

**`topbar.gui` 的定义**：

- `fullScreen = yes`，`size = 2048×100`；
- 有 `show_position {0,-1}` 与 `hide_position {0,-165}` 两个动画位置。

原版嵌套的 `pause_window` 写的是 `Orientation = "CENTER_UP"`、`x=-203`（宽 406 的一半），实际居中显示。推断：`topbar` 内子元素的方位锚点是全屏的顶栏，也就是屏幕。

### 2.3 何时重建、何时销毁

**新开或读入一局（从主菜单进入）**：

1. 主菜单 `0x10da520`（`frontend.cpp`）`new(0x5bc8)` 并构造 idler（`0x803270`），然后调用 `0x14c2530(app, &idler, 0)` 排队切换。这一步已验证。
2. 应用帧 `0x14c25a0` 在 `app+0x48` 置位时执行切换（已验证）：
   - 旧 idler 依次调用 `+0x50`、`+0x38`（InvalidateDeviceObjects）；
   - 除非 `app+0x80` 置位，否则删除旧 idler；
   - 新 idler 放进 `app+0x40`，依次调用 `+0x48`、`+0x28`、`+0x30`（RestoreDeviceObjects，顶栏在这里创建）。

结论：**每局游戏，即每个游戏内 idler，建一次，不是每次运行程序只建一次。**

**回到主菜单**：

1. 切到主菜单 idler 时，旧 idler 调用 `+0x38`，即 `0x81e8f0`。这一步是推断：切换机制已验证，但"回主菜单走这条切换"是推断。
2. `0x81e8f0` 先把 `idler+0x12d8` 置 0，再删除顶栏对象（已验证）。
3. 删除过程：`0x14317c0` → `0x14318c0`（Kill `speed_controls` 等）→ `0x149aca0(topbar+0x650)`（已验证）。

**游戏内重新读档**：

- 函数 `0x5d0580` 带云存档字符串，调用者是一个命令对象和调试命令 `0xe95610`。推断它是不经主菜单、在游戏内读档的路径。
- 它先置 `idler+0x460=1`，读档后直接调用 `0x81af10`，再把 `+0x460` 清零（已验证）。
- 在这条路径上，**顶栏对象和根都不重建**，根只重新登记，指针不变。

**GUI 重载**（已验证）：

1. **登记监听者**：idler 构造时用 `0x14e0d90` 把 `idler+0x3d0` 登记为以下文件的重载监听者：`interface/main.gui`、`topbar.gui`、`menubar.gui`、`macrobuildinterface.gui`、`macrobuildinterface_override.gui`、`papacy.gui`、`great_powers.gui`、`parliament.gui`、`mapmode_more.gui`、`more_interface.gui`、`unitpanel.gui`、`outliner.gui`、`core.gui`。
   - `topbar.gui` 一项在反汇编 `0x80a4dd`（`lea rbx,[rsi+0x3d0]`）处直接看到；
   - 其余各项按字符串邻近关系判断。
2. **控制台 `reload <file>`**：`0x14e1140` 先重读文件，然后按路径在全局表 `*0x242bf58` 中找监听者，调用 `listener->vtbl[+0x10]`。对 idler 来说就是 `0x82b470`。
3. **`0x82b470` 对顶栏的处理**：
   - `0x14318c0(topbar)`；
   - `0x149ad60(topbar+0x650)`：记下旧根的 `+0xf5`，再调用 `0x149aca0` 销毁旧根、调用 `0x149ad00` 重建 `topbar` 根，最后重新登记；
   - `0x1431a80(topbar)`。

   **根指针会变。** 无论重载的是上面哪一个文件，都会走到这里。

**控制台 `reloadinterface`（无参数）**：`0xe590d0` 只调用 `0x81ecf0(idler)`，重建 `idler+0x1110` 下的 14 个视图对象，不碰顶栏（已验证）。

**显卡设备重置**（切出全屏、改分辨率）是否也会走 Invalidate/Restore：没有找到对应路径，未验证。Kill 钩子能覆盖这种情况。

**滑出与可见性**（已验证）：

- 根 vtable `+0x298`（`0x1547c60`）把窗口动画移到 `hide_position`，`+0x288`（`0x1547ec0`）移回 `show_position`。
- 以下情况会把 `topbar`（和 `menubar` 等）滑出：
  - 切到地图模式 0x25（`0x821ff0`）。`timeline_controls` 只在 0x25 下显示（`0x1430510`），推断 0x25 是时间线模式；
  - `0x81fdc0` 的两个调用者：`0x145b160`（军队重组窗口）和 `0x1170ba0`（未识别）。
- 滑回由 `0x81ffb0` 完成。
- 滑出时子元素会随顶栏一起离开屏幕。`+0xf5` 是否因此改变，未确认。

## 3. 销毁路径与挂钩点

### 3.1 `0x6ecc80(idler, root)`（已验证）

- 第一个参数是**游戏内 idler**，不是 GUI 管理器。军队面板析构里写成 `*(world+0x1e00)`，顶栏里是 `*(topbar+0x648)`。
- 它在 `idler+0x90` 的链表里按**指针比较**找到 `root` 的节点：
  - 节点 0x20 字节：`{root, prev, next, removed 字节}`；
  - `idler+0xa4` 非 0（正在遍历）时，只把节点 `+0x18` 置 1；
  - 否则摘链、释放节点、计数减一。
- 它**不读 root 的内容**，所以对已经 Kill 的根调用也安全。
- 对应的登记函数是 `0x6ecbd0`，有 71 个直接调用点；这张链表就是 idler 的"每帧窗口更新表"。基类的帧函数 `0x6ea380` 遍历它：
  - 对未 Kill 的根调用 `root->vtbl[+0x238](root, dt)`，即 `0x1546ac0`；
  - 把已 Kill（`+0xf4` 非 0）的根用 `0x6ecc80` 摘掉。
- 它**不是** CreateWindow 窗口的通用拆除路径。CreateWindow 只把窗口登记到 GUI 管理器，是否进入 idler 链表由拥有者决定。

### 3.2 根窗口 Kill：`root->vtbl[+0x130]` = `0x1547520`（已验证）

- 先置 `root+0xf4 = 1`。这个字节是 GUI 子对象的 `+0xc4`，即 "已死亡" 标志；紧挨着的 `+0xf5` 是可见标志（GUI `+0xc5`）。
- 对各类元素表中的每个子元素调用 `child->vtbl[+0x78]`。元素表包括 `+0x5b8`、`+0x5e8`、`+0x618`、`+0x648`、`+0x678`、`+0x708`、`+0x738`、`+0x768`，以及几张散列表；按钮的 `+0x78` 是 `0x15aea30`，它置 `button+0xc4 = 1`。
- 对子窗口表 `+0x958` 中每个子窗口递归调用 `+0x130`。
- 对背景元素 `+0x520` 调用 `+0x78`。
- **不释放内存。**
- GUI 子对象的 `+0x78` 是 `0x1547910`，它做 `rcx -= 0x30` 后跳到 `root->vtbl[+0x130]`。所以经 GUI 子对象 Kill（如 `0x81e8f0` 对 `alerts_parent`）也会汇到 `0x1547520`。

### 3.3 真正释放（已验证）

- GUI 管理器的更新 `0x14e9fa0(mgr, dt)` 遍历 `mgr+0x110`（`0x14eb360` 登记的全部对象），对 `+0xc4` 非 0 的对象调用 `obj->vtbl[+0x38](obj, 1)`。
- 对根来说，这一项是 `0x15503cc`：`rcx -= 0x30` 后跳到 `0x1546510`。`0x1546510` 调用析构体 `0x1546730`，再 `free(root, 0xa80)`。
- 窗口构造 `0x1543f80` 用 `mgr->vtbl[+0x98]` 逐个登记子元素和子窗口，所以它们在同一次清扫中各自释放。框架现有的 `BUTTON_DESTROY 0x10b5670` 就是按钮类的 `+0x38`。
- `0x14e9fa0` 由 `0x14c5810` 在末尾无条件调用。`0x14c5810` 又由游戏内 idler 帧 `0x8137c0`（`0x815914` 处）、主菜单帧 `0x10d2e80` 和 `0x1253d80` 调用。
- 结论：**从 Kill 到释放，至少隔到同一帧稍后的清扫。** 而且清扫发生在 `0x8137c0` 返回**之前**。

### 3.4 各拆除路径都经过 Kill（已验证）

| 路径 | 顺序 |
|---|---|
| 顶栏持有者 `0x149aca0`（顶栏析构、GUI 重载） | `0x6ecc80` → GUI 隐藏 `+0x90` → `+0x130` → `holder.root = 0` |
| 军队面板析构 `0x144f560` | `0x6ecc80(*(world+0x1e00), root)` → `+0x130` |
| `0x82b470` 重建 `menubar` | 隐藏 → `+0x130` → `0x6ecc80` |
| `0x81e8f0`（回主菜单） | 删顶栏对象（走持有者），其他根用 GUI `+0x78` |
| 主菜单 `0x10d8330` / `0x10dcb00` | 隐藏 → `+0x130` |

**派生窗口类**：`0x10a1dd0`（另一个窗口类的 `+0x130`）也跳到 `0x1547520`，`0x10a1cb0` 调用 `0x1546730`。那是别的工厂建的派生类，不影响 CreateWindow 的根。

### 3.5 推荐挂钩点

1. **主挂钩点**：在 `0x1547520` 入口挂观察钩子，`rcx` 是窗口指针。
   - 若等于已绑定的根，就立即解绑：退订按钮信号、清除对象指针。
   - 此时根和子元素的内存都还有效，解绑安全。
   - 子窗口被递归 Kill 时也会触发，按指针过滤即可。
2. **兜底**：在 `0x1546510` 入口再挂一个，`rcx` 是窗口指针，也来自 `0x15503cc` 这个 thunk；或者沿用 `BUTTON_DESTROY` 这类元素析构钩子。
3. **不要**用 `0x8137c0` 的 after 钩子来发现销毁：那时清扫已经做完，元素已被释放。

## 4. 在其他根上查找（已验证）

**`0x155c260` 不按原型挑选类**：它总是分配 0xa80 字节并调用 `0x1543f80`。构造函数一开始就无条件写入 `*root = 0x1d926b0`、`*(root+0x30) = 0x1d929d0`。嵌套的 `windowType` 也经 `0x155c260` 建出，属于同一个类，放在 `root+0x958` 子窗口表里。

**`0x1d926b0` 就是通用窗口类的 vtable**，`ui.rs` 里的 `ROOT_VT` 和 `ROOT_GUI_VT` 校验对 `topbar` 根同样成立。相关槽位：

| 槽位 | 函数 | 作用 |
|---|---|---|
| 根 `+0x00` | `0x1546510` | 删除析构（0xa80） |
| 根 `+0x68` | `0x1548700` | 按 `const char*` 找按钮。依次查 `+0x5b8/+0x5d0`、`+0x618/+0x630`、`+0x5e8/+0x600` |
| 根 `+0x98` | `0x1548d30` | 按 `const char*` 找即时文本框（`+0x708/+0x720`） |
| 根 `+0xc8` | `0x15492e0` | 按 `const char*` 找图标（`+0x648/+0x660`） |
| 根 `+0x130` | `0x1547520` | Kill |
| 根 `+0x1c0` | `0x15481a0` | 按 `std::string*` 找子窗口 |
| 根 `+0x238` | `0x1546ac0` | 每帧更新（由 idler 链表调用） |
| GUI `+0x38` | `0x15503cc` | 删除析构的 thunk |
| GUI `+0x78` | `0x1547910` | Kill 的 thunk |
| GUI `+0x88` | `0x1547d90` | 显示：置 `+0xc5=1`，即 `root+0xf5` |
| GUI `+0x90` | `0x1547b00` | 隐藏：置 `+0xc5=0` |

注意：

- 三个查找方法**只查根自己的直接子元素**，不会深入子窗口。拼接时元素要放在 `topbar` 的 `windowType` 块里，不要放进嵌套窗口；若放进嵌套窗口，先用 `+0x1c0` 取子窗口。
- 查不到时，三个方法都会转到 `0x14154e930`，带上类型名 `Button`、`InstantTextBox` 或 `Icon`，可能返回一个替补对象。所以 `ui.rs` 里"核对元素名字"的检查要保留。
- 鼠标输入（`0x14ea150`、`0x14ea630`）跳过 `+0xc4` 非 0 或 `+0xc5` 为 0 的对象。Kill 之后元素不会再收到点击。

## 5. 越出窗口范围的子元素

- **命中测试**（已验证）：`0x14ea630` 经 `0x14dda50` 遍历一张扁平的场景节点表（`scene+0x298`）。每个节点用**自己的**矩形判定，矩形是 `node+0x128..+0x12e` 处的 short；过程中不检查父窗口的范围。
- **越界检查只写日志**（已验证）：`0x1546e70` 在子元素越出背景元素（`root+0x520`）的尺寸时，写日志 `Illegal object boundaries`，不截断也不移动。`topbar` 的 `backGround=""`，推断没有背景元素，不会触发。
- **渲染**（未完全验证）：原版 `.gui` 没有任何 `clipping` 字段。D3D9 渲染器有剪裁实现（`0x173f830`），但没有追到哪些 GUI 元素会打开它。
- **结论**：没有找到按父窗口 `size` 剪裁的代码，与军队面板子元素越界仍能显示的运行时现象一致。剪裁这一项仍属推断。

## 6. 主菜单的常驻窗口（可选）

**主菜单 idler**（`frontend.cpp`）的 vtable 是 `0x1d5a8c8`（已验证）：

## 建议的实现

1. **拼接**：把提示窗口的元素（背景图标、文本框、关闭按钮）直接拼进 `interface/topbar.gui` 的 `windowType "topbar"` 块，名字加 `eu4harmony_` 前缀。可以照 `pause_window` 的写法用 `Orientation` 相对屏幕定位。
   - 也可以拼成一个嵌套的 `windowType`，整体用 GUI `+0x88/+0x90` 显隐。代价是查找时要先用 `+0x1c0` 取子窗口，这一步要构造 `std::string`。
2. **发现与绑定**：在已有的 `MANAGER_FRAME`（`0x8137c0`）after 钩子里：
   - 以 `rcx` 作为 idler，按 2.1 读出并校验 `root`；
   - 若与已绑定的根不同，就先解绑再重新绑定，方法与军队面板相同。
3. **解绑**：在 `0x1547520` 入口挂观察钩子，`rcx == 已绑定的根` 时立即解绑；`0x1546510` 入口作兜底。保留 `BUTTON_DESTROY`。
4. **主菜单（可选）**：在 `0x10d2e80` 用同样的方法绑定 `*(frontend+0x790)`。

## 风险与需要运行时验证

1. **滑出**：地图模式 0x25（推断为时间线）和军队重组窗口会把 `topbar` 滑到 `y=-165`。提示窗口会随之移出屏幕，需要确认这是否可以接受，以及 `+0xf5` 在滑出期间的值。
2. **定位**：推断全屏窗口里子元素的方位相对屏幕，要在不同分辨率下确认，尤其是宽度小于 2048 的屏幕。
3. **层级**：提示窗口与顶栏同层渲染，可能被别的窗口遮挡，或者遮挡别的窗口。
4. **路径确认**：回主菜单是否确实经过 `0x81e8f0`；新开一局时旧顶栏在切换中的删除顺序；显卡设备重置是否重建根。用 `0x1547520`、`0x1431020`、`0x149ad00` 打日志确认。
5. **重载**：`reload interface/topbar.gui`，以及 `menubar.gui`、`unitpanel.gui` 等其他被监听的文件，重载后根指针会变。要确认先触发 Kill 钩子、下一帧重新绑定，并且信号退订不发生在点击分发过程中。
6. **线程**：上述函数都应运行在主线程（应用帧 `0x14c25a0`，推断），但 Kill 钩子会在任何调用 Kill 的线程上触发，钩子里要检查线程身份。
7. **主菜单下的 world 指针**：`world+0x1e00` 在主菜单里推断为 0。切换 idler 的那一帧里，它会短暂指向已删除的 idler。所以只在 `0x8137c0` 钩子里、以 `rcx` 为准读取指针链。
8. **其他 Mod 改了 `topbar.gui`**：如果改名或删掉 `topbar` 窗口，CreateWindow 返回 0，而原版 `0x1431a80` 不检查空根，会直接崩溃；这与框架无关。拼接器找不到目标块时，应跳过并报告。
9. **版本**：本文只覆盖原版 `9ad3efe1…`。
