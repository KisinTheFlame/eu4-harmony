# Questions and offers (for `game::questions` and `game::offers`)

Baseline 1.37.5. All addresses are RVAs. Found by reading eu4.exe on 2026-10-29; what was checked in the running game is marked "tested" (prototype-log.md, 2026-10-29, remote control C7). Terms are in the GLOSSARY: a question is one of the game's events waiting for the player's answer, an offer another country's proposal waiting for it.

## Questions

### The pending events

- **The world keeps the events shown to players and not yet answered** (gamestate.cpp): an array at world `+0x1e98` (data `+0x1ea0`, capacity `+0x1ea8`, length `+0x1eac`, i32), records of `0x28` bytes; the last id given at `+0x1eb0`. Saves write them as `pending_events` and `last_pending_event_id` (the world's writer `0x74ff30`, `0x751519`: token `0x2e63`, each record's write method at its vtable `+8`).
- **A record** (added by `0x756f00(world, event, scope)`, which returns its id): `+0` a vtable (`0x1cb01e8`) and `+8` the type `0x165`; `+0x10` the event; `+0x18` the scope it happens in, a `0xd0`-byte object of its own (made by the scope copy `0xcf6a0`); `+0x20` the last day to answer: the date the event fired plus a number of months (the define at `0x233e840`, `AUTO_SELECT_EVENT_MONTHS`, 4 in vanilla; `0x14c8030(date*, months)` adds months); `+0x24` the id: one more than the last given, or more until no record has it (`0x756fc0`). Tested: the deadline read was the event's date plus four months, and two events left unanswered were answered by the game past it ("Auto-selected event option …" in the game's log).
- **Removing one** is `0x7570b0(world, id)`, which choosing an option does last.
- **Whose it is**: a scope's country is its tag at `+0x44` when the byte `+0x4b` is set, else at `+0x2c`; with no valid tag there (the byte at bit 56 zero), the owner of its province (`+0x28`, i32), as the world's reopening of windows reads it (`0x756d20`).

### How the game shows and answers them

- **Firing an event** (eventmanager.cpp "TriggerEvent", `0x6f4f40(…, event, scope)`): an event with options gets a pending event; for an AI country (or a hidden event, `+0xa61`) the game picks an option at once (`0x6f0180`) and sends the command below; for the player on this computer it has the map manager show it, through the map manager's method `+0x108` (`0x828c00`), which makes an event window (`0x10b9a50`) and adds it to the map manager's popups (`0x6ecae0`). The game console's `event` command does the same through `0xe5bb30`: a pending event, then the window, directly. After a save is loaded, `0x756cd0` makes a window again for every pending event of the player's.
- **The map manager's popups** are a list (the game's doubly linked list, `objects::list`) at map manager `+0x78`; every frame `0x6ea380` asks each popup, through its vtable `+0x18`, whether it stays, and removes and destroys those that do not. Event windows and the diplomacy dialogs opened from icons (below) are both in it.
- **An event window** (graphics/eventwindow.cpp, `0x3e8` bytes, vtable `0x1d590f8`): `+0x38` its GUI window ("EventWindow"), `+0x40` the map manager, `+0x48` the event, `+0x50` a copy of the scope, `+0x120` the pending event's id, `+0x124` open (u8; set by its constructor, cleared by choosing and by its close method, vtable `+0x28`, `0x10b9a20`). Its update (vtable `+0x18`, `0x10bbeb0`) finds its pending event by the event and the scope, and once the date is past the record's last day picks the option the AI would (`0x10bc580`) and goes. It returns its open byte; it does not close when its pending event is gone. Tested: each event that came up while time ran had an open window among the popups, with its pending event.
- **An option button** is named with the option's number after an underscore; the click (`0x10bc220`, through the window's button list at `+0x208`) reads the number and calls `0x10bc2d0(window, number)`. That logs "Selected event option N for event ID", makes a `CSelectEventOptionCommand` (`0x6f2660(command, event, scope, number, pending id)`, `0x140` bytes, vtable `0x1cab740`), sends it with the map manager's session (`[map manager]+0x80` gives it; the inline twin of the dispatcher `0x14ca2d0`) and clears the open byte. The command's execution (`0x6f2700`, eventcommands.cpp) runs the option's effects and removes the pending event. It checks neither that the pending event still exists nor that the player may choose the option, so a window whose pending event is gone would apply an option again: the framework only answers through windows whose pending event still exists, and only with options the player may choose. Tested: `0x10bc2d0` called at the safe point closed the window, logged "Selected event option 2 for event army_professionalism_events.1", and the option's effect (prestige −10) was there at once, the game paused; the same with the game running.
- **An event** (`CEvent`): `+0x14` its number, `+0x20` its id (`std::string`, `flavor_fra.1`), `+0x790` its options (a vector of pointers), `+0x7e0` its title's localisation key (`std::string`), `+0x808` and `+0x814` its descriptions with their triggers. **An option**: `+0x88` its name's localisation key, `+0xa8` its trigger; `0x6f6b30(option, scope)` says whether the player may choose it, and the event window shows only those (`0x10bb5c3`), numbering every option all the same.
- **Texts**: `0x10bc860(result, scope, key, tag)` returns, in `result`, a localisation key's text with the scope's names filled in (THISCOUNTRY, FROMCOUNTRY, pronouns and so on); `key` is a `std::string` taken by value, which it destroys; every caller passes the tag `---` (`0x2d2d2d`) as `tag`. The event window uses it for the title, for the description key `0x6edfb0(event, result, scope)` picks, and for each option. Tested: called with the window's scope, it gave the title, description and options the window showed, in Chinese. The description then has `§W` turned into `§b`, which the framework leaves out with every other color code.

## Offers

### Where they are kept

- **A diplomatic action reaching a country** (`0x4e7c50`, the action command's execution): for an AI the game decides at once; for a human it copies the action (vtable `+0xb0`), gives the copy an id (`+0x3c`, from the world's counter `0x771be0`) and the date it arrived (`+0x2c`), and appends it to the country's list at `+0x18d8` (count `+0x18e8`). `0x360970(country, id)` removes the action of that id. An action: `+0x10` the country making it, `+0x20` the one it is made to, `+0x28` when it was made, `+0x34` its state (0 unanswered, 1 declined, 2 accepted; the AI's answer is `1 + accepts`, `0x4e81c1`), `+0x3c` its id; vtable `+0x40` makes the command that sends an answer, `+0x58` returns its title, `+0xb0` copies it, `+0xd0` says whether it needs an answer, `+0xf0` whether it is accepted without asking.
- **The map manager's frame** (`0x8141d0`–`0x814364`) walks the player's list: an action it has not handled and that needs an answer is either accepted at once (vtable `+0xf0`: a copy in state 2, sent with `0x14ca210`) or shown (vtable `+0xd8`, given the map manager); handled ones are kept in a vector at map manager `+0x19f8`.
- **Showing one** goes through the map manager's method `+0x118` (`0x828cd0`): `0x828ef0` makes the diplomacy dialog for the action's type (about forty classes, `0x240` bytes each), and `0x828d20` wraps it in a diplomatic message icon (`0x107ffe0`, `0x160` bytes) appended to the list at `[map manager +0x1400] +0x4c78`, the diplomatic message icons. When the dialog's message type is in the list at `[0x242bde8]+0x230`, the icon is clicked at once (presumably the message settings' "pop up"). Some actions open their dialog directly (`0x5a6370`).
- **An icon**: `+0x20` its dialog, `+0x40` the date it came, `+0x44` and `+0x48` that date plus 52 and 62 days, `+0x140` done (u8), `+0x158` its own copy of the action. Its update (`0x10805f0`): done, it goes; while it flashes (`+0x141`, which `0x828e71` sets on every icon it makes) and the date is after `+0x44` and before `+0x48`, it only flashes, and stays; past `+0x48`, it answers its dialog (vtable `+0x50` when the dialog's `+0x90` says so, else `+0x58`, that is, it declines) and goes; otherwise it asks its dialog whether it is still open to an answer (vtable `+0x60`, below) and goes when it is not. So for the ten days of flashing nothing asks the dialog, and an offer the game no longer takes an answer to can be seen: clicking it opens the dialog, whose first update asks, and the offer is declined at once. Clicked (`0x1080770`), it hands its dialog to the map manager (`0x6ecd10`, which adds it to the popups and to the list of open dialogs at map manager `+0x370`), forgets it and is done. Tested: royal marriage and peace offers came as icons (in this layout at the top left, under the alerts); one whose dialog was declined from outside and marked done went at the next frame.

### The dialogs

- **Every dialog with agree and decline buttons** (`0x10a03f0`): `+8` its GUI window, `+0x10` the map manager, `+0x114` done (u8). Its "AgreeButton" calls vtable `+0x50`, its "DeclineButton" vtable `+0x58` (`0x10a0f48`, `0x10a0f40`). Its update (`0x10a08d0`) keeps it while it is not done and vtable `+0x60` says it is still open to an answer.
- **A diplomacy dialog** (`0x1066320`, diplomacydialogs.cpp, "DefaultDialog"): `+0x1c0` a callback object (class `0x1cb80c8`) with the dialog at `+0x1c8` and `0x1079f90` at `+0x1d0` for its popup button, which no other object has, so the framework tells a diplomacy dialog by it; `+0x238` its own copy of the action. Accepting (`0x1066a40`) sends the action's answer in state 2, declining (`0x1066b80`, through `0x1066ad0`) in state 1; both set done. Tested from an icon's dialog: accepting a royal marriage took the legitimacy its description named, accepting a white peace ended the war, both at once with the game paused; a declined offer left the player's list. Still open to an answer (`0x1066b10`): the action's date plus two months (`0x14c8030`, docs/research/dates.md: the same day of the month, or the month's last when it is shorter) is not before today, and the action is unanswered; when the two months are past it declines (vtable `+0x98`, `0x1066b80`) and says no.
- **Its subclasses about an action** (forty constructors call `0x1066320`; nine vtables keep the base's accept `0x1066a40` and decline `0x1066ad0`): their check at vtable `+0x60` is `0x1066b10` itself (vtables `0x1d54518`, `0x1d547b8`, `0x1d548f8`) or asks conditions of its own first and then ends with `0x1066b10`, so the two months hold for each: `0x1067e30` (the alliance's, `0x1d54d58`) and `0x1068330` look up the maker's records of the recipient (country `+0x1510`) and decline on what they find, `0x1069390` and `0x1069f30` also ask the action itself (its vtable `+0x80`), `0x1077110` looks up what the action refers to, and `0x106f680` sends an answer of its own in some cases; a check that fails says no, having declined or not. Asking the check is therefore what lets an offer go, and it is how the player meets it too: the dialog's first update asks it.
- **Its other subclasses** are not about an action and keep something else at `+0x238`, with their own accept, decline and check: the succession war's (`0x106fa45`, vtable `0x1d54a38`, "SUCCWAR_TITLE2"), which keeps a country's tag there, and two at `0x11bc6a4` and `0x11bce35` (vtables `0x1d65500`, `0x1d65590`), which keep there what `0x14cf730` finds from `+0x240`, and a date of their own at `+0x250`. Reading their `+0x238` as an action reads a tag as an address, so the framework takes for an offer only a diplomacy dialog whose accept method is `0x1066a40`, which sends the action's answer.
- **Its texts** are in its window's text boxes "Title" and "Description" (each subclass fills them as it is made, such as `0x10679a0` for an alliance: the action's title, `ALLIANCEREQDESC` with the maker's name); a text box keeps its text at `+0x170` (`0x10a2885`). Tested: read from dialogs never opened, they were the royal marriage's and the peace offer's texts. An action's `+0x28` read a few days before the offer showed up: when it was made.

## Not established

- Whether the game ever has a player's pending event without a window, other than for a moment between firing and the map manager's next frame: the framework then lists no question for it.
- The diplomacy dialogs whose classes override accepting or declining with more than the base does; the framework calls the dialog's own methods, as the buttons do.
- An offer answered from a dialog open on screen (the list at map manager `+0x370`), and an option the player may not choose: neither came up in the run.
- An offer older than two months, which the framework leaves out of the list, and one whose dialog's check says no when it is answered, which the framework refuses after the check let it go: neither came up in the run; the date arithmetic is a unit test, against the game's own reading above.
- When the message settings open an icon's dialog at once (`[0x242bde8]+0x230` looks like the message types set to pop up, by its use in `0x828e92`).
