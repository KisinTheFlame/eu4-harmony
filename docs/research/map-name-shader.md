# The map names' shader

What draws the names on the map once their meshes are built: how the game reads and compiles `gfx/FX/mapname.shader`, how it caches the result, what the names' draw binds and sets, and how it samples the font page. The plan for map names drawn from distance fields ([plans/map-text-sdf.md](../plans/map-text-sdf.md)) rests on it: the framework would change the shader's text as the game reads it and fill the map font's page with distances.

Baseline 1.37.5 (`9ad3efe1…`). All addresses are RVAs. What is marked [V] comes from eu4.exe's disassembly (capstone over the `.pdata` functions, with an index of `E8` calls and RIP-relative references) and has been checked; [I] is inferred. Read 2026-11-09, statically only: the game was not started. The shader cache was read from the user folder's `shadercache\dx9\` as the game left it.

## Why names blur when the map is close

- **The page is magnified with a linear filter** [V]: the names' meshes lie on the map in world space, and the file's `DiffuseTexture` sampler magnifies with `MagFilter = "Linear"` (below, "Who uses the mapname effect"). A glyph's texels reach the screen as many times larger as the camera is close, and the bilinear filter spreads each over that many pixels: soft edges, and the stepped edges of bilinear magnification along slanting strokes.
- **How much** [I]: vanilla's `Mapfont.fnt` has lines of 100 pixels (`common lineHeight=100`), and the framework draws a map font's system glyphs at an em of the line over the face's ascent and descent (`unicode/fill.rs`, `metrics`), about 75 pixels for a Chinese face. A player's screenshot at the closest zoom, 2026-11-09, showed such characters about 250 to 300 pixels tall, three to four times their texels. The camera's closest zoom was not measured.
- **Mips** [V]: vanilla's `Mapfont.dds` has 11 mip levels ([font-textures.md](font-textures.md), "Adding glyphs to a page"); the page the framework puts in its place has one, so farther out the names are minified from the first level alone (below, "The font page's mips and color space").

## How a shader file is read

- **An effect is asked for by a `.lua` name** [V]. The map's setup 0x10a2e40 calls the effect manager's load 0x16c6240 with `gfx/FX/mapname.lua` (0x1d57c20) and the effect name `mapname` (0x1d2c650) at 0x10a3554, the manager being `[map+0x18]+0x560` (the graphics object's) and the device context `[..+0x88]`; it keeps the effect's index at `map+0x4e0` (0x10a3559; 0x10a2f9f sets it to -1 first). 0x16c6240 returns an effect already loaded under that name with the same defines; otherwise it turns the name's `.lua` into `.shader` (0x16c6466 to 0x16c6555) and calls the manager's function at `+0x10` with that path (0x16c65d2).
- **The file is parsed as script** [V]. The shader parser (`clausewitzlib\graphics\pdxshaderparser.cpp`) loads a file in 0x15e0220: it hashes the path (FNV-1a) and returns a file already parsed under it (0x15e1e10); otherwise it opens it with the lexer's file constructor 0x170dd70 → the CLexer 0x170cd10 → 0x1718300 → `PHYSFS_openRead` (0x19f7f60, called only from 0x17183a0), builds a lexer with "UNNAMED_SESSION" and reads it with the generic persistence read 0x17068b0, as `.gui` files are read ([ui-injection.md](ui-injection.md)). 0x15e08b0 (no direct caller found; the manager's `+0x10` is assumed to lead to it [I]) loads the effect's file through 0x15e0220 (0x15e08e5), its includes through 0x15df3a0 (0x15e0905), makes its sampler states and shaders through the renderer's slots (0x1fd1100, 0x1fd1110, 0x1fd11c0, 0x1fd11b0, 0x1fd1118) and logs "Failed adding vertex shader %s(%s)", "Failed adding pixel shader %s(%s)", "Failed linking shader %s(%s)".
- **Includes** [V]: 0x15df0a0 puts `gfx/FX/` (0x1d9da58) before each name in `Includes`, loads it through the same 0x15e0220 (0x15df27b, "Shader include file '%s' not loaded" when it fails) and follows its own includes (it calls itself at 0x15df2c7). So `.fxh` files are parsed files too, each read once per path [I: whether the console's `reload` empties the parsed files was not looked into].
- **The HLSL text** [V]: 0x16fa460 (`gfx_dx9_hlsl_builder.cpp`; `edx` 0 builds the vertex shader, 1 the pixel shader) writes `#define VERTEX_SHADER` or `#define PIXEL_SHADER`, a `#define` for each of the effect's defines, `gfx/FX/defines_hlsl.fxh` read raw through 0x1718300 and `PHYSFS_read` (0x16fa5fc, 0x16fa638), a `sampler %s : register(s%d);` per sampler (0x1dbf338), the constants and structs (0x16f9bb0, 0x16fa290), and the main code it finds (0x16c90e0; "Failed finding main code %s"). A cached source shows the result in that order: the map's own defines (`MAP_SIZE_X`, `MAP_SIZE_Y`, the powers of two), `defines_hlsl.fxh`, the three samplers, the game's constants from `c0` and `vTargetOpacity_Fade : register(c32)`, the structs, the text of `constants.fxh` and `standardfuncsgfx.fxh`, then `main`.
- **When** [I]: the map's setup runs in the main menu's part, and loads its shaders (`mapname` among them) before it asks for its fonts by name ([loading.md](loading.md), "The map graphics in the main thread's wait"); the fonts themselves, with their pages, are loaded earlier with the interface's `.gfx` files at the application's start, so the map font's page has been made, and its own page's outline read, by the time `mapname.shader` is read.
- **For the framework**: every read of a `.shader` or `.fxh` goes through `PHYSFS_openRead`, and `PHYSFS_read` through `PHYSFS_readBytes` (0x19f8150 calls 0x19f8180), the functions `physfs.rs` hooks, so a splice of `gfx/FX/mapname.shader` (an `Addition::Edit`) reaches the compiler, a mod's copy of the file included, since PhysFS opens the copy that wins [I: not tried in the game]. None of the eleven mods in the test machine's workshop folder has a `mapname.shader`; three have `constants.fxh` or `standardfuncsgfx.fxh`, which it includes.

## The shader cache

- **Compiling** [V]: the pixel shader is built by 0x16d5c30 → 0x16d5b20 with level 2, which picks `ps_3_0` from `ps_1_1`, `ps_2_0`, `ps_3_0` (0x16d5b38 to 0x16d5b8f); the vertex shader likewise by 0x16d5a20 → 0x16d5910 with `vs_3_0`. 0x16d5430 compiles with `D3DXCompileShader` (import 0x1b670e0, called at 0x16d556b) with no defines, no include handler (the text is whole), entry `main`, that profile, and flags 0 (`r8d` cleared at 0x16d5b8c), then `CreatePixelShader` (vtable `+0x350`, 0x16d5bcf). So `ddx`, `ddy` and `fwidth` are there (ps_3_0), and the compiler optimizes as by default.
- **The key is the whole text** [V]: 0x16cb540 names a cache file `shadercache/dx9/<profile>/` plus three 32-bit numbers in hex, each written lowest nibble first (0x16cb450): the flags (0), the text's length, and the FNV-1a hash of the text (each byte sign-extended before the xor, 0x16cb58e to 0x16cb5b5). It opens `<name>.scache`, compares its length and bytes with the text (0x16cb876, memcmp at 0x16cb888), and only when they match loads `<name>.bin` (0x16cb8a5); otherwise it compiles and 0x16cbae0 writes both files. Checked against the cache: the names of 200 of the user folder's `ps_3_0` files are that formula of their `.scache` contents. The mapname pixel shader has four entries there, differing in the map size and the terrain texture size the defines and `standardfuncsgfx.fxh` bring in (mods with other maps).
- **So a changed `mapname.shader` is compiled again** and never served an old binary; the old entries stay in the folder [V].

## Who uses the mapname effect

- **Only the map names** [V]. `map+0x4e0` is read in two places of the map's code (scanned 0xfc0000–0x10c0000 and 0x12d0000–0x12f0000): 0x10a59a0, the map's draw, which takes the effect at `[map+0x18]+0x580 + index*0x38` (0x10a5c42 to 0x10a5c5f) and hands it to 0xfd7880 for each of the two name sets, `map+0x4e8` and `map+0x590` (0x10a5cd6, 0x10a5d51); and 0x10a4250, which reloads it (0x16c6a50), called by the console's `reload` with `map`, `mapname` or `postfx` (0xe594d4, "Map reloaded"). `gfx/FX/mapname.lua` is referenced nowhere else.
- **What the names' draw binds** [V] (0xfd7880, its loop from 0xfd7be2): per name mesh, the font page from the texture manager by `font+0x970` (0x16c3f10, 0xfd7d86) and two fog-of-war textures from the pdxmap (`+0x1640` and `+0x16a8`, through 0x10a5c8a), three textures in one call of the bind slot `[0x1fd11f0]` (0x16d8560) for the pixel stage from slot 0, with the effect's sampler states (`[effect+0x20]`, 0xfd7da4).
- **The sampler states are the file's** [V]. For each texture 0x16d8560 sets `SetTexture` (vtable `+0x208`) and, when the effect's sampler differs from the one last set on that slot, 0x16d8360 sets `ADDRESSU`, `ADDRESSV`, `MAGFILTER`, `MINFILTER`, `MIPFILTER`, `MIPMAPLODBIAS` and `MAXANISOTROPY` (`SetSamplerState`, `+0x228`, states 1, 2, 5, 6, 7, 8 and 10) from the sampler object, which 0x15e08b0 makes from the `Samplers` block. Nothing else in the draw sets sampler states. So `DiffuseTexture` is sampled with linear magnification, minification and mip filtering and an LOD bias of -1, as the file says, and a splice of the block (another bias, anisotropy) would take effect the same way [I: not tried].
- **The blend** [V, from the file]: `SourceBlend = "src_alpha"`, `DestBlend = "inv_src_alpha"`, no alpha test, red, green and blue written. The pixel shader returns the page's color and alpha, the alpha times the two constants below, the color through the distance fog and the fog of war.

## Constants

- **`vTargetOpacity_Fade`** [V]: `ConstantBuffer( 1, 32 )` is `register(c32)` in the built text. Per mesh, when its fade changes, the draw writes two floats, `[rsp+0x48]` the target opacity (`xmm7`, from the map's draw) and `[rsp+0x4c]` the fade by distance (0xfd7cf9 to 0xfd7d38), through `[0x1fd11d0]` (0x16d22e0) and binds buffer 1 of 0x20 bytes to both stages through `[0x1fd11e8]` (0x16d71b0; `r9d` 1, size 0x20, 0xfd7d4f to 0xfd7d6c). The view constants (`c0` on) are bound the same way as buffer 0 before the loop (0xfd7b71, 0xfd7b94).
- **A value of the framework's needs no constant**: whatever the shader needs that is fixed for a run, such as an outline's color and its fall-off or a distance field's spread, can be written into the spliced text as literals, since the text is read once, after the fonts are loaded, and the cache keys on the text. Passing a value that changes during a run would need a constant of its own, which the game does not upload; that was not looked into further.

## The font page's mips and color space

- **No mip handling** [V]: the bind path (0x16d8560, 0x16d8360) never looks at a texture's levels. A page of one level is sampled at that level whatever the mip filter (Direct3D 9's behavior); a page made with mip levels would be filtered between them with the file's bias of -1.
- **sRGB sampling is off for font pages** [V]. The bind sets `D3DSAMP_SRGBTEXTURE` (state 0xb) from the texture wrapper's `+0x08` on every bind (0x16d8657, 0x16d83a5). The wrapper's flag is set when the texture is made (0x16d7aa0, 0x16d7afd) for the even engine formats 2 to 14, the sRGB twins of the odd ones (jump table at 0x16d7d84). The texture loader 0x16cc6e0 moves a format to its sRGB twin when the load options' byte `+1` is set (0x16cca08 to 0x16cca77), for `.dds` and `.tga` alike; the options come from the texture entry's `+0x3c` (0x16c3fda, written at 0x16c37ec from the registration's options `+1`). A font registers its page in 0x15953c0 with options `0x1000000` and 0 (0x159548a, 0x1595485): byte `+1` is 0. So the page is sampled without sRGB decoding, the game's own page and the framework's in its place alike (the framework keeps the game's wrapper and does not write `+0x08`), and values stored in it, such as distances, reach the shader as stored.
