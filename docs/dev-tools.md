# Development tools

Tools for trying things in a running game, finding dependency points and looking at crashes. What needs the repository is a command of `cargo xtask` (`xtask/`, `cargo xtask --help`), for development machines only and not among the player's files, which `cargo xtask release` packs; what does not is a command of the command line tool, `eu4-harmony`; what runs inside the game is a feature of the core, built into a developer build. Why each is where it is: [dev-commands.md](plans/dev-commands.md).

## Caveats

- **Claim a test game first.** The game rewrites a save after loading it and rewrites its settings; a test game does that in its own user folder, never the player's ([test-games.md](plans/test-games.md)). Ask it with `eu4-harmony game --test-game <owner>`, or with `EU4_HARMONY_TEST_GAME` set. A player or mod author without the repository backs up with `eu4-harmony backup <new folder>` and restores with `eu4-harmony restore <that folder>`.
- **Crash dumps** are in the documents folder at `Europa Universalis IV\crashes\eu4_<date>_<time>\minidump.dmp`; the framework's logs are in `eu4-harmony\logs\`. `cargo xtask crash-dump <dump> <log> '!analyze -v' 'kn 30'` writes what the debugger says of one into `<log>`, the core's own frames named from this checkout's release build, or from its player package as `cargo xtask release` last built it.

## Disassembly

```
cargo xtask disasm ARG...
```

Arguments (numbers are hex, with or without `0x`; addresses are all RVAs):

- `RVA`: the whole function starting there, its end taken from the exception directory; a leaf function, which has no entry in the directory, runs to the padding after its `ret`, at most 40 instructions;
- `RVA:N`: N instructions from RVA, which need not be the start of a function;
- `bytes:RVA:N`: N bytes in hex, in the same format as dependency points;
- `args:RVA`: how many arguments the function reads, which is how many an observe point on it must forward at least;
- `uses:`, `refs:`, `slots:` and `chain:` find the instructions that use a field, a global or a vtable, as `core/examples/disasm.rs` describes. They read operands: a direct `call` or `jmp` to a function is not among what `refs:` finds, so a function with no `refs:` may still be called directly.

It runs `core/examples/disasm.rs` with the core's `analysis` feature. The same analysis runs the offline check, `cargo xtask offline-check`: the core's ignored tests, with `EU4_GAME_DIR` set to the game found, run once in a player's build and once with `--features eu4-harmony-core/dev`.

## Developer builds

Each development tool is a feature of the core, and `dev` turns them all on:

```
cargo build --release --features eu4-harmony-core/dev
cargo build --release --features eu4-harmony-core/dev-command-log,eu4-harmony-core/dev-call-trace
```

A tool built in is on; nothing else turns it on. The heap census observes every allocation of the game's, which slows it down: build only the tools a run needs, with `dev-test-games` for a test game. The build goes where the player build goes, `target\x86_64-pc-windows-msvc\release`, and `cargo xtask game start` copies whichever was built last into its test game; the first line of the framework log and of the startup report says "developer build" and names the tools, and the report lists their options as they took effect. `cargo xtask release` builds the player build itself before packing it.

The tools' options are in `dev.toml` at the top of the repository, which is not checked in; `cargo xtask game start` copies it beside the test game's core, and `cargo xtask install` into the game folder's `eu4-harmony\`, and the core reads the one beside it at startup. [core/dev.toml.example](../core/dev.toml.example) shows every section with its defaults; a section left out takes them, and a file the core cannot read, or an option it does not know, fails startup.

## Call tracing

In `dev.toml`'s `[call-trace]`, `functions` lists the RVAs of the functions to trace, for example `["0x15988e0", "0x159c600"]`. The first 20 calls to each function (`calls` changes this) go into the framework log: the value of each argument, with the text when an argument points to text (a C string or a `std::string`, decoded as game text), the call site, and the return value.

With `times = true`, every call of each traced function is timed as well, into `call-times.tsv` in the logs folder, a new file each run: the function, the thread (`main` for the main thread), its start and end in microseconds, the game's date, its first argument, and, for a function `fields` names, the eight bytes at an offset into the object the first argument points at (`fields = { "0xb0fa0" = "0x20" }`). It is for how long calls take and how they lie on the threads, such as the tasks of a parallel stage ([research/late-game.md](research/late-game.md)); `calls = 0` leaves the log out. The calls are kept in memory and written by a thread of the tool's own once a second. Each timed call goes through the observer and takes a lock, so a function called very often slows the game and lengthens the calls of the functions that call it, and fills the file: tens of thousands of calls a second did not show in the days a second, while a function called 300,000 to 600,000 times a second made its callers take several times as long and wrote 11 GB in four minutes ([Inside an AI country's task](prototype-log/2026-11-07-inside-ai-country-task.md)). For where a call's time goes, sample instead (`cargo xtask profile --threads`); time only the calls whose length, order or argument is the question. Any number of functions can be traced. A function that reads more than 12 arguments is left out, since an observer forwards no more. The count is of the arguments a function reads before its first call; one it hands on to a call unread is not counted, and the observer then forwards garbage in its place: the AI agents' thinks (`0xe9f30` and the others, counted as reading one) take the day's argument and hand it on, and traced so they crashed the game. Give such a function's count as `RVA:N`, which takes the place of the one counted. Tracing the army search `0x1022b0` as `0x1022b0:11` also crashed the game, in the search's caller (`eu4+0xe978a`), the cause not found (2026-11-07, [prototype-log/](prototype-log/)). A function the framework itself hooks at its start, such as the daily update `0x758430` or the in-game frame `0x8137c0`, cannot be traced: startup fails, naming both.

The number of arguments is counted from the function's code. For a leaf function with no entry in the exception directory, write `"RVA:N"` and give the count yourself; give too few and the function reads garbage, and the game may crash.

## Write watch

In `dev.toml`'s `[write-watch]`, `function` is the RVA of a game function, for example `"0x74ff30"`, the world's write of itself into a save. During its first call on the main thread (`calls` changes how many), every other thread of the process is suspended but those that write a save's countries and provinces with the main thread, whose writes are watched too, and every page of the process heap that holds a block and every writable page of `eu4.exe` is read-only. Each write to one of them stops at an exception handler, which records it and lets it through. When the call returns, the pages are as they were, the threads go on, and the framework log lists the writes, grouped by the instruction and the calls it was in, most first:

```
write watch #0: 40539 main write static at 0x15bf95 to 0x2458c00 in 0x861c55 < 0xd2f434 < 0x29cde7 < …
write watch #0: 4300 main write block at 0x29cd99 to 0x50 bytes +0x40 in 0x2976ac < 0xd2f434 < 0x297568 < …
```

What a write went to is `static` (`eu4.exe`'s data, by its RVA), `block` (a heap block that was there when the call began: its size and the offset written), or `new` (the rest of the heap's pages: blocks made during the call, and the heap's own records). Writes to the stack and to memory outside the heap and the image are not seen.

**What one call reads and the next writes.** `reads-before` names other functions, up to eight, for example the map's and the GUI's drawing (`["0x10a59a0", "0x14dd010"]`). In each round the next call on the main thread of each of them is watched first, and its reads too: its pages are inaccessible instead of read-only, so that reads stop at the handler as well, and the blocks and the eight bytes of `eu4.exe`'s data it read or wrote are kept. Its report says how many blocks of each size it read, which tells the kinds of object, and its largest groups (`read` or `write`). Then the next call of `function` is watched as before, once at least one of them has been, and each of its writes to what they read or wrote is marked `(read before)`, those listed first. So a frame's drawing and the day after it say which of what the drawing reads the day changes. `calls` counts rounds. `after-days` begins the watch once that many game days have passed one after another, as the watched functions see the date, so that it falls in a game that runs and not at its load.

**When the watched call stops.** A call that waits for a held thread, or for a lock one has, would wait for ever. With `give-up-after` (30 s unless it says otherwise, 0 for ever), a watchdog thread of the tool's ends a watch in which the main thread has read or written nothing new for that long (no instruction, calls or target it had not before: a loop that waits reads the same again): it logs the main thread's calls as it found them (`write watch: given up after …, the main thread at …`), the pages get their protection back and the threads go on, and the call's report says the watch was given up. `let-run` names modules, by file name, whose threads are not held (`["nvd3dumx.dll"]`, the graphics driver's); what they read and write is recorded as another thread's. Tried on a frame's drawing with the driver's threads let run, the watch of the map's drawing did not end in 28 minutes, why was not found ([what the drawing reads and the next day writes](prototype-log/2026-11-08-what-the-drawing-reads-and-the-next-day-writes.md)). So a call that uses Direct3D, such as the GUI's drawing, or a day through D3DX, is watched only up to its first wait in the driver; watch the parts of it that do not call Direct3D instead.

**What the drawing thread reads, and who writes it.** `drawing = true`, with no `function`, watches the drawing thread instead (`core/src/write_watch/drawing.rs`): which writes land in what it reads while the main thread runs a day, the races the presentation lock does not cover ([drawing-thread.md](plans/drawing-thread.md)). Once `after-days` days have passed, its next `drawing-frames` frames (1 unless it says otherwise) are watched for their reads, every other thread held but `let-run`'s, which must name the graphics driver (`["nvd3dumx.dll"]`), as the drawing waits on its threads; only what `eu4.exe`'s own code reads is kept, the blocks by their start and the image's data by its eight bytes, and a page read 32 times goes on unwatched, so that a frame takes minutes and not hours. Then, from the next day on, for `drawing-days` days (3 unless it says otherwise), the pages of what was read are read-only while every thread runs, and each write to a block or bytes read is recorded by who wrote it: `main-unlocked` (the main thread without the presentation lock), `other` (another thread than the main and the drawing threads), `main-locked` and `drawing`. The report (`write watch 0x8183b0 #0`) counts each and lists the groups of the first two first, which are the races to look at: a write the lock does not keep from the drawing thread's reads, unless the drawing does not read that part of the block while the main thread may write it. A block freed and made again at the same start between the two parts passes for the one read.

- Build it alone (`--features eu4-harmony-core/dev-write-watch`): the held threads may hold a lock the watched function then waits for, and the heap census takes one at every allocation.
- The watched call runs many times slower: an ironman save of 55 MB from 1724 took about a minute and wrote 25.8 million times. Setting it up walks the heap, 0.6 s for 8 million blocks.
- A function that waits for another thread never returns while watched.
