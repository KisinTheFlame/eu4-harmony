# Development tools

Tools for trying things in a running game, finding dependency points and looking at crashes. What needs the repository is a command of `cargo xtask` (`xtask/`, `cargo xtask --help`), for development machines only and not among the player's files, which `cargo xtask release` packs; what does not is a command of the command line tool, `eu4-harmony`; what runs inside the game is a feature of the core, built into a developer build.

## Performance windows

`cargo xtask scenario perf --owner <name>` runs the standard two-scenario performance suite (`perf-early` followed by `perf-late`, both alone) on the `dev` build with `[performance] enabled = true` in its `dev.toml`, adding `[test-switches] game-paths` when `--perf.game_paths` (or `--perf-early.game_paths` / `--perf-late.game_paths`) is given:

- **`perf-early`** (early game): starts a hidden fresh 1444.11.11 campaign in observe mode (`menu.start` with no player country), puts Ming (`MNG`) in view (`session.view MNG`), pauses, centers the camera on Beijing (`1816`), waits ten seconds, records the camera, then measures bounded paused and speed-5 windows (30 and 120 seconds by default).
- **`perf-late`** (late game): loads `observer-1780.7.1` (default, 40.5 years of runway to 1821.1.2; overridable via `--perf-late.save`) in observe mode, resolves the rank-1 great power from the save's `great_powers` block (`TUR` in `observer-1780.7.1`, overridable via `--perf-late.country`), puts that country in view (`session.view`), pauses, centers the camera on its capital read from the save (`151` for `TUR`), waits ten seconds, records the camera, then measures the same paused and speed-5 windows.

Using observe mode with the starting rank-1 great power in view keeps the AI running for every country (no idle player nation) while exercising a realistic major-power HUD, fog-of-war and map camera load. `--perf.paused_seconds` and `--perf.running_seconds` each accept 1–600 seconds. Startup/load time, CPU and memory remain in the report. `--perf.collect false` leaves collection off in the same instrumented build; this is an overhead comparison, not an uninstrumented player build.

The development-only remote capabilities `performance.begin` (with `seconds`, 1–600) and `performance.end` control one bounded window. The deadline is measured inside the process; retrieving the result later does not extend it. An expired window must be collected before another can replace it. Results split when session, speed, pause state or declared frame target changes. CPU and memory bracket the window from outside the process and have their own elapsed duration. The external date interval also includes the begin/end requests and report export before pausing; a collection-on/off rate comparison includes those control costs, whereas the CPU bracket ends before export.

The versioned JSON and Markdown reports contain completed-day rates and durations, successful Present-wrapper return intervals, long-gap counts, update-ready intervals, first-submission delays, update outcomes and wall-time-weighted interface age. Quantiles are nearest rank; age quantiles are weighted by time, including stalls. Missing observations are null, not zero. The timeline holds at most 262,144 events: overflow reports lost records and the retained time, preserves whole-window observed counts and makes the measurement incomplete. Unfinished days, update waits and frame gaps are reported at the window's end.

A frame can submit an older update after the next one has been prepared; attribution is captured before Present releases the presentation lock. Pause, speed and target changes split interval statistics but retain update associations and known interface age within the same session. Each update's final outcome and first-submission delay belong once to the segment that prepared it, even if submission occurs in a later segment. Outcomes and pending-update age are resolved at the end of the retained timeline; a session change invalidates pending prepared data and clears submission associations and age. Main-thread drawing is included, with its readiness measured at entry to in-game drawing rather than at the drawing thread's publication point. A Present that began before collection still counts when it returns inside the window, with call duration and update association unknown, including when its token came from an earlier window. A failed or held-back Present is not counted as a successful submission. Local save entry/return and device reset are explicit markers; pauses split segments, and their time remains in the overall window.

The report measures submission on the CPU, not display latency or GPU work. Pure interface-work duration and action response are unmeasured. Hidden runs do not establish visible smoothness. There are no performance pass/fail thresholds: incomplete measurement fails its collection check, while slow but complete measurements remain reportable. The [metric plan](plans/README.md#measurement) describes the broader comparison methodology and deferred work.

## Caveats

- **Claim a test game first.** The game rewrites a save after loading it and rewrites its settings; a test game does that in its own user folder, never the player's ([test-games.md](dev-tools.md#test-games)). Ask it with `eu4-harmony game --test-game <owner>`, or with `EU4_HARMONY_TEST_GAME` set. A player or mod author without the repository backs up with `eu4-harmony backup <new folder>` and restores with `eu4-harmony restore <that folder>`.
- **Crash dumps** are in the documents folder at `Europa Universalis IV\crashes\eu4_<date>_<time>\minidump.dmp`; the framework's logs are in `eu4-harmony\logs\`. A crash the game's crash handling caught has two `crash:` lines in `core.log`: what it was and where, and the calls it was in, `eu4.exe`'s as RVAs and the core's as offsets into `eu4_harmony_core.dll` ([research/crash-handling.md](game/program/crash-handling.md)). A player's troubleshooting files, from the About page of the settings window, hold complete logs and all existing crash folders, including dumps, without size or count limits. `cargo xtask crash-dump <dump> <log> '!analyze -v' 'kn 30'` writes what the debugger says of one into `<log>`, the core's own frames named from this checkout's release build, or from its player package as `cargo xtask release` last built it.

## The first upload

The proxy is built with Harmony's published file id (`workshop\item.toml`), which the Workshop gives only once the item exists. So the item is made first, private and holding a build without the id, and then uploaded again as the first version:

1. `cargo xtask release`, then `cargo xtask workshop-upload --user <login> --create`: SteamCMD makes the item, private, writes its id back into `target\workshop\harmony.vdf`, and the command records it in `workshop\item.toml`.
2. Commit `workshop\item.toml` and merge it into master.
3. Merge the version PR and let GitHub create its tag and Release. From a clean checkout of that tag, run `cargo xtask release`, which builds the proxy with the id and writes it into the descriptor as `remote_file_id`, then `cargo xtask workshop-upload --user <login>`. Upload uses the existing tag without creating one.
4. On the item's page: the descriptions by language, the comparison images as preview images, then the visibility.

Every later version is step 3 after raising the workspace and internal lockfile versions, adding the changelog section and merging through a PR. Merging the version PR starts GitHub publication and creates the tag automatically; Workshop upload remains local.

## Disassembly

```
cargo xtask disasm [--module <file>] [--game-dir <dir>] ARG...
```

Arguments (numbers are hex, with or without `0x`; addresses are all RVAs):

- `RVA`: the whole function starting there, its end taken from the exception directory (shown with its range and byte size in the header); a leaf function, which has no entry in the directory, runs to the padding after its `ret`, at most 40 instructions;
- `RVA:N`: N instructions from RVA, which need not be the start of a function;
- `bytes:RVA:N`: N bytes in hex, in the same format as dependency points;
- `args:RVA`: how many arguments the function reads, which is how many an observe point on it must forward at least;
- `uses:`, `refs:`, `slots:` and `chain:` find the instructions that use a field, a global or a vtable, as `xtask/src/disasm.rs` describes. They read operands: a direct `call` or `jmp` to a function is not among what `refs:` finds; `callers:` finds those;
- `vtable:RVA[:N]`: lists each 8-byte slot of the table starting at RVA. Without `N`, stops automatically before non-code pointers or the earliest subsequent slot referenced directly by code (capped at 128 slots);
- `callees:RVA[:depth]`: builds a tree of direct `call` targets and out-of-function tail `jmp` targets up to `depth` (default 1, max 5), marking cycles `(recursive)` and already-expanded nodes `(shown above)`;
- `data:RVA[:N]`: dumps `N` (default `0x80`) bytes as hex and ASCII, resolving relocated pointers into the image with their target RVA, name and string preview;
- `callers:RVA[:N]`: who calls the function: each `call` or `jmp` to it and each instruction that takes its address, then each vtable (or other table of code pointers) that holds it, at which offset, with the instructions that use the table, the first N (50) of each. The game has almost no RTTI, so vtables lie back to back; a table is taken to begin at the nearest place before the pointer that code uses;
- `str:TEXT`, `stri:TEXT`, `wstr:TEXT`: the strings in the binary's data that hold TEXT (everything after the colon, colons too)—case-sensitive ASCII (`str:`), case-insensitive ASCII (`stri:`), or UTF-16LE (`wstr:`)—each with the instructions that use it and the pointers to it, the way into the code from a log line, an assert's path or a script word.

`refs:`, `callers:`, `str:`, `stri:` and `wstr:` read the functions in the exception directory; a leaf function has no entry there, so a jump at its end to another function is not found. Only `eu4.exe` reads names from `docs/game/addresses.toml`; other binaries inspected via `--module` leave address names blank.

The command runs directly in `xtask/src/disasm.rs`, without building the core or changing its DLL, library or symbols in `target\\`. PE image reading and instruction analysis live in the independent `eu4-harmony-analysis` crate (`analysis/`), shared with the core's offline checks, call tracing and write watching. Instruction formatting belongs to xtask.

`cargo xtask offline-check` still builds and runs the core's ignored tests, with `EU4_GAME_DIR` set to the game found, once in a player's build and once with `--features eu4-harmony-core/dev`. Unlike disassembly, those checks change the core's build artifacts.

## Decompilation

```
cargo xtask decompile --init [--rebuild] [--module <file>] [--game-dir <dir>]
cargo xtask decompile --status | --stop [--module <file>]
cargo xtask decompile [--module <file>] [--game-dir <dir>] [--timeout <seconds>] [--oneshot] <rva>...
```

Decompiles functions to C pseudocode through a local Ghidra installation without re-importing on every query:

1. **Toolchain setup**: `xtask` locates Ghidra and JDK from `GHIDRA_INSTALL_DIR` / `JAVA_HOME`, then `%LOCALAPPDATA%\eu4-harmony-dev\ghidra.toml` (under `EU4_HARMONY_DEV_DIR` if set, with optional keys `ghidra_dir`, `java_home`, `max_mem`), then `PATH`. When `GHIDRA_HEADLESS_MAXMEM`, `GHIDRA_MAXMEM`, and `max_mem` are unset, JVM max heap defaults to half of physical RAM clamped to `2G..=8G`.
2. **One-time project initialization (`--init`)**: imports the binary into `%LOCALAPPDATA%\eu4-harmony-dev\ghidra\projects\<module>-<sha256[..16]>\`, runs Ghidra's full auto-analysis with live output, and writes `ready.json` only on clean completion (`--rebuild` stops any running server and re-analyzes from scratch). Querying an uninitialized binary fails immediately and tells you to run `--init` first.
3. **Warm server and `--oneshot`**: querying RVAs auto-starts a read-only background Ghidra server bound to `127.0.0.1` with a random token, serializing requests and exiting automatically after 15 minutes idle. `--status` inspects cached projects and live servers; `--stop` shuts down a module's warm server (or all servers if `--module` is omitted); `--oneshot` runs a single headless invocation without leaving a background process.
4. **RVA output and live annotations**: passing an interior RVA resolves to its containing function (with `.pdata` fallback) and displays the offset in the header. For `eu4.exe`, Ghidra's default module-VA names (`FUN_14...`, `DAT_14...`, `LAB_14...`, `PTR_..._14...`, etc.) are rewritten to RVAs, and names/notes from `docs/game/addresses.toml` are overlaid live in the header, inline comments, and a referenced-addresses footer without mutating the cached Ghidra database. Each function defaults to a 60-second decompile limit (`--timeout` overrides).

## Developer builds

The core has two development features (`core/Cargo.toml`): `dev-test-games` (test-game pipes only, used for player-equivalent test runs) and `dev` (which includes `dev-test-games` and all development tools):

```
cargo build --release --features eu4-harmony-core/dev-test-games
cargo build --release --features eu4-harmony-core/dev
```

In a `dev` build, all development tools are compiled in and controlled through `dev.toml` at the top of the repository (not checked in). Tools with runtime hooks or listeners (`performance`, `heap-census`, `command-log`, `crossings`) stay off with no extra runtime hooks installed unless their section sets `enabled = true`; `call-trace`, `write-watch` and `test-switches` act only when configured; `memory-account` answers remote control's `memory` on demand at no cost between asks. `[heap-census] enabled = true` and an active `[write-watch]` cannot be enabled together and fail startup. The build goes where the player build goes, `target\x86_64-pc-windows-msvc\release`, and `cargo xtask game start` copies whichever was built last into its test game; the first line of the framework log and of the startup report identifies a developer build (or a test-games build), and a developer build's report lists its active options. `cargo xtask release` builds the player build itself before packing it.

`cargo xtask game start` copies `dev.toml` beside the test game's core, and `cargo xtask install` copies it into the game folder's `eu4-harmony\`, and a `dev` core reads the one beside it at startup (a `dev-test-games`-only build does not read `dev.toml`). [core/dev.toml.example](../core/dev.toml.example) shows every section with its defaults; a section left out takes them, and a file the core cannot read, or an option it does not know, fails startup. Scenarios always supply their own `dev.toml` (empty by default) rather than inheriting the checkout's file.

## Call tracing

In `dev.toml`'s `[call-trace]`, `functions` lists the RVAs of the functions to trace, for example `["0x15988e0", "0x159c600"]`. The first 20 calls to each function (`calls` changes this) go into the framework log: the value of each argument, with the text when an argument points to text (a C string or a `std::string`, decoded as game text), the call site, and the return value.

With `times = true`, every call of each traced function is timed as well, into `call-times.tsv` in the logs folder, a new file each run: the function, the thread (`main` for the main thread), its start and end in microseconds, the game's date, its first argument, and, for a function `fields` names, the eight bytes at an offset into the object the first argument points at (`fields = { "0xb0fa0" = "0x20" }`). It is for how long calls take and how they lie on the threads, such as the tasks of a parallel stage ([research/late-game.md](game/ai/work-scheduling.md)); `calls = 0` leaves the log out. The calls are kept in memory and written by a thread of the tool's own once a second. Each timed call goes through the observer and takes a lock, so a function called very often slows the game and lengthens the calls of the functions that call it, and fills the file: tens of thousands of calls a second did not show in the days a second, while a function called 300,000 to 600,000 times a second made its callers take several times as long and wrote 11 GB in four minutes ([Inside an AI country's task](research/performance-evidence.md)). For where a call's time goes, sample instead (`cargo xtask profile --threads`); time only the calls whose length, order or argument is the question. Any number of functions can be traced. A function that reads more than 12 arguments is left out, since an observer forwards no more. The count is of the arguments a function reads before its first call; one it hands on to a call unread is not counted, and the observer then forwards garbage in its place: the AI agents' thinks (`0xe9f30` and the others, counted as reading one) take the day's argument and hand it on, and traced so they crashed the game. Give such a function's count as `RVA:N`, which takes the place of the one counted. Tracing the army search `0x1022b0` as `0x1022b0:11` also crashed the game, in the search's caller (`eu4+0xe978a`), the cause not found (2026-11-07, [research evidence](research/README.md)). A function the framework itself hooks at its start, such as the daily update `0x758430` or the in-game frame `0x8137c0`, cannot be traced: startup fails, naming both.

The number of arguments is counted from the function's code. For a leaf function with no entry in the exception directory, write `"RVA:N"` and give the count yourself; give too few and the function reads garbage, and the game may crash.

## Write watch

In `dev.toml`'s `[write-watch]`, `function` is the RVA of a game function, for example `"0x74ff30"`, the world's write of itself into a save. During its first call on the main thread (`calls` changes how many), every other thread of the process is suspended but those that write a save's countries and provinces with the main thread, whose writes are watched too, and every page of the process heap that holds a block and every writable page of `eu4.exe` is read-only. Each write to one of them stops at an exception handler, which records it and lets it through. When the call returns, the pages are as they were, the threads go on, and the framework log lists the writes, grouped by the instruction and the calls it was in, most first:

```
write watch #0: 40539 main write static at 0x15bf95 to 0x2458c00 in 0x861c55 < 0xd2f434 < 0x29cde7 < …
write watch #0: 4300 main write block at 0x29cd99 to 0x50 bytes +0x40 in 0x2976ac < 0xd2f434 < 0x297568 < …
```

What a write went to is `static` (`eu4.exe`'s data, by its RVA), `block` (a heap block that was there when the call began: its size and the offset written), or `new` (the rest of the heap's pages: blocks made during the call, and the heap's own records). Writes to the stack and to memory outside the heap and the image are not seen.

**What one call reads and the next writes.** `reads-before` names other functions, up to eight, for example the map's and the GUI's drawing (`["0x10a59a0", "0x14dd010"]`). In each round the next call on the main thread of each of them is watched first, and its reads too: its pages are inaccessible instead of read-only, so that reads stop at the handler as well, and the blocks and the eight bytes of `eu4.exe`'s data it read or wrote are kept. Its report says how many blocks of each size it read, which tells the kinds of object, and its largest groups (`read` or `write`). Then the next call of `function` is watched as before, once at least one of them has been, and each of its writes to what they read or wrote is marked `(read before)`, those listed first. So a frame's drawing and the day after it say which of what the drawing reads the day changes. `calls` counts rounds. `after-days` begins the watch once that many game days have passed one after another, as the watched functions see the date, so that it falls in a game that runs and not at its load.

**When the watched call stops.** A call that waits for a held thread, or for a lock one has, would wait for ever. With `give-up-after` (30 s unless it says otherwise, 0 for ever), a watchdog thread of the tool's ends a watch in which the main thread has read or written nothing new for that long (no instruction, calls or target it had not before: a loop that waits reads the same again): it logs the main thread's calls as it found them (`write watch: given up after …, the main thread at …`), the pages get their protection back and the threads go on, and the call's report says the watch was given up. `let-run` names modules, by file name, whose threads are not held (`["nvd3dumx.dll"]`, the graphics driver's); what they read and write is recorded as another thread's. Tried on a frame's drawing with the driver's threads let run, the watch of the map's drawing did not end in 28 minutes, why was not found ([what the drawing reads and the next day writes](research/interface-evidence.md)). So a call that uses Direct3D, such as the GUI's drawing, or a day through D3DX, is watched only up to its first wait in the driver; watch the parts of it that do not call Direct3D instead.

**What the drawing thread reads, and who writes it.** `drawing = true`, with no `function`, watches the drawing thread instead (`core/src/dev/write_watch/drawing.rs`): which writes land in what it reads while the main thread runs a day, the races the presentation lock does not cover ([drawing-thread.md](plans/README.md#drawing)). Once `after-days` days have passed, its next `drawing-frames` frames (1 unless it says otherwise) are watched for their reads, every other thread held but `let-run`'s, which must name the graphics driver (`["nvd3dumx.dll"]`), as the drawing waits on its threads; only what `eu4.exe`'s own code reads is kept, the blocks by their start and the image's data by its eight bytes, and a page read 32 times goes on unwatched, so that a frame takes minutes and not hours. Then, from the next day on, for `drawing-days` days (3 unless it says otherwise), the pages of what was read are read-only while every thread runs, and each write to a block or bytes read is recorded by who wrote it: `main-unlocked` (the main thread without the presentation lock), `other` (another thread than the main and the drawing threads), `main-locked` and `drawing`. The report (`write watch 0x8183b0 #0`) counts each and lists the groups of the first two first, which are the races to look at: a write the lock does not keep from the drawing thread's reads, unless the drawing does not read that part of the block while the main thread may write it. A block freed and made again at the same start between the two parts passes for the one read.

- Keep `[heap-census] enabled = false` while using write watch (startup rejects both enabled together): the held threads may hold a lock the watched function then waits for, and the heap census takes one at every allocation.
- The watched call runs many times slower: an ironman save of 55 MB from 1724 took about a minute and wrote 25.8 million times. Setting it up walks the heap, 0.6 s for 8 million blocks.
- A function that waits for another thread never returns while watched.
