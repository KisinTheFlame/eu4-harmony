# First version design

Status: final (2026-10-27). For terms see [GLOSSARY.md](../GLOSSARY.md); for decisions that are hard to undo see [adr/](adr/).

## Goals and scope

- **Goal**: finish the framework first, then port regional-combat to a mod on the framework. The minimal example is generated by the scaffold; there is no separate example mod. Capabilities are designed in a general way and make no concessions to the port.
- **Audience**: the first version is for the author's own use only. The interface version is 0.x, with no promise of compatibility.
- **Repository**: the framework repository holds the proxy, the core, the SDK and the scaffold; the regional-combat port stays in its own repository ([ADR 0004](adr/0004-ports-live-outside-framework-repo.md)).
- **Naming**: user-facing folders and files always take the `eu4-harmony` prefix, never `harmony` on its own.

## Installation and process

- **Entry**: a `version.dll` proxy in the game's root folder; `eu4.exe` is left untouched ([ADR 0011](adr/0011-version-proxy-injection.md), which replaced the original `winmm.dll` proxy).
- **Installation**: ship an archive with installation instructions: copy `version.dll` and the `eu4-harmony/` folder into the game's root folder. The framework core and the framework's own interface assets are all in `eu4-harmony/`. If the root folder already has a `version.dll`, the instructions say to move it into `eu4-harmony/backup/` first; the proxy does not load it. Uninstalling is deleting these files and putting the backed-up `version.dll` back where it was. The framework itself is not distributed or updated through the Steam Workshop.
- **Registered baselines**: vanilla 1.37.5 (`9ad3efe1…`) and unrestricted (`97dd63…`). The two have the same section layout and differ by only 138 bytes inside the original sections.
- **Unregistered exe**: if the positions and sizes of its original sections match a registered baseline, and every dependency point (an address plus the bytes expected there, by default the first 16 bytes of a function) matches too, it is used as that baseline. Otherwise the game starts as usual, no extensions are loaded, and a notice says what does not match.

## Extensions

- **Form**: a native DLL exporting a C ABI ([ADR 0002](adr/0002-native-dll-extensions.md)). An extension is a Rust project and uses capabilities through the Rust SDK; the framework is written in C++ and Rust.
- **Between SDK and core**: the extension exports one entry function, and the framework passes it a function table that carries a version number and a length; new capabilities are only ever appended at the end.
- **Capability boundary**: extensions can use only the capabilities the framework provides; symbols, hooks, memory reads and writes, and native calls are used only inside the framework ([ADR 0005](adr/0005-extensions-use-capabilities-only.md)).
- **Discovery and enabling**: an ordinary Paradox mod plus `eu4-harmony/manifest.json`; `dlc_load.json` decides, and extensions are loaded once, when the game starts ([ADR 0003](adr/0003-discover-extensions-via-paradox-mods.md)). Enabled in the playset means loaded; there is no approval prompt.
- **Manifest**: `id`, `api_version`, `extension` (the DLL's relative path), `ui` (the interface fragments to inject). The author picks the `id`. It is the key for logs and extension save data, and the development copy and the Steam Workshop copy share it. Of a duplicated `id` only the one that appears first is loaded; the other is rejected and recorded in the startup report. Name, version and the like come from `descriptor.mod`.
- **Interface version**: during 0.x an extension is loaded only if its `api_version` is exactly the framework's; from 1.0 on, compatibility is judged by semantic versioning.
- **Lifetime**: no hot reloading; once loaded, an extension is not unloaded until the game process ends.
- **Threading model**: the framework calls extensions only at safe points on the game's main thread. Events raised during a callback are queued and dispatched after the current callback returns. Only "post to the game thread" may be called from any thread.
- **Code shape**: an extension implements one SDK trait, with one method per kind of event (empty by default). Event methods receive a "game" context; every capability is a method on it, and it is out of reach once the callback returns. The only thing that can be taken out of a callback and used from other threads is the "poster".
- **Errors**: panics and native exceptions are caught at the callback boundary. After that the extension is not called again (it is not unloaded), its interface elements are hidden, and one notice is shown and the error logged.
- **Between extensions**: extensions do not call each other and do not declare dependencies. The order in which one event is dispatched, the order of buttons in the button area, and coloring requests made at the same moment all follow the order of mods in the playset.

## First version capabilities

- **Session**: whether a game is in progress, the player's country, the current date, whether the game is paused.
- **Events**: every frame (fires while paused too), a day finished advancing, a save finished loading, a save finished writing, back to the main menu, the player gave an army an order by hand, an army was defeated.
- **Countries**: identifier; whether two countries are hostile.
- **Provinces**: owner, controller, neighboring provinces, whether visible to the player.
- **Armies**: owner, current province, current route and where it came from (the player, this extension, another extension, the game), state (in battle, sieging, retreating, movement locked), whether visible to the player.
- **Pathfinding**: ask for the game's own route from an army to a province.
- **Commands**: move an army to a province; stop an army. Each returns at once with "accepted" or "rejected + reason"; accepted does not mean arrived. An extension's own commands do not raise the "player gave an order by hand" event.
- **Interface**: buttons (telling left and right clicks apart), tooltips, coloring the map by province and restoring it; see the next section.
- **Localisation**: the player language and this mod's texts; see "Localisation".
- **Extension save data**: one piece of serializable data per extension, tied to a save by the save's identity (full SHA-256, save path, game date) and stored outside the save file; empty when the identity does not match ([ADR 0007](adr/0007-extension-save-data-outside-saves.md)).
- **Logging**: see "Logs and diagnostics".

Game objects are values made of the game's own stable identifiers: province number, country tag, the army's full 64-bit ID. Extensions may keep them as long as they like; the framework looks each one up again on every use and returns "does not exist" when it is gone. No pointers are exposed, and no handles that are valid only inside a callback. One read fetches a snapshot of one object; there are also list queries (such as all armies of one's own country, or a province's neighbors). Whether army IDs are reused within one session has not been verified.

## Interface

- **Injection**: the framework splices text into `.gui` files as the game reads them, hooking the PhysFS functions that eu4.exe exports by name; mods do not override vanilla `.gui` files ([ADR 0006](adr/0006-inject-ui-at-runtime.md); the evidence is in [research/ui-injection.md](research/ui-injection.md)).
- **Host window**: by design any vanilla window can be one; the first version verifies and opens only the single army panel, `single_unitpanel`.
- **Declaration**: interface fragments are written in Paradox `.gui` syntax in the mod's own files, and the manifest's `ui` field declares the fragment files and their host windows. Fragments that go in the button area are marked `"area": "buttons"`; the coordinates of other fragments are relative to the host window. Sprites go in a new `.gfx` file of the mod's own.
- **Naming**: injected elements get the prefix `eu4harmony_<id>_` added to their names in the game automatically, while extension code keeps using the original names; a mod only has to avoid duplicate names within itself.
- **Button area**: a vertical strip against the outer right edge of the army panel's background image (`regiment_bg`, a fixed 516×450 image), with a stretchable bordered background. Buttons are all 48×48 and spaced 44 pixels apart, and a new column starts after 7. Sizes and coordinates are worked out from all the manifests at splice time; a button hidden at run time leaves its slot empty, and the strip does not shrink. The vanilla panel is not changed.
- **Map coloring**: belongs to one extension at a time. A new request takes over from the old one, and the extension it took over from receives a "coloring taken over" event; when the holder releases it, the original map mode is restored.
- **Text**: text an extension sets through the SDK is always passed as UTF-8 and shown by the framework's Unicode module, which can draw any character ([ADR 0010](adr/0010-built-in-unicode-module.md)).
- **Notices**: cases such as an extension stopped after an error, or a duplicated `id`, are shown in the framework's own in-game notice window. It deliberately looks different from vanilla dialogs, so the player sees at a glance that the framework is speaking, not the game. The notice window is spliced into two vanilla windows that are always there, the main menu and the in-game top bar ([ADR 0008](adr/0008-notice-window-in-vanilla-hosts.md)); notices raised before the main menu appears are queued first. When the exe is not recognized, the framework hooks no game functions and falls back to a Windows message box; it does the same when showing a notice in the game fails. Each case is shown at most once per session. The wording is in the player language.

## Localisation

The reasons are in [ADR 0009](adr/0009-localisation-in-the-player-language.md).

- **Player language**: the framework's and every mod's texts are shown in this language for the session. It is decided once per start: Simplified Chinese when the Windows display language is Chinese, otherwise the language in the game's settings (English, French, German or Spanish) ([ADR 0010](adr/0010-built-in-unicode-module.md) replaced the original extra condition "and the CJK font plugin is installed"). The decision is made in one place only, the core's `lang` module; everything else only reads the result. Adding an in-game language setting later means changing only this place.
- **Localisation files**: a mod puts them at `eu4-harmony/localisation/<name>_l_<language>.yml`, in the game's format (` KEY:0 "text"`), with plain UTF-8 content. `\n` is a line break, and `$NAME$` is a value filled in by code. The language names available are `english`, `french`, `german`, `spanish` and `simp_chinese`. A key missing from the player language falls back to English; if English lacks it too, the key's name is shown.
- **Keys used by interface fragments**: the framework takes the keys of the mods in this load, in the player language, and appends them unchanged to the end of `localisation/text_l_<language>.yml` for the game's current language, so interface fragments can use them as they use vanilla keys. Keys share one namespace with vanilla, so authors add their own prefixes; when several mods define the same key, the one earlier in the playset wins, and this is recorded in the startup report.
- **Texts at run time**: an extension gets its own mod's texts with `game.text(key)` and `game.text_with(key, values)`, and the player language with `game.language()`.
- **The framework's own texts**: the wording of notices and the settings window is built in, in every player language: English, French, German, Spanish and Simplified Chinese (`core/localisation/`). Error details, logs and the startup report stay in English.

## Developer tools

- **SDK**: a Rust crate, referenced in the first version as a local path dependency and not published to crates.io. It provides logging macros.
- **Fake game**: the SDK comes with an in-memory fake game for writing extension unit tests without EU4. It is only a data store and does not simulate game rules: tests set out snapshots directly, choose pathfinding results and raise events by hand; commands and interface actions are only recorded and have no effect. It can read a mod's real localisation files in a given language.
- **Scaffold**: the command line tool `eu4-harmony.exe`, with Rust templates only.
  - `new <id>`: creates a mod in the current folder: `descriptor.mod`, `eu4-harmony/manifest.json`, localisation files in Chinese and English, and a Rust extension project that depends on the SDK (with an example event handler and a test written against the fake game).
  - `build`: builds in release mode and copies the DLL to `eu4-harmony/win64/`.
  - `link`: writes `<id>.mod` under `mod/` in the user folder, with `path=` pointing at the development folder; nothing is copied. Then tick the mod in the launcher by hand. It does not change `dlc_load.json`.
  - `package`: produces a clean folder to upload, holding only `descriptor.mod`, the game assets, and the manifest, interface fragments, localisation files and DLL under `eu4-harmony/`; it refuses to package when a localisation file has errors. Uploading uses the tool that comes with the Paradox launcher.

## Logs and diagnostics

- The framework writes one log file per extension, plus a framework log and a startup report (which mods it found, and whether each extension loaded and why). They all go in `eu4-harmony/logs/` in the user folder and are overwritten at each start; one copy from the previous start is kept.
- The framework records how long every callback of every extension takes. A single callback over a threshold (such as 5 ms) is logged, and the startup report includes a summary of each extension's time.

## Not in the first version

Approval prompts; detecting multiplayer (only a statement that just single player is supported); hot reloading; extensions calling each other; signature scanning; C headers and C++ templates; distributing or updating the framework through the Steam Workshop; an installer; switching language in the game; Japanese and Korean; rearranging the button area at run time; capabilities that intercept or rewrite results in the middle of the game's calculations; host windows other than `single_unitpanel`.

## Order of work

First build a prototype that runs the whole chain: `winmm.dll` proxy → find mods → splice in one button → write a log line when it is clicked. Use it to test the following in the game; only when all of them pass, build out the rest as this document describes:

1. When the proxy loads, and chain-loading an existing `winmm.dll`.
2. Which thread loads GUI definitions (the main thread or LoadingThread); the hooks are thread safe.
3. The format of the paths passed to `PHYSFS_openRead` for the target files; there is no second read path or cache.
4. Coexisting with mods that override the same `.gui` file: the splice applies to the file that wins.
5. The spliced text parses cleanly: the button appears in the panel, and `error.log` shows no duplicate names or syntax errors.
6. The interface declarations are ready in time for `LOADING_GUI_DEF`.
7. After `reload` / `reloadinterface` the splice still takes effect, and the binding is made again correctly as the panel is rebuilt.
8. Coexisting with other native plugins that hook PhysFS; the entry bytes are checked before hooking.
9. The game can read the framework's interface assets in `eu4-harmony/` (the notice window's textures and so on) by paths relative to the game's root folder.
10. The notice window spliced into the main menu and the top bar can be shown and closed, and is bound again after its host window is rebuilt.
11. The game reads localisation files through `PHYSFS_openRead`, and the appended mod keys can be used by the interface; the CJK font plugin is already loaded when the language is decided.
